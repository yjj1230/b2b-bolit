2 · 总体策略与部署拓扑

2.1 为什么“先主库、再做备库、发布前提升为可写副本”

  • 新生产环境从 0 构建，而旧生产环境（数据库 / 飞书多维表 / 飞书三方审批流程）正在真实运作，不能停。
  • 现场程序员已完成本地 PostgreSQL 与所需数据同步，并交付 pgAPI 读写 API——这是 0.1 的数据底座。
  • 主库：同步节点 + 校验/回填/准备工作的主战场；备库：数据副本，发布前提升为可写副本后承载 v0.1。
  • 切到可写副本 = 一次不打扰旧环境的生产级预演；副本出问题，旧飞书流程照常，商务无损。
  • 本次是“本地数据 + 本地服务”的特殊部署；未来 SaaS 化后，现场只保留少量数据适配，云端为主——因此本次所有现场配置都要沉淀成可复用的部署手册与配置模板，而不是一次性操作。

11 · 本期明确不做（防蔓延）

  • 不做全量用户迁移（财务/仓管仍走飞书）。

  • 不做 purchase-contracts 在 b2b 的写接入与对账（H4 完整接入）；只做只读可见（M-05，D-007 Q1=B）。
  • 不做 b2b 对外产品/客户管理 HTTP 端点（H5）。
  • 不做 pgAPI 缓存/重试降级策略（H6）。
  • 不启用企微订单 → 购销合同表写路径（D-007 Q1=B：只做只读可见；写路径下一迭代 OI-016）。
  • 不激活 ECM（OI-001/002 仍开放）。
  • 不做云端 SaaS 化改造（本期只沉淀现场配置为可复用资产）。
