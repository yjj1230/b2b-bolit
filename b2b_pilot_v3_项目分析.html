第一章 · 总览

0.1 冲刺：一个人先跑起来

以长安仁恒为样板客户，落地「客户开口 → 订单 → 审批 → 备货 → 发货 → 回单开票 → 归档」的完整履约闭环。当前阶段不再是全量验证，而是 0.1 版上线冲刺：先让商务虹励一个人用起来，飞书原流程不停。

B2B 订单履约型企业的经营长期在两处承压：订单侧，客户在群里口头要货、销售手工建单、听错数量、漏单催单；履约侧，审价靠人盯、备货发货开票三大闸门分散在不同会话、回单不齐卡住开票、超发错发难防。b2b_pilot_v3 的回答是：把「群聊一句话」与「订单履约闭环」合并为一个企微原生的验证项目——行为一次采集，流程处处留痕，授权按图判定。0.1 的答案更收敛：把自动下单移出一期，把财务、仓管留在飞书原流程，用数据同步让飞书侧数据在本系统流里可见可操作，先让虹励一个人跑通全流程。

2.2 · 关系类型：世界的动词

关系是带方向的语义边，标注 domain → range。关系的精确性决定下游查询的可靠程度——这里不用「相关」这种模糊动词，每条关系都对应一种明确的业务事实，且每条关系至少服务一个能力问题。0.1 新增四条关系：发票关联、守门员守卫、机器人抓取、仓库群归属。

守恒是业务与代码之间的桥，0.1 的桥只修需要走的那几段。备货、发货、库存、开票四道守恒把「不超发、不多开、不漏发」翻译成可校验的数值不等式；锁库存暂缓不等于删掉守恒——表、约束、校验逻辑全部保留，只是不启用扣减链路。凭证把现实世界的动作锚定到订单（后台主路径 + 机器人兜底），守门员把「什么能到客户面前」变成一条可审计的边界。没有守恒，流程只是自述；没有凭证，审计只是一堆日志；没有守门员，自动化就是惊吓。

第五章 · 项目机制

证据收敛式迭代：项目如何自我治理

双图谱回答「业务与产品如何对齐」，ECM（Evidence-Convergent Mechanism）回答「项目如何演进、交接与验收」。机制身份：ECM 1.0.0 · PROPOSED（bootstrap 落库，未激活）。

项目不是一条从需求到代码的流水线，而是一组异步更新、粒度不同、权威范围不同的事实与承诺。机制的任务不是选出一份「最新文档」，而是持续回答：每条声明现在是什么状态，谁有权决定它，哪些制品已经跟上，哪些证据仍然有效，下一步改哪里最能推动项目向前。目录只表达制品的职责与生命周期；真正的决定性必须落在带稳定 ID 的声明、决策、实现和证据关系上。

5.1 · 三态正交与九种关系

「已决定、已实现、已验证」是三个不同维度，禁止合并成一个「状态 = 完成」。例如 0.1 的发群守门员是 ACCEPTED（A3 拍板）+ IMPLEMENTED(demo) + UNVERIFIED(backend)；自动下单是 DEFERRED(vNext) + 部分实现保留——两者都不是「完成」，也不能互相冒充。关系是治理的边：DERIVED_FROM / REFINES / IMPLEMENTS / VERIFIES / DECIDES / SUPERSEDES / DEPENDS_ON / CONFLICTS_WITH / VALID_DURING。一条「群内金额不可见」声明会同时约束 demo 截图、API 投影、ReBAC、测试和产品说明——影响半径沿边计算，变化只作废受影响证据，不全量重跑。

三组状态必须分开（Semantic / Implementation / Verification）
