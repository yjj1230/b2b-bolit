0 · 方法论定位

Graph Engineering 分两个半边，本项目完整应用：

半边回答的问题本项目的落地物
🧠 知识图谱智能体/系统记住什么§1 世界知识图谱：订单、客户、产品、库存、授权、事件的 ontology
⚙️ 任务图谱智能体/系统如何工作§2 任务图谱：ORD / STK / SHP / INV 四流程状态机 + 主流程/子流程编排 + 预订单 AI 流程
核心心智模型：先建模后抽取、先融合后存储、每个阶段都验证。本体是有 schema 的产品，不是三元组的堆砌 —— 本文档从能力问题（competency questions）出发定义 schema，能力问题同时就是后续测试的规格（见 03-testing.html 的 roundtrip 映射表）。

业务事实基线（源自 spec/ 调研）：

  • 客户样板：长安仁恒，订单履约型 B2B 企业，四仓（阳原 / 长兴 / 东莞 / 成都），销售用公司工作机登录个人微信（可被会话存档）。
  • 履约闭环四分支：ORD 订单创建 → STK 备货审批 → SHP 发货分配及出库 → INV 开票回单审批 → 回款跟踪 → 合同归档 → 订单关闭。
  • 三方审批 = 商务 · 财务 · 仓管 三方协同；客户 C/D 级触发董事长审批；款到发货按供方分流财务确认到账。
  • 核心业务原则：① 订单提交 ≠ 已履约，状态必须由实际业务结果汇总；② 回单不卡开票（四分流）；③ 仓管不查看价格/金额；④ 销售只看本人客户；⑤ 流程可审计、可回溯、版本固化。
  • 技术输入：SpiceDB RBAC+ReBAC 混合、Temporal 主流程+子流程+Signal/Timer、企微 S1–S4 场景、AI 安全边界（LLM 只产候选 + 确定性代码校验 + 人工确认才生效）。

1 · 世界知识图谱（World Knowledge Graph）

1.1 能力问题 —— 本体的规格与测试

方法论要求：先写能力问题，再设计 schema，克制添加实体，直到某个能力问题要求为止。

#能力问题（CQ）所属域
CQ-01用户 U 对订单 O 当前拥有哪些操作权限（查看 / 提交 / 审批 / 备货 / 发货 / 开票 / 关闭）？授权
CQ-02用户 U 的数据可见范围是什么？（销售本人及代办 / 商务全公司 / 仓管本仓 / 财务按供方分流 / 管理层全量）授权
CQ-03仓管查看订单时，价格/金额字段是否已被剥离（字段级授权投影）？授权
CQ-04订单 O 当前处于什么状态？允许哪些状态迁移？哪些迁移是禁止的？流程
CQ-05订单 O 的审批链（销售主管审价 → C/D 级董事长）当前状态与结果是什么？流程
CQ-06备货守恒：订单 O 的累计备货确认量是否 ≤ 订单数量（含分批、退回、转仓）？业务一致性
CQ-07发货守恒：累计发货量 ≤ 备货量？订单全部发货（累计发货 = 订单量）的完成条件是否成立？业务一致性
CQ-08库存联动：实际发货与库存扣减是否同事务？任何时刻库存不为负？业务一致性
CQ-09开票守恒：累计开票金额/数量 ≤ 可开票金额/数量（按有效发货计算，双维度）？（开票不超发货，回单不卡开票）业务一致性
CQ-10订单 O 的回单状态（按发货批次汇总：未回 / 部分 / 全部；无回单超 5 天自动进例外审核）？流程
CQ-11企微消息 M 生成的预订单当前状态与确认结果？消息 → 预订单 → 正式订单的全链幂等是否成立？流程 + AI
CQ-12订单 O 的完整事件链（谁、何时、何因、结果）是什么？能否回放？流程 + 审计
CQ-13代办授权 D 是否在有效期内？到期后代办权限是否即时失效？授权
CQ-14哪些操作并发作用于同一订单/库存（重复确认、超发、重复开票、并发扣减）？如何被阻止？业务一致性
CQ-15凭证链（签收单/回单）是否只追加不覆盖？任一版本能否回放？上传者权限如何界定？流程 + 审计

这 15 个能力问题即本体存在意义的判据：schema 中每个实体/关系/事件都必须至少服务一个 CQ，否则删除。

1.2 本体 Schema（Ontology）

# ontology.yaml —— 项目单一事实源（此处的权威版本；实现后由代码 schema 回填并 roundtrip 校验）
entities:
  Tenant:      { desc: 企业租户（长安仁恒 / 智厨…），多租户隔离根节点, ex: [chang-an] }
  User:        { desc: 系统用户（销售/销售主管/董事长/商务/财务/仓管/管理员）, ex: [alice-sales] }
  Customer:    { desc: 客户，带等级（A/B/C/D，C/D 触发董事长审批）, ex: [cust-0001] }
  Product:     { desc: 产品（标准型号，SKU 归一化目标）, ex: [SKU-C68] }
  Warehouse:   { desc: 仓库（阳原/长兴/东莞/成都）, ex: [wh-yangyuan] }
  Order:       { desc: 订单主档（统一订单总表），四分支状态机载体, ex: [ORD-2026-0001] }
  OrderItem:   { desc: 订单产品明细（产品/数量/单价/账期/仓库分配）, ex: [item-01] }
  StockPrepare:{ desc: 备货审批聚合（预定量/到款确认/仓库分配/出库单）, ex: [STK-0001] }
  Shipment:    { desc: 发货单（一次发货，关闭后不再自动新建）, ex: [SHP-0001] }
  Invoice:     { desc: 开票申请/发票（状态：待开票/处理中/已开票/失败/无需开票）, ex: [INV-0001] }
  PreOrder:    { desc: 预订单（企微群消息 → AI 候选 → 人工确认 → 正式订单）, ex: [PRE-0001] }
  ApprovalTask:{ desc: 审批任务（主管审价/董事长/仓管确认/财务到账/回单异常）, ex: [AT-0001] }
  Event:       { desc: 事件（append-only 事件链，审计回放根基）, ex: [EV-0001] }
  Evidence:    { desc: 凭证（签收单/回单，只追加版本，rebac 场景 D）, ex: [EVD-0001] }
  Permission:  { desc: 授权关系（RBAC/ReBAC + caveat），由 SpiceDB 托管, ex: [alice:ship@wh-yangyuan] }

relations:
  BELONGS_TO:   { domain: User,      range: Tenant,    desc: 用户属于租户（多租户隔离） }
  OWNS:         { domain: User,      range: Customer,  desc: 销售负责客户（ReBAC 直接关系） }
  DELEGATED_TO: { domain: User,      range: User,      desc: 代办授权（caveat: 有效期） }
  COVERS:       { domain: Order,     range: Customer,  desc: 订单属于客户 }
  CONTAINS:     { domain: Order,     range: OrderItem, desc: 订单含明细（可多条） }
  EXECUTES:     { domain: Warehouse, range: OrderItem, desc: 明细执行的仓库（仓库分配） }
  STORES:       { domain: Warehouse, range: Product,   desc: 仓库库存（数量，数量守恒载体） }
  PREPARES:     { domain: Order,     range: StockPrepare, desc: 订单产生备货审批（可分批） }
  FULFILLS:     { domain: StockPrepare, range: Shipment, desc: 备货审批产生发货单（可多张） }
  GENERATES_INV:{ domain: Order,     range: Invoice,   desc: 订单产生开票（可合并/拆分） }
  DERIVES:      { domain: PreOrder,  range: Order,     desc: 预订单确认后派生正式订单（1:1） }
  TRIGGERS:     { domain: PreOrder,  range: Event,     desc: 预订单产生事件（msgid 幂等） }
  PRODUCES:     { domain: Order,     range: Event,     desc: 订单产生事件（append-only） }
  CONTACT_OF:   { domain: User,      range: Customer,  desc: 客户联系人（rebac 场景 D/H，customer#contact） }
  ASSIGNED_TO:  { domain: User,      range: Shipment,  desc: 仓管被分配发货单（rebac 场景 C，shipment#warehouse_operator） }
  REQUESTS:     { domain: User,      range: Shipment,  desc: 发货发起人（rebac 场景 B/F，shipment#requester） }
  UPLOADS:      { domain: User,      range: Evidence,  desc: 凭证上传者（rebac 场景 D，evidence#uploader） }

events:
  PreOrderCaptured:   { trigger: 企微会话存档拉到消息, args: [tenant, group, msgid, intent_features, archive_ref] }
  IntentParsed:       { trigger: 意图识别（LLM 候选+确定性校验）, args: [pre_order_id, confidence, candidates] }
  PreOrderConfirmed:  { trigger: 销售人工确认（卡片按钮）, args: [pre_order_id, operator] }
  OrderRequested:     { trigger: 预订单确认 或 销售/代办快速下单, args: [order, customer, items] }
  OrderModified:      { trigger: 已生效订单修改请求（按 A/B/C/D/E 分类走不同回退路径）, args: [order, class, revision, resubmit_root_flow_id] }
  PriceReviewed:      { trigger: 销售主管审批, args: [task, verdict: APPROVED/RETURNED/REJECTED] }
  ChairmanReviewed:   { trigger: 董事长审批（仅 C/D 级）, args: [task, verdict] }
  ContractGenerated:  { trigger: 合同生成校验通过, args: [order, contract_no] }
  StockAssigned:      { trigger: 商务备货（选仓+发货量）, args: [order, warehouse, qty] }
  WarehouseConfirmed: { trigger: 仓管确认可执行/退回/申请转仓, args: [task, verdict] }
  PaymentConfirmed:   { trigger: 财务确认到账（按供方分流）, args: [task, ledger_ref] }
  ShipOrderIssued:    { trigger: 商务发出发货命令, args: [order] }
  GoodsShipped:       { trigger: 仓管填实际发货量（库存联动事务）, args: [shipment, qty] }
  InvoiceApplied:     { trigger: 提交开票申请, args: [order, items] }
  InvoiceIssued:      { trigger: 财务确认开票完成, args: [invoice, tax_no] }
  PaymentTracked:     { trigger: 回款登记, args: [order, amount] }
  ReceiptException:   { trigger: 无回单超 5 天 Timer / 提交人提前申请, args: [order, shipment_ids] }
  OrderClosed:        { trigger: 合同归档完成, args: [order] }
  FlowFailed:         { trigger: 异常/超时/补偿, args: [order, error, compensation] }

constraints:
  - 备货守恒: "∑(备货确认量) ≤ 订单数量（每明细）"
  - 发货守恒: "∑(发货量) ≤ ∑(备货量)；订单全部发货 ⇔ ∑(发货量) = 订单数量"
  - 库存守恒: "库存 = 初始 + 入 - 出（出与发货同事务，恒 ≥ 0）"
  - 开票守恒: "∑(开票金额) ≤ ∑(可开票金额)；∑(开票数量) ≤ ∑(有效发货数量)（金额+数量双维度，开票不超发货；available_invoice_amount/qty 随发货推进更新）"
  - 回单不卡开票: "无回单超 5 天自动进例外审核，不阻断开票流程"
  - 事件不可变: "Event 只追加（append-only），无 UPDATE/DELETE"
  - 原始聊天不落业务库: "事件链只存意图特征与存档引用（archive_ref），原始文本存独立加密可过期存档，业务库零留存"
  - 消息幂等: "同一 (tenant, group, msgid) 只生成一个 PreOrder"
  - 订单幂等: "同一 idempotency_key 只生效一次（预订单确认与快速下单共用）"
  - 修改分类: "A/B/C/D/E 修改分类规则为配置数据（源自三方审批流程图原图 fig12/13），不同类别走不同流程动作；修改产生新 revision（resubmit 链）"

1.4 授权本体（SpiceDB Schema 设计）

// schema.zed —— RBAC/ReBAC 合一 + caveat（条件关系）的图式授权
// 设计来源：docs/01-core-graph.html §1.4（权威版本）+ spec/rebac_cases_spicedb.html 全景表
// 三层模型：租户隔离（tenant->member 兜底）→ 资源级关系（ReBAC：account_owner/contact/
//   owner/warehouse_operator/requester/uploader）→ 条件关系（caveat：expiry_ok 代办时效；
//   阶段二：within_void_window 作废窗口）
// 注：SpiceDB v1.39 起权限表达式中的图遍历使用 `->` 箭头；版本固定：spicedb v1.39+，
// M1 门禁要求 schema 实际编译通过（L1-07 集成测试前置）。
// 【实施校准（roundtrip）】v1.33+ caveat 语法为「名 类型」空格分隔（冒号形式已移除），
// 且 CEL 环境不含内置时钟：`now` 是 caveat 参数，判定侧由 authz.Checker 注入（RFC3339）。
// 【人类架构师决策（2026-08，docs/CHANGELOG-rebac-cases.html §6）】
//   D1 全量迁移：prestock/shipment/evidence 一等授权对象（order 保留聚合视图）
//   D2 命名统一：customer.owner → customer.account_owner
//   D3 权限细化：8 个细粒度 permission（create_prestock/change_quota/request_shipment/
//      confirm/reject/append_evidence/void/close）
//   D4 Outbox 投影器落地：业务事务写 outbox_event → 投影器同步 SpiceDB 关系（场景 G/H）

definition order {
    relation owner: user                    // 下单销售（本人）
    relation delegate: user with expiry_ok  // 代办（caveat）
    relation reviewer: user                 // 审批链当前节点（主管/董事长/商务/财务）
    relation customer: customer             // 层级边：经 customer 继承 account_owner/ops
    relation tenant: tenant
    relation warehouse: warehouse           // 发货仓（ReBAC 层级边）：仓管经此获得发货权

    // 读权限：销售本人+代办、客户 account_owner、本仓仓管、管理层（联系人见 shipment#customer_contact）
    permission view            = owner + delegate + customer->account_owner + customer->delegate + warehouse->staff + tenant->ops + tenant->admin
    // 写权限：仅销售本人/代办/商务（提交、修改）
    permission edit            = owner + delegate + tenant->ops
    // 审批权限：审批链节点 + 管理层
    permission approve         = reviewer + tenant->admin
    // 场景 A 聚合入口：客户负责人（经 customer 层级边）或商务可开备货单
    permission create_prestock = customer->create_prestock + tenant->ops
    // 备货/发货（聚合视图；对象级判定见 prestock/shipment）
    permission stock           = tenant->ops
    permission ship            = tenant->ops + warehouse->manage
    // 财务确认到账：财务角色 + 供方分流关系（关系按 tenant->accounting + reviewer 绑定）
    permission confirm_payment = reviewer + tenant->accounting + tenant->admin
}

ReBAC 的体现（含 rebac_cases_spicedb.html 场景 A–H）：customer->account_owner 层级边使客户负责人自动获得其客户下订单/备货单的权限（新增订单无需逐条授权）；customer.contact 使客户联系人获得发货单物流视图（场景 D，字段投影裁剪价格）；prestock#owner/shipment#warehouse_operator/shipment#requester 为对象级直接关系（场景 A/B/C，创建/分配时由 Outbox 投影器自动写入）；delegate 用 caveat expiry_ok 表达代办有效期（CQ-13，场景 G：TTL 到期 Outbox 删除元组）；撤销即删边，即时生效（FullyConsistent 读）；跨租户由 & tenant->member 语义兜底（场景 E）。

决策后改动点清单（无论选 A/B，仅改以下 5 处，其余不变）：① INV 状态图入口条件（READY_FOR_INVOICE 进入标签）；② domain/receipt.go 分流判定（款到/回单分流是否需先有发货）；③ L0-04/L2-10 用例断言（INV FSM 入口合法迁移集合）；④ L3-02 对账规则（开票守恒是否包含「无发货即开票」违规项）；⑤ 验收脚本断言。

3 · 图谱维护规则（方法论纪律）

  1. 克制添加：新增实体/关系必须先绑定一个 CQ，否则不加。
  2. 事实单一来源：数量守恒基准只在 order_items.quantity；库存只在 warehouse × product；任何状态更新必须与事件链同事务。
  3. 授权是图不是表：权限判定只走 SpiceDB（应用代码不做 if-else 硬编码授权），授权变更即图拓扑变更；字段级投影由 BFF 基于授权判定结果执行。
  4. 事件链完整：每个订单/预订单的每步迁移都产生事件，事件不可删改（append-only）。
  5. 人工闸门不可绕过：任何 AI/自动化路径都不得生成正式订单或推进关键审批节点（Signal 之外无旁路）。
  6. roundtrip 是验收：代码实现后必须能回答本文档全部 15 个 CQ；答不出的就是设计裂缝。
