数据流（对应图谱 §1.5 事件图）：

路径说明
企微 → 预订单会话存档拉取（cmd/wecom）→ 消息幂等落库 → 意图识别 → 预订单 → 销售确认卡片 → Signal → 正式订单（幂等键）

设计原则（沿用 pilot_app 并扩展）：

  1. 状态机显式化：四个流程 + 预订单的状态迁移全部由图谱定义，代码用同一 FSM 表驱动（单一事实源）。
  2. 副作用与决策分离：Workflow 只做确定性决策（状态迁移、Signal 等待、Timer 编排）；PG/SpiceDB/企微副作用全在 Activity。
  3. 授权纵深防御：API 预检 + 每个业务副作用 Activity 内再次 CheckPermission；企微出站与入站分别验签。
  4. 幂等优先：预订单（msgid）、订单、发货单、开票全部带幂等键，DB 唯一约束兜底。
  5. 可对账：数量守恒（备货 ≤ 订单、发货 ≤ 备货、开票 ≤ 发货、库存 ≥ 0）任何时刻可聚合校验。
  6. 人工闸门为核心：三方审批是业务主体（Signal 等待 + Timer 催办升级），AI 路径不得绕过（安全边界）。

2.3 SpiceDB 授权整合

2026-08 升级（人类架构师决策 D1-D4，见 docs/CHANGELOG-rebac-cases.html §6）：授权对象从 order 级粗粒度升级为 prestock/shipment/evidence 一等授权对象（spec/rebac_cases_spicedb.html 全景表）；关系元组由 Outbox 投影器自动同步。
  • 唯一授权判定点：所有权限判定走 authz.Checker → SpiceDB CheckPermission（FullyConsistent，撤销即时生效，CQ-13）；应用代码零硬编码授权。
  • 三层模型：租户隔离（tenant->member 兜底，场景 E）∩ 资源级关系（ReBAC：customer.account_owner / customer.contact / prestock.owner / shipment.warehouse_operator / shipment.requester / shipment.customer_contact / evidence.uploader）∩ 条件关系（caveat expiry_ok 代办时效；阶段二 within_void_window 作废窗口）。
  • 对象级授权：备货单/发货单/凭证各自独立 SpiceDB definition（场景 A/B/C/D 的精确隔离）；order 保留为跨段聚合视图（create_prestock 聚合入口 = customer->create_prestock + tenant->ops）。
  • 字段级投影（CQ-03，BFF 执行）：
    • 仓管视图（shipment#warehouse_operator 判定通过）：剥离 unit_price_cents / 金额字段 / 销售内部备注
    • 客户联系人视图（shipment#customer_contact 判定通过）：只暴露物流状态 / 凭证，剥离价格 / 内部备注 / 审批链
    • 双保障：SpiceDB 资源范围判定 + BFF 字段投影
  • Outbox 投影器（D4 落地，场景 G/H 前提）：
    • 业务事务内写入业务数据 + outbox_events 表（Transactional Outbox 模式）
    • Go 投影器异步消费 → SpiceDB WriteRelationships / DeleteRelationships，幂等可重放
    • 投影规则：备货单创建 → 写 prestock#owner；发货单创建/分配 → 写 shipment#requester / shipment#warehouse_operator；客户联系人变更 → Delete 旧 + Write 新（场景 H）；代办 TTL 到期 → Delete delegate 元组（场景 G）
    • 保证「业务库关系 = SpiceDB 判定关系」
  • 授权关系变更：WriteRelationship / Touch / Delete（离职交接 = 删 account_owner 边 + 加新边；代办授权 = 带 caveat 的 delegate 边），不影响进行中流程。
  • 测试替身：StaticChecker（checker.go 模式）使 API/Workflow 单测零 SpiceDB 依赖；L1 集成用 spicedb testserver 覆盖权限矩阵（8 场景）。

3 · 数据库设计

4 · 一致性防线（业务守恒 · 层层兜底）

pilot_app 的「7 层一致性防线」针对资金守恒；本项目针对数量守恒与状态可信（业务原则：订单提交 ≠ 已履约），防线同构、语义替换：
#防线位置防什么对应 CQ
1CHECK 约束DB负库存 / 负数量 / 超量发货（qty>=0、quantity>0、shipped_qty<=planned_qty）CQ-06/07/08
2行锁 SELECT ... FOR UPDATE库存扣减 / 守恒校验 Activity并发发货超卖、并发确认竞态CQ-08/14
3UNIQUE(tenant_id, idempotency_key)DB 约束重复下单 / 重复发货 / 重复开票 / 重复建预订单（Temporal 重放安全）；跨租户同键互不影响CQ-11/14
4单事务多写发货 + 库存扣减；开票 + 守恒校验；状态 + 事件链部分生效（发货了库存没扣 / 开票超发货量）CQ-07/08/09
5守恒聚合校验事务内聚合 + L3 脚本∑发货 ≤ 订单量、∑开票金额 ≤ ∑可开票金额、∑开票数量 ≤ ∑有效发货数量、库存恒 ≥ 0（对账根基）CQ-06/07/08/09
6FSM 表驱动领域层非法状态迁移（如开票量超可开票量、未备货就发货；「开票独立于发货」见 §7 ADR 与 01 §2.5 开放问题）CQ-04
7补偿/回退路径幂等Saga / 退回 / 转仓部分失败后订单状态与事实一致（退回重提、转仓换仓、开票失败重试）CQ-04/09/14

双重表述：PG orders.state + order_events（事实与审计）⇄ Temporal History（执行轨迹）；两者都不可变可回放，任一缺失可从另一侧重建（验证项目设计既定）。

5 · 幂等机制（三层叠加）

层机制示例

8 · 数据迁移布局（为既有数据迁移提前布局）

设计意图（meta.md + 用户确认）：理解原三方系统（spec/biz/飞书三方审批系统存储表及字段说明.md）的存储 schema，是为后续迁移既有数据提前布局。本 baseline 不实施迁移，但以下布局必须在建表/编码时预留，否则迁移成本随数据量线性膨胀。

8.1 原系统存储模型（迁移源）

  • 非关系型：JSONL 追加式数据文件——一行一条 JSON 记录，业务状态变化即追加新记录；「同一业务编号多条记录 = 不同时间的状态快照」。
  • 16 张逻辑表：四审批环节主表+事件表成对（orders/order_events、stock_prepares/stock_prepare_events、shipments/shipment_events、invoices/invoice_events）+ 8 张横切表（approval_comments、external_instances、background_jobs、bitable_flow_records、callbacks、customer_bitable_sync、approval_bot_messages、warehouse_notice_cards）。
  • 贯穿键：flow_id 贯穿一笔订单的 ORD→STK→SHP→INV 四环节；每环节 stage_id（审批实例）+ stage_code（ORD/STK/SHP/INV）+ stage_seq（环节/分批序号）；审批任务 instance_id / task_id / current_task_id。

8.3 迁移执行策略（后续阶段，非 baseline）

  1. 分阶段：ORD → STK → SHP → INV 逐环节迁移（与原系统四阶段一致），每阶段验证守恒后再进入下一段。
  2. 快照优先、事件不伪造：先迁当前状态（最新有效快照）；源 *_events 原样进入对应分域事件表或只读归档。仅有快照、没有源事件时可生成带 source=SNAPSHOT_DIFF 标记的推导事件，不得冒充原始操作证据。
  3. 双跑窗口：迁移期间新旧系统并行，legacy_flow_id 映射支撑追溯与回滚。
  4. 迁移验证：复用 L3-02 对账脚本（四守恒全库聚合）在迁移后全量执行 + 抽样比对（原 JSONL 最新快照 vs PG 当前态）。
  5. 幂等红线：迁移工具本身幂等（migration_batches 批次表，可重跑不重复）。
  6. 租户前缀：原系统为单租户；迁移时统一补 tenant_id（多租户隔离总则，§3.1），缺省映射到默认租户并人工核验。
建表预留清单（编码时即做，避免后补）：§3.1 已将预留项纳入正式表清单，包括 orders.legacy_flow_id/submission_mode/resubmit_*、stock_prepares/stock_prepare_items/stock_prepare_events、shipments.stock_prepare_id/batch_seq/split_flag/previous_shipment_id/remaining_quantity、shipment_events/invoice_events、approval_comments、legacy_flow_mapping 与 migration_batches。横切过程记录在迁移阶段进入 legacy_* 只读归档，不参与 baseline 业务写路径。
