诚实声明：

  1. 与 95%/98% 目标的差距（约 320 个语句）全部位于防御性错误分支：pgx 行扫描错误（需 schema 损坏才能触发）、每句 SQL 的 if err != nil 返回（已用触发器级故障注入覆盖主事务路径：建单/发货/开票/事件中途失败全量回滚）、以及物理不可达分支（如 ReconcileInventory 的负库存分支被 CHECK(qty>=0) 阻断，是「防线生效」而非「测试缺失」）。
  2. 错误注入手段（删表/触发器/唯一冲突/关连接池）≠ 真实故障形态（网络抖动/磁盘满/企微限流 45009）；覆盖率 87.8% ≠ 故障注入等价性 100%。
  3. 正确性核心（domain 100%：FSM 穷举/守恒断言/幂等键/值对象）与防线（CHECK/行锁/幂等/单事务守恒，L1 全绿 + 触发器级回滚验证）均有专项背书。

4 · 覆盖倒推影响面（测试失败 → 设计点）

  • 第一梯队·守恒：L1-03/04（行锁/单事务）、L1-05（开票双维）、L3-01（并发脚本）、触发器级回滚验证 → 防线 1/2/4/5
  • 第二梯队·幂等：L1-02（含跨租户）、L2-12/13（预订单双层）、L2-02（修改 revision 链）→ 防线 3/7
  • 第三梯队·授权：L1-07/08/09/10、L2-14 → SpiceDB 唯一判定点 + caveat 时效 + BFF 投影
  • 第四梯队·事件链：L1-12、L3-05（audit 真库）、L3-06（seeddata 幂等）→ 审计回放
  • 第五梯队·系统：L3-02/03/04（reconcile 真库全绿、cover 门禁、roundtrip 15/15）

5 · 经验教训与后续建议

  1. Score Card 先行、覆盖率是结果不是目标 —— 49 例全部落地，CQ→测试映射零漂移（03-testing.html §4）。
  2. 测试即设计的验收：L2 逐调用点故障注入逼出 8 个真实编排缺陷（R1-R8），比覆盖率数字更有价值。
  3. 企微接入的真实进程级 E2E 未补：mock 全链已绿（HTTP API + 企微 mock 模式可直接测试），真实 Temporal + 企微沙箱需接入 official 通道后人工验收（W3/W4 证据清单就绪）。
  4. LLM 评测集沉淀：MockParser 规则为基线，LLM 钩子（LLMParser）未接线——选型决策时补评测集与直接确认率实测。
  5. 覆盖率差距的诚实交代：87.8% vs 目标 95/98%，全部为防御性错误分支；若需追平，方向是 SQL 层错误注入框架（mock pgx 连接）而非更多端到端测试。

6 · 最终结论

  • ☑ Score Card 49/49 落地；domain/config 覆盖率 100%；全仓 87.8%（门禁 85% + domain 硬门禁）；零静默 Skip / 零假绿 / 零空测试；CQ→测试映射零漂移。
  • ☑ 履约四道防线（CHECK/行锁/幂等/单事务守恒）、授权闸门（SpiceDB 唯一判定点 + caveat）、AI 安全边界（LLM 只产候选 + 人工确认 Signal）均有专项测试背书；并发守恒真库压测通过。
  • ⚠️ 剩余风险集中在：真实运行环境（企微 official 接入、Temporal 接线、CI 依赖）、覆盖率与 95% 目标的差距（防御性错误分支，见 §2 声明）、业务规则待确认项（13+1 条）。
