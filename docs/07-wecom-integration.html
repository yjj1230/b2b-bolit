2 · S2 群消息捕捉（主路径：会话内容存档）

2.1 为什么是会话存档

  • 普通自建应用没有客户群（外部群）全量消息回调（技术核验报告结论）。
  • 外部群读取的唯一官方通道 = 会话内容存档（付费、按存档账号计、需企业认证 + 员工知情同意 + 外部联系人同意）。
  • 明确不采用：微信小程序形态（双套链路）。
暂缓标注（与 §3.0 一致）：会话存档自动拉取循环（§2.2，即 GetChatData 主动拉取 → 两段解密 → 归一化 → 触发 PreOrderWorkflow）当前暂缓实现、暂缓测试（2026-08-07 决策，-tags deferred）。本节拉取架构以设计态保留；不受影响的保留项：wecom_archive_cursor 存档游标基础设施（L1-14 repo/cursor.go）、数据窗口/限流/解密/幂等防线（§2.3）、预订单确认卡片 → 正式订单人工段与 S1/S3/S4 降级路径（见 §4）。恢复条件满足（§3.0 四项）后，再由维护者将自动拉取段由灰转实并恢复测试矩阵。

3.4 确认与升级

  • 确认：应用消息 template_card（确认 / 修改 / 忽略 三按钮），点击回调验签 → Signal → PreOrderWorkflow。
  • 修改：销售改数量/产品后确认（MODIFIED → ORDER_REQUESTED）。
  • 升级：24h 未处理 → Timer 升级（ESCALATED，重新推送 + 抄送主管）；48h 仍未处理 → 人工兜底（业务链接）。
  • 出站回复：被动回复按协议用流式消息/模板卡片（text 仅欢迎语）；response_url 主动回复 1 小时有效、只能调用一次，需幂等处理（过期 → 改走应用消息）。

4 · 企微 × 流程执行结合（产品设计）

架构约束（与 02-architecture.html §2.1 一致）：企微 = 建构于底层 HTTP API 之上的特定应用转接层—— 每个企微交互最终都映射为一次 HTTP API 调用（信号 / 查询 / 预订单动作），转接层不承载任何业务逻辑。 因此「企微接入后」与「直接 HTTP」的行为等价——scripts/fullchain 与 tests/l2_e2e 独立走通全部 HTTP 流程，即为企微接入的等价验证（见 §4.4）。

4.5.8 代办与有效期（CQ-13，跨角色）

任何需要审批/确认的角色（销售、商务、仓管等）都可被代办授权：DELEGATED_TO（caveat expiry_ok 有效期）。代理人在企微中的动作与本人等价（order.delegate / prestock.delegate），但：

  • 到期前：delegate 权限生效，代办可审批/确认（卡片 assignee 映射为代办）。
  • 到期后（CQ-13 场景 D 403）：expiry_ok caveat 失败 → 服务端即时拒绝（403），代办过期不持有残留权限；Outbox 同步删除 TTL 到期元组。
  • 企微视角：到期后代办点击卡片 → X-User-Id 映射 → SpiceDB expiry_ok 校验失败 → 409/403 幂等回执「任务已过期」。不会因代办过期造成越权推进。

暂缓段角色流程（§3.0 灰标）：会话存档自动拉取（§2）与意图解析自动建单（§3.1）暂缓。因此本节不绘制「群消息 → 自动捕捉 → 自动生成预订单」自动段；只绘制「预订单确认卡片 → 正式订单」人工段（4.5.1 建单-预订单行）——该段是保留主流程，不依赖意图识别。恢复条件满足（§3.0）后，再补充自动捕捉段的销售角色流程。

  • 多备案的测试环境：用企微沙箱/测试企业 + HTTPS 隧道（如 cloudflared）模拟备案域名，CI 中仅 L1 级覆盖（L1-14 游标测试 + 回调验签单测），真实备案域名的进程级 E2E 在 Phase 3 人工验收。

10.2 真实企微部署清单（路径 ③）

  1. 前置申请（企业微信管理后台 / 开发者中心）：创建自建应用，取得 corp_id（企业 ID）、agent_id（应用 ID）、secret（应用密钥）；配置接收消息服务器：回调 URL（https://<备案域名>/wecom/callback/<tenant_id>）、token、encoding_aes_key（43 位随机 base64）；配置网页授权及 JS-SDK 可信域名（S1 侧边栏）、可信 IP（服务器出口 IP，access_token 调用白名单）。
  2. 租户配置：复制 config/wecom-tenant.example.json → wecom-tenant.json，填入上述值（archive.enabled=false 时存档段不启用——会话存档需企业认证 + 单独开通，属 §3.0 暂缓段前置）。
  3. 部署：docker compose up -d --build 后设置并重启 wecom 服务： 
    docker compose exec wecom env \
  B2B_WECOM_PROVIDER=official \
  B2B_WECOM_TENANT_CFG=/config/wecom-tenant.json \
  B2B_API_ADDR=http://api:8080 \
  # 或写入 compose 环境变量后 docker compose up -d wecom
    wecom-tenant.json 挂载进容器（compose volume）。回调链路：企微 → 回调域名（HTTPS 反向代理）→ wecom 服务 :18081 → VerifyCallback 验签 → CallbackHandler → HTTP API（B2B_API_ADDR）。

10.3 验证步骤（真实企微测试企业）

  1. curl https://<域名>/wecom/healthz → {"status":"ok","provider":"official"}（容器内 curl :18081/wecom/healthz 等价）。
  2. 企微后台「接收消息服务器」点保存 → 企微发送 URL 验证请求 → wecom 服务 VerifyURL 应答（W1 已用同算法单测覆盖；此处验证真实密钥）。
  3. W3 门禁（会话存档）：archive.enabled=false 时明确不启用（暂缓段，§3.0）；恢复条件满足后按 §2.3 配 private_keys/secret 并人工验收。
  4. W4 门禁（S1-S4 交互）：侧边栏入口（三入口分流 + 双票据签名 + OAuth exchange → 查订单）、应用消息卡片（审批点击 → 回调 → 流程推进，对照 W5 语义）、S2 确认卡片。逐项记录证据（截图 + 日志 + 时间戳）到 §9.2 表格。
  5. 出站通知：走完一笔订单（对照 scripts/fullchain 的信号序列，用 H5/接口驱动），核对审批/状态/回单异常卡片到达对应成员。
