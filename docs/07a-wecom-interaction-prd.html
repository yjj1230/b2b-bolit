0.2 交互设计原则（由 07 §1 交互红线推导）

  1. 人工确认可视化：任何「系统生成的业务结果」在 UI 上都必须以显式人工确认为终点——预订单卡片三按钮、审批卡片通过/驳回；确认前界面不得出现「正式订单」字样或状态。
  2. 轻提醒不打扰：低置信/多候选场景只发轻提醒（卡片标记「需人工核对」，不提供一键确认的强引导）。
  3. 反馈可追踪：每次操作的成功反馈都携带可追踪标识（订单号 / 消息 ID / 事件引用），出站卡片保留来源。
  4. 投影即呈现：字段级权限（剥价 / 剥金额 / 剥内部备注）在 UI 上表现为字段级显隐，而非整页拒绝——用户只看到自己有权看到的内容，且不提示「存在隐藏字段」。
  5. 幂等友好：重复点击 / 已决任务 / 过期代办在 UI 上给出明确的终态文案（「该任务已被处理」「链接已失效」），而非裸报错。

2 · S1 侧边栏 H5 交互设计（→ 07 §6.1）

2.1 入口与上下文（三入口分流）

同一套 H5 面板，由企微侧边栏入口参数决定注入的上下文与默认 Tab（服务端依据 X-WeCom-Context 重认证，不信任前端传入身份）：

入口场景注入上下文默认 TabUI 差异点
single_chat_tools单聊（与客户/同事一对一）会话对象身份（客户联系人 → 客户）查订单顶部显示当前会话客户名；「人工下单」预填客户
group_chat_tools客户群群 ID → 群绑定客户 + 归属销售（wecom_context_bindings）查订单顶部显示群名 + 绑定客户；无绑定则提示「未绑定客户群」并引导联系管理员
normal工作台/菜单直入无会话上下文查订单（需先选范围）无上下文 banner；「人工下单」客户必选

2.2 进入流程（用户感知层时序）

失败态（用户可感知）：① 签名失败 → 面板内提示「请在企微客户端内打开」+ 重试按钮（不跳转外部浏览器）；② 授权失败 → 「登录已失效，请重新打开」；③ 上下文无法解析（群未绑定） → 黄色提示条「未识别客户群，功能受限」，仅开放无上下文能力（查库存/查订单需手动选客户）。

顶部：上下文 banner（客户群名 / 客户名 / 无上下文提示）。中部：能力 Tab（按角色裁剪）：

Tab可见角色核心内容

2.4 查订单交互

列表页：默认按最近更新排序；状态筛选（进行中/已完成/已驳回）+ 关键字搜索（订单号/客户名）。每行显示：订单号、客户名、状态徽标、金额（按投影）、更新时间。点击行 → 详情页。

详情页：分区呈现——① 订单头（订单号/状态/创建时间）；② 商品明细（SKU/数量/单价×数量，按投影）；③ 履约进度（审价→备货→发货→开票→回单，垂直时间线，当前闸门高亮）；④ 凭证区（签收/回单图片列表，可上传）；⑤ 操作区（按角色与状态显示按钮：作废发货 / 上传凭证 / 跳转审批）。

字段投影的 UI 表现（原则 ④）：

角色单价/金额列内部备注UI 呈现方式
销售（本人订单）/ 商务 / 董事长 / 管理员✅ 显示✅ 显示正常渲染
仓管❌ 剥价❌列头与单元格整体不渲染（不留空列、不显示「—」占位，避免暗示存在隐藏字段）
客户联系人❌ 剥金额❌ 剥内部备注物流视图仅渲染：发货进度、承运信息、签收凭证、回单状态

三态：加载中 → 骨架屏/居中 spinner；空 → 「暂无订单」（附「新建订单」或「联系销售」CTA）；失败 → 错误页 + 重试（见 §6.2 文案）。

2.5 查库存交互

  • 仓库选择（下拉，默认上下文客户对应仓）→ SKU 列表：型号、名称、可承诺量（高亮）、在途/占用。
  • 搜索：型号模糊匹配（标准型号映射表，08-external-integration §1.4）。
  • 「库存不足」的 SKU 置灰 + 标记「可下单·排期」，点击提示「可提交预订单，到货后履约」——不阻止下单（07 §3.3 库存校验规则）。

2.6 人工下单表单交互

字段与校验（→ 07 §4.5.1 建单-人工）：

字段控件必填校验规则错误提示（示例）
客户下拉搜索是（normal 入口必选；群/单聊入口预填可改）必须为当前角色可服务的客户「无权为该客户下单」
产品（SKU）搜索 + 多选是≥1 项；标准型号匹配「请选择至少一个产品」

提交反馈：点击「提交订单」→ 按钮 loading「提交中…」→ 成功：绿色 toast「订单已创建 ORD-2026…」+ 按钮变「查看订单」跳详情；重复提交（409 幂等）→ 黄色 toast「订单已提交，请勿重复操作」（07 §4.2 幂等语义的 UI 化）。

2.7 发货操作交互（→ 07 §4.5.3 仓管）

  • 发货数量录入：详情页「发货」→ 数量输入（部分/整批），预填可发量；超发（超出分配量）→ 红色校验「超出可发数量 N 件」并禁止提交（07 CQ-07 守恒的 UI 化）。
  • 作废发货：30 分钟窗口内显示「作废」按钮 + 剩余时间倒计时（mm:ss）；窗口过期后按钮消失/置灰（07 §4.5.1 场景 F；超窗后端 403 → UI 提示「作废窗口已过」）。作废需二次确认弹窗（防误触，§6.4）。

2.8 凭证上传交互（→ 07 §4.5 场景 C/D）

  • 入口：详情页「凭证区」→ 选择图片（≤9 张）→ 逐张上传进度条 → 成功后凭证列表追加缩略图 + 「已登记」徽标。
  • 凭证只追加（CQ-15）：UI 不提供删除/覆盖，文案注明「凭证仅可追加，历史版本可回放」。
  • 重复提交同版本（409）→ toast「该凭证已登记」。

3 · S2 预订单确认卡片交互设计（→ 07 §4.1/§4.2，人工段）

3.1 卡片结构规范（template_card）

区域内容规则
标题「预订单待确认」固定前缀，一眼可辨为待办而非通知
摘要（来源）群名 · 发言人 · 时间人工段来源 = 销售/协助者录入或候选生成；注明「需人工核对」当候选置信度低
主体（候选信息）SKU / 数量 / 单价 / 合计逐行展示候选；价格展示给归属销售（确认卡片只发归属销售）
辅助行客户 / 仓库 / 幂等提示「仅可确认一次」弱提示（防重复点击焦虑）
按钮区确认 / 修改 / 忽略（横排主按钮）确认=主按钮（实心），修改=次按钮（描边），忽略=文字按钮（弱化）

3.2 三按钮交互流

按钮点击后 UI 反馈成功态异常态
确认按钮 loading「确认中…」，卡片防重复点击卡片更新为「✅ 已生成正式订单 ORD-2026-…」+ 订单链接（点击跳 S1 详情）非待确认态（409）→ 卡片刷新为「该预订单已被处理」；网络失败 → toast「网络异常，请重试」
修改卡片切换为编辑态：候选行变可编辑（数量/产品），底部「保存并确认 / 取消」保存 → 同确认成功态（候选已更新）校验失败（数量超限）→ 行内红色错误；非待确认态 → 「已被处理」
忽略二次确认弹层「确认忽略该预订单？此操作不可撤销」[取消][确认忽略]卡片更新为「已忽略」终态（置灰，无按钮）非待确认态 → 「已被处理」
关键原则：三按钮任何路径，确认前 UI 不出现「正式订单」；成功反馈必须携带订单号（原则 ③ 可追踪）。「修改」无独立后端信号（= confirm + confirmed:false，07 §4.2）——UI 层仍以独立交互呈现，后端语义不变。

4.3 各卡片特殊交互

  • 催办卡：「前往处理」→ 打开原任务卡片（同 EventKey）；原卡片仍显示在消息列表中，置顶提示「已催办」。
  • 状态卡（只读）：无决策按钮，仅「查看详情」→ 跳 S1 H5 详情页（跳转需重新走 OAuth 静默授权，见 §2.2）；不做敏感操作（07 §4.1 出站行）。
  • 回单异常卡：「处理异常」→ 进入例外审核（财务/销售 assignee）；卡片展示回单超期天数（「已超期 3 天」红色徽标）。
  • 董事长大单卡：主体区额外展示客户等级（C/D）徽标与金额大字（决策需全字段，07 §4.5.5）。

6.4 安全与防误触

  • 二次确认：不可逆操作必须二次确认——预订单「忽略」（§3.2）、发货「作废」（§2.7）；弹层文案含后果说明。
  • 防重复提交：所有提交按钮点击后立即 loading + 置灰，客户端先防重，后端幂等兜底（409 文案化）。
  • 审计可见性：敏感操作成功反馈附「操作已记录」（事件链留痕的 UI 暗示，07 §8 审计要求）；原始聊天/会话内容不出现在任何 UI（业务库零原始文本，07 §8 合规）。
  • 暂缓段不出现在 UI：意图识别相关文案（「AI 识别」「自动生成」）禁止出现在当前版本任何界面——当前候选来源仅「人工录入/协助」，界面文案用「候选信息」而非「AI 识别结果」。
