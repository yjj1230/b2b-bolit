外部依赖接入层
Integration Layer

文档定位：架构文档（architecture），与 07-wecom-integration.html 同为「接入类专项架构」。独立成章的原因：外部依赖是横切关注点——新增数据源、切换配置源时本层独立演进，不污染主架构文档（02）与开发计划（04）。编号延续文档家族 07 → 08。本文档回答「系统如何组织对外部世界的接入」（组件边界、接口契约、依赖方向、演进路径）；落地实施步骤见 §6 附录（轻量），详细里程碑见 04-development-plan.html。

0 · 结论摘要（TL;DR）

  • 系统对外部有两类依赖：① 动态数据源（企微会话存档/出站/回调，未来飞书多维表格）；② 业务配置性数据（审批催办、回单超期、修改分类、自动审批阈值）。
  • 新增独立层 internal/integration/ 统一承接两者，领域层 internal/domain 保持纯 Go 零依赖（只依赖接口/纯函数，不感知接入实现）。
  • 基线实现 StaticConfigProvider：值 = 历史硬编码默认值（24h/48h/5d），行为完全不变（决策点 2026-08：Static 起步）。
  • 已接线：internal/workflows/client.go 的 Timer 硬编码常量（24h/48h/5d/24h）改为从接入层策略读取。
  • 明确不归入本层：数据迁移源（legacy_* 只读归档 → 独立 internal/migration/）、SpiceDB/Temporal/PG 接入（已相对独立）。
  • 业务依赖数据（主数据类）与「配置性数据」边界明确：前者是业务事实、随业务运营变化、需权威来源与维护人，不归 BusinessConfigProvider 策略接口。审计清单（§1.4）：客户档案（等级/归属销售）、用户与企微 ID 目录、产品/SKU、仓库、库存均已落库但由 seed 种子供给、无权威维护源；审批人分配（5 处硬编码）、SKU 标准型号映射、客户等级价格表、供方分流路由为纯硬编码/部分配置化；企微上下文绑定与多备案配置已落库/已配置化。

1.3 未来外部数据源（迁移布局揭示）

02-architecture.html §8 揭示原系统（飞书三方审批）为 JSONL 非关系型追加式存储 + 飞书多维表格（bitable_flow_records / customer_bitable_sync）。用户决策：

  • 迁移源（legacy_* 只读归档）→ 独立 internal/migration/，不归入接入层（一次性工程 ≠ 运行时依赖）；
  • 飞书多维表格若未来作为动态业务数据源/配置源 → 实现 integration.DynamicSource 注册即可（§4），业务代码零改动。

1.4 业务依赖数据（主数据类）：现状、归属与演进 （与 §1.2 配置性数据区分）

边界：§1.2 的「配置性数据」是策略参数（阈值/规则，如 24h 催办、5 天回单超期、修改分类 A-E），归 BusinessConfigProvider；本节「业务依赖数据」是业务事实/主数据（客户档案、价格、映射、路由、组织与权限基础），随业务运营变化，需要权威来源与维护人，不归 BusinessConfigProvider——应走 DynamicSource 或独立主数据接口（演进见 §5.3）。下表为 2026-08 全量审计（代码 + migrations 核验），「有一批」的完整口径。

2 · 设计目标与非目标

Goals

  1. 将对外部系统的接入收敛到 internal/integration/ 一层；
  2. 将业务配置性数据从硬编码抽离为可动态加载的配置（接口契约 + 可替换 Provider）；
  3. 保持 internal/domain（纯 Go 零依赖）解耦——领域层只依赖接口/纯函数。

Non-Goals

  • 不重构已有 SpiceDB / Temporal / PG 接入（已相对独立）；
  • 不在本阶段实施数据迁移（baseline 明确不实施，仅预留）；
  • 不改变 internal/wecom/ 内部解密/验签实现，仅将其归位为接入层的动态数据源实现；
  • 不做企微合规降级的运行时热切换（部署期配置决定）。

依赖规则（与 01 §2.1 领域层纯度约束一致）：

  • integration → domain：复用其纯类型/函数（domain.Modification / ClassifyModification），domain 不感知 integration；
  • workflows / api → integration：只依赖接口契约，不感知 Static/DB/外部源差异；
  • 物理依赖必须是 integration 依赖 domain，禁止反向。

4 · 接口契约

4.1 业务配置数据（internal/integration/config.go）

// 审批催办：24h 提醒 / 48h 升级（01 §2.1）
type ApprovalPolicy interface {
    RemindAfter() time.Duration
    EscalateAfter() time.Duration
}

// 无回单超期：5 天自动进例外（01 §2.5）
type ReceiptPolicy interface {
    ReceiptExceptionAfter() time.Duration
}

// 修改分类规则 A/B/C/D/E（01 §2.2，配置数据；委托 domain 纯函数）
type ModificationRulePolicy interface {
    Classify(m domain.Modification) domain.ModificationClass
    TargetState(class domain.ModificationClass) (string, error)
}

// 自动审批阈值（02 §8.2；基线全人工闸门，恒 false）
type AutoApprovePolicy interface {
    AutoApprove(stageCode, grade string, amountCents int64) bool
}

// 预订单确认升级：24h（01 §2.6）
type PreOrderPolicy interface {
    PreOrderEscalateAfter() time.Duration
}

// 聚合契约：业务层只依赖这一个接口
type BusinessConfigProvider interface {
    ApprovalPolicy
    ReceiptPolicy
    ModificationRulePolicy
    AutoApprovePolicy
    PreOrderPolicy
}

4.2 动态数据源（internal/integration/source.go）

// 动态数据源标识：外部系统实时/近实时数据接入点
type DynamicSource interface {
    SourceName() string // "wecom" / "feishu_bitable" ...
}

// 注册表：按名称取用（cmd/* main 注入，无全局可变状态）
type Registry struct{ /* ... */ }
func NewRegistry() *Registry
func (r *Registry) Register(s DynamicSource)
func (r *Registry) Get(name string) DynamicSource

现有实现：internal/wecom.Gateway（企微会话存档拉取 / 出站卡片 / 回调验签）即 DynamicSource 的第一个实现，归位说明见 §5.1。

5 · 实施落地

5.1 企微归位（接口已就绪，物理迁移留后续）

internal/wecom/ 已具备完整 provider 隔离（Gateway 聚合接口 + NewGateway(cfg) 工厂 + TenantConfig 多备案），本轮不移动代码物理位置（避免破坏 cmd/wecom 与 internal/api 依赖链），通过接口 + 本文档建立统一接入层心智模型。目标态：

  • cmd/wecom / cmd/api 只依赖 integration.Registry + wecom.Gateway（作为 DynamicSource 注册）；
  • 业务逻辑（意图识别 intent.go、消息幂等、预订单触发）留在业务侧，不归入接入层。

5.2 已接线清单（本轮交付）

5.3 演进路径（配置源 Static → 可替换）

  1. 基线（当前）：StaticConfigProvider，值 = 历史硬编码，行为不变；
  2. DB 配置源：新增 DBConfigProvider 实现 BusinessConfigProvider（读 business_configs 表，租户维度热更新）——接口已就绪，业务代码零改动；
  3. 外部配置源：飞书多维表格实现 BusinessConfigProvider 或 DynamicSource 注册。

业务依赖数据（§1.4）同构演进：审批人分配（§1.4 #8）为最短路径项——可随 DBConfigProvider 一并建 approval_routing 表（tenant × stage → assignee），或独立主数据接口；其余主数据（客户/用户/产品/仓库/库存/价格表/SKU 映射）走 DynamicSource 或独立主数据接口，业务代码零改动。

7 · 决策记录（ADR）

决策选择理由
配置介质Static 默认值起步接口契约先落地，StaticProvider 用当前硬编码值，行为完全不变；后续可无缝换 DB/外部源，零风险
legacy 归档归属独立 internal/migration/迁移是一次性工程，与持续运行的接入层职责不同
企微降级开关部署期配置决定现有 WeComProvider 机制已可表达（mock/official/thirdparty），无需运行时热切换
接入层文档定位架构文档，独立成章（08）外部依赖是横切关注点，独立演进；与 07 企微文档同属「接入类专项架构」
本轮迁移范围不物理移动 wecom 代码避免破坏 cmd/wecom 与 api 依赖链；接口 + 文档先行，物理迁移独立迭代
业务依赖数据归属不归 BusinessConfigProvider，单列 §1.4 审计主数据是业务事实（需权威源/维护人），与策略参数（阈值/规则）性质不同；先全量审计暴露缺口（审批人分配 5 处硬编码为最高优先级），演进走 DynamicSource / 独立主数据接口（§5.3）
