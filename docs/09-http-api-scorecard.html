3 · 覆盖率 / 风险性 / 影响面评估

3.1 业务覆盖率（HTTP 视角）

  • 场景级：15/15 全绿——21 个 E2E 用例覆盖全部 13 个端点与全部业务分支。
  • 行覆盖率：87.8%（make cover，门禁 85% + domain 100% 硬门禁）——差距全部为防御性错误分支（repo pgx scan error、workflows 闸门防御返回），非业务路径缺失；正确性核心 domain 100%。
  • 可运行证据：scripts/fullchain 22 步 demo（订单全链 INV_CLOSED + 26 事件 + 凭证 + 预订单 + 待办 + 出站卡片）连续 2× exit=0。

3.2 风险性

  • 高影响面：订单创建/信号/投影/凭证/预订单——全部有 E2E + 权限拒绝用例（AuthzDenied/403/401），跨角色投影本轮补 contact 剥离（07 §4.1 偏差已修）。
  • 残余风险：① TestSuite 信号递送竞态（环境层，300ms 间隔规避，tests/README 记录）；② 真实企微通道（official）未做端到端（W3/W4 真实环境门禁，Phase 3 人工验收——诚实声明不冒充）；③ Outbox 投影器阶段二（本地 StaticChecker 判定）。

3.3 影响面

  • 本轮新增端点（jsapi-config / auth/exchange）仅服务 S1 H5，不影响既有 11 个业务端点；withContext 的 X-WeCom-Context 校验仅在携带该头时生效（既有调用零影响）。
  • ProjectOrder contact 剥离变更影响面：仅 CONTACT 角色订单视图（此前错误地暴露金额），已由 W6 + api 单测 + 既有 Projection 用例验证。

4 · 设计贯通结论（任务 1）

  1. 端点 ↔ 设计：13 端点 ↔ 02 §2.1 设计清单 + CQ-01..15 全映射（05 roundtrip 15 CQ 代码图锚点抽查存活）；07 §6.1 S1 服务端能力本轮补齐（jsapi 双签名/OAuth 交换/context 校验）。
  2. 流程贯通：HTTP 入口 → Starter（LocalRunner/Temporal 5 实现）→ OrderWorkflow / PreOrderWorkflow 调用链完整（code-review-graph 图证）；E2E 21 用例 + demo 全绿。
  3. 本轮修复：① ProjectOrder 对 CONTACT 不剥价（07 §4.1 设计偏差，W6 暴露并修复）；② 预订单 modified 分支派生状态硬编码（上轮 W5 暴露并修复）。
  4. 结论：HTTP API 视角订单履约全流程完全符合设计、全线贯通；剩余缺口仅为覆盖率数值 87.8%（防御分支性质）与真实企微环境人工验收（Phase 3）。
