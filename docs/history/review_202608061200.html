实施基线前的阻断项

本记录归档对 docs/ 文档家族的静态交叉审查意见。审查以 spec/meta.md 为任务入口，并核对当前 spec/ 输入、文档之间的派生关系以及已有 pilot_app 的复盘经验。

8 × P1实现或验收阻断项

01 · 审查结论

当前文档还不能作为实现基线。 主要问题集中在授权 schema、跨租户隔离、业务状态覆盖、数量守恒的数据模型和企微验收门禁。HTML 发布页面与 Markdown 内容基本同步，因此这些问题同样存在于发布页面。

02 · 主要发现

P1 SpiceDB schema 无法直接加载

文档使用了 pilot_app 复盘中已经修正的点号图遍历语法，如 tenant.ops、customer.owner；同时 order.ship 引用了未声明的 warehouse 关系。按 M1 计划生成并应用 schema.zed 时会直接失败。

依据：01-core-graph.md:230、01-core-graph.md:258；pilot_app 已使用 bank->admin，见 pilot_app/schema.zed:2。

建议：先固定 SpiceDB 版本并让 schema 通过实际编译；补齐订单到仓库的关系，再为每种遍历和 caveat 增加集成测试。

P1 多租户隔离没有落到数据库和 Workflow ID

资源表的 FK 没有限制关联对象属于同一租户；订单、发货、开票和预订单的幂等键又使用全局唯一约束，Temporal Workflow ID 也没有 tenant 前缀。只依赖 SpiceDB 无法弥补数据库层的跨租户错误关联或幂等冲突。

依据：02-architecture.md:145、02-architecture.md:194；授权 schema 见 01-core-graph.md:236。

建议：使用复合 FK/唯一键（至少包含 tenant_id），Workflow ID 显式包含 tenant，增加跨租户读写、幂等和配置路由测试。

P1 订单修改 A/B/C/D/E 分支没有进入文档闭环

源规格要求修改订单按 A/B/C/D/E 分类进入不同的回审价、重生成合同或静默修改路径。当前 ORD 状态图只有通过、退回和拒绝，没有修改分类、状态迁移、事件字段、数据模型或 Score Card 用例。

依据：验证项目设计.html:258、验证项目设计.html:461；当前状态图见 01-core-graph.md:365。

建议：将修改分类定义为 ORD 的显式事件/状态分支，补充修改记录表、权限边界、回退规则、Temporal Signal 及专项测试。

P1 开票是否必须先发货存在直接冲突

源规格写明“订单存在即可开票”，而当前状态机把“未发货就开票”列为非法，并让 INV 从已发货状态开始。这会改变业务流程和验收结果，不能通过实现细节自行决定。

依据：验证项目设计.html:223；当前状态机见 01-core-graph.md:433，架构约束见 02-architecture.md:183。

建议：业务方先确认“订单可申请开票”与“发票金额/数量只能按有效发货核验”两者的关系，再统一状态图、SQL 守恒规则和 L2 用例。

P1 预订单事件无法写入当前事件表

ontology 允许事件挂在 order_id 或 pre_order_id 上，但数据库设计只有 order_events.order_id FK。消息捕捉、意图识别和人工确认发生在正式订单创建前，无法完整进入 CQ-12 的事件链。

依据：01-core-graph.md:211、01-core-graph.md:331、02-architecture.md:157。

建议：采用独立的 polymorphic aggregate key，或拆分 pre_order_events 与 order_events；明确正式订单派生前后的审计回放规则。

P1 开票数量守恒缺少可计算的数据模型

约束要求按数量校验，但 invoice_items 只有 shipment_id 和 amount_cents，没有开票数量、订单明细或产品维度。它无法可靠表达部分开票、多次开票或按多个订单合并开票。

依据：01-core-graph.md:106、02-architecture.md:152、02-architecture.md:227。

建议：增加订单明细/发货明细维度的开票数量分配和唯一性约束；如果实际只验证金额守恒，应同步重写 CQ-09，不再使用“开票量”表述。

P1 企微核心验收没有纳入主测试门禁

回调验签、多租户配置隔离被放在独立补充用例中，真实 S1/S2/S3/S4 E2E 又明确排除自动化门禁；但 M8 只要求 44 个主用例和 L3 全绿。这样可以在没有验证企微核心支柱的情况下完成最终结论。

依据：07-wecom-integration.md:208、07-wecom-integration.md:219、04-development-plan.md:37；源规格验收要求见 验证项目设计.html:646。

建议：把补充用例纳入正式验收矩阵，至少设置 S1/S2/S3/S4 的真实环境或明确的有证据 Fake 门禁，并单独记录真实 E2E 未覆盖项。

P1 原始聊天留存策略前后不一致

源规格要求原始消息不落业务库；当前事件定义却把 raw 作为事件参数，企微文档还要求原始聊天访问审计，但没有明确脱敏、引用、删除和留存期限边界。若事件链 append-only，原始消息可能被永久保留。

依据：验证项目设计.html:583；当前事件定义见 01-core-graph.md:87，审计要求见 07-wecom-integration.md:190。

建议：事件只保存意图特征和必要引用；原始内容进入独立、加密、可过期的存档区，并补充访问审计、清理任务和合规验收证据。

03 · 低优先级文档问题

部分章节引用指向错误：架构文档将存档拉取指向 07 §3，实际内容位于 07 §2；测试文档对游标和 Timer 的引用也有类似偏移。见 02-architecture.md:129 和 03-testing.md:64。这不改变设计语义，但会增加实施时的查找成本。

04 · 审查边界

  • 审查对象：docs/ Markdown 与对应 HTML，以及 spec/meta.md、当前 spec/ 输入和 pilot_app 复盘资料。
  • 审查方式：静态交叉核对、引用核对和结构一致性检查。
  • 本记录生成时未修改业务设计文档，当前仓库也尚未包含可执行的 Go 实现，因此没有执行应用测试。

05 · 建议的解除顺序

  1. 先修正并实际编译 SpiceDB schema，明确租户隔离模型。
  2. 由业务方确认开票独立性和订单修改 A/B/C/D/E 规则。
  3. 根据确认结果重画状态图、补齐事件和数量守恒数据模型。
  4. 将企微合规、真实交互和多租户隔离纳入最终验收门禁。
