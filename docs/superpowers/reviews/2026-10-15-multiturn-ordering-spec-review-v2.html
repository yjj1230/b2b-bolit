二、v2 新引入的问题

阻断级 必须解决后才能进 plan

N-1 草稿状态枚举漏了 CONFLICT——自相矛盾

§4.3 定义的 pre_order_drafts.status 枚举是：

status   // CURRENT、SUPERSEDED、CONFIRMED、REJECTED

但 §7 和 §12 都要求写入一个 status=CONFLICT 的版本：

§7  ：…同时写入一个 status=CONFLICT 的不可确认版本记录本次冲突
§12 ：字段冲突：创建一个 status=CONFLICT 的不可确认版本…

枚举里没有 CONFLICT，但正文要求写入它。这是文档内部直接打架，实现者按 §4.3 建枚举就会漏掉这个状态，按 §7 写又会越出枚举。

修法：§4.3 枚举补为 CURRENT、SUPERSEDED、CONFIRMED、REJECTED、CONFLICT，并说明 CONFLICT 版本对唯一"CURRENT"约束不产生干扰（因为它不在部分唯一索引的谓词内）。

N-2 CONFLICT 版本编号与"current_draft_version 不前进"冲突——真设计缺陷

这是 v2 最严重的问题，而且是为了解决旧问题而新引入的。把它拆开看：

§7 规定冲突时"写入一个不可确认版本，current_draft_version 不前进"。§10 的事务又规定新版本编号方式是：

读取 current_draft_version
…
INSERT pre_order_drafts(version + 1)
UPDATE order_conversations(current_draft_version, last_message_at)

两者相乘，得到一条自相矛盾的路径：

当前 current_draft_version = 3
→ 消息"D90"判为冲突，写入一条版本记录
→ current_draft_version 保持 3，但该条冲突记录占用了哪个版本号？

若是 4：
  下一条合法消息（"改成D90"）按 §10 用 version+1 = 4
  → 主键 (tenant_id, pre_order_id, 4) 与冲突版本相撞 ❌

注意现有实现 CreatePreOrderDraftVersion 用的是 MAX(draft_version)+1（不会撞），但 §10 白纸黑字写的是"读取 current_draft_version 后 version+1"——两个版本的编号口径不一致，实现者照 §10 写就会踩主键冲突。

修法（三选一，spec 必须明确）：
  • 方案 a：编号统一改为 MAX(draft_version)+1（"版本槽"），current_draft_version 只指向"最后一个可确认版本"，两个指针分离；
  • 方案 b：冲突版本不占用 pre_order_drafts 的版本序列，改存独立 draft_conflicts 表；
  • 方案 c：冲突不落版本，只写 pre_order_events 审计 + 会话转 MANUAL_REQUIRED（最简，但丢失"冲突内容"的版本化留痕）。

重要级 会变成实现期返工点

N-3 PRE_PENDING_CONFIRM 缺 → PRE_EXPIRED 边（B-3 的收尾）

§8.2 说 expires_at 到期后"进入 PRE_EXPIRED"，但 §8.1 的边表里 PRE_COLLECTING / PRE_AMBIGUOUS / PRE_ESCALATED 都有 → PRE_EXPIRED，唯独 PRE_PENDING_CONFIRM 没有。而 §13.6 又要求"加入 PRE_COLLECTING、PRE_EXPIRED 和完整入出边"。

后果：一个已推卡、销售迟迟不点的会话（最典型的过期场景），走 PENDING_CONFIRM → EXPIRED 会被 FSM 拒绝，会话无法过期。

修法：§8.1 的 PRE_PENDING_CONFIRM 出边补 → PRE_EXPIRED。

N-4 §10 事务序列漏更新 escalate_at（W-2 的收尾）

§8.2 明确规则："收到有效补充后重新计算 escalate_at，不延长 expires_at"。但 §10 的事务只写了：

UPDATE order_conversations(current_draft_version, last_message_at)

没有 escalate_at。实现者照事务序列写，升级 Timer 不会因新消息而顺延——24h 提醒会在用户仍在积极补充时错误触发。

修法：§10 改为 UPDATE order_conversations(current_draft_version, last_message_at, escalate_at)，并注明 escalate_at = now() + 24h、expires_at 不变。

N-5 §5 已确认会话三分支的"明确"判定主体未定义——自设门禁过不了

§5 规定已确认会话收到新消息时：

- 消息明确表示新订单 → 创建新会话
- 消息明确引用已确认订单 → 进入修改/售后入口
- 两者都不明确 → 创建人工关联待办

问题：谁判"明确"？用什么判？ 这三种分叉是会话归属判定，本身就是 §3.2 划红线的领域。若交给 LLM 判"是否新订单"，就触碰了"不让 LLM 自主决定会话归属"的边界；若用规则判，spec 又没给规则。

更关键的是：§14 结尾你自己立了门禁——"Spec 只有在以上 18 条均能由固定输入得到固定结果后，才允许进入实现计划阶段"。而 TC-13 的 Then 正是这三个分支，判定标准缺失 → TC-13 无法由固定输入得到固定结果 → 自设的门禁自己过不了。

修法：把三分支判定显式绑定到 §5 前四条确定性规则上（引用/订单号/唯一会话），并补齐兜底规则：
  • 能命中前四条确定性规则 → 按规则归属；
  • 否则一律 MANUAL_REQUIRED + 人工待办（不做"新订单/修改"的自动分叉）。
这样 TC-13 就有确定结果了。

N-6 pre_orders 唯一约束的处置未定义（B-1 的收尾）

§13.2 只说"调整 pre_orders 关系，使一个会话拥有一个主预订单，并保留根消息作为审计字段"，但没说现有的这条约束怎么办：

UNIQUE (tenant_id, group_id, msg_id)   -- migrations/003_preorder.sql L18

消息幂等若已迁移到 inbound_messages，这条约束是保留、放宽还是删除？保留的话，"会话由非消息事件创建"（如相似度候选被选中后建会话）时没有根消息，约束会误伤；删除的话，要说明消息幂等的防线已完全由 inbound_messages 承接。

修法：§13.2 明确该约束的去留，并给出迁移 010 的字段级改动清单。

N-7 pre_order_drafts 字段级迁移清单不全

把 v2 §4.3 的字段列表与已建成的 migration 009 逐项对齐，差异远不止 §13.3 提的三项：

变更类型字段§13 是否提及
新增snapshot_json、patch_json（diff 已有）✅ 提及
改名+改类型source_msg_id(TEXT) → source_message_ids(多值)✗ 未提
新增created_by✗ 未提
去向未说明customer_basis / product_basis / contract_basis / price_basis（009 用于主数据匹配追溯）✗ 未提

其中 basis 系列的消失最需要警惕：§7 合并器第 3 步要"应用主数据匹配结果"，§15 门禁要"可追溯到…"。这些"匹配依据"在 009 里是专门存字段，v2 §4.3 把它们删了却没交代转移去向——可能是无意的审计能力回退。

修法：§13.3 扩为完整的字段级 diff 清单，明确 basis 系列是保留、搬表还是明确放弃。

建议级 打磨项

  • N-8：PRE_EXPIRED 需纳入 domain.IsTerminal()（现只认 PRE_IGNORED/ORD_REJECTED/INV_CLOSED）；§13.6 建议点名 IsTerminal，否则"终态"语义与 FSM 不同步。
  • N-9：会话与主预订单的创建事务边界未定义。§10 只管"合并"，不管"创建"。会话创建与主预订单创建是否同事务？谁先谁后？§4.2 的 pre_order_id 是否加 FK 到 pre_orders(tenant_id, id)？未说明会导致孤儿会话。
  • N-10：群会话数超上限（§5 默认 10）时，已落库的 inbound_messages 该是什么 parse_status？现有枚举 RECEIVED/PARSED/FAILED/IGNORED 覆盖不了"因上限被挂起"，会留下永不回填 session_id 的消息。
  • N-11：验收矩阵补 2 条用例——① CONFLICT 版本的编号与唯一 CURRENT 约束（验 N-2）；② 有效补充后 escalate_at 顺延、expires_at 不变（验 §8.2 与 N-4）。v2 新增的这两条承重规则目前无用例覆盖。
  • N-12：§4.3 status 含 CONFIRMED，确认后该版本离开 CURRENT；若此时再触发"读取当前 CURRENT 版本"（§9）会取不到。需说明确认流程的读取时序（先读后改），或保留一个 CONFIRMED 作为可读终态。
