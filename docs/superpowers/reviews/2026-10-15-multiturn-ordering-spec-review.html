一、承重事实核对（点评的地基）

先核了 spec「当前代码的适配点」一节的自述，再核代码本身。四处的差异是后文所有问题的根，先摆出来：

#spec 的陈述代码真实状态判定
1 "同一订单的多轮消息可以归并到同一份预订单草稿" pre_orders 的幂等约束是 UNIQUE(tenant_id, group_id, msg_id)，CreatePreOrder 是"一消息 → 一预订单" 硬冲突
2 "LLM 不应每轮重新生成完整订单，而应返回本轮字段变化 changes:{...}" IntentParser.Parse 返回 []byte，LLMParser.Parse 直接 Decode(&cands) 成 []IntentCandidate——是候选数组不是补丁 契约冲突
3 "新消息补充 → 新 DraftVersion，回 PRE_COLLECTING" PreOrderFSM 里没有 PRE_COLLECTING；PRE_PENDING_CONFIRM 的出边只有 Confirmed/Modified/Ignored/Escalated，无回退边 FSM 不支持
4 "确认卡片必须绑定草稿版本；旧卡片不能确认新版本" ValidatePreOrderDraft 已实现 draft_version_conflict；migration 009 的 pre_order_drafts 不可变版本表已建 准确

二、架构层面：这份设计的成功之处

1. "不确定性隔离带"划得非常干净

spec 把系统切成三段——LLM 只产候选（不可信）→ 确定性策略裁决（可信）→ 人工确认（最终权威）。这是 AI 落地企业交易类系统的正解，也是这份设计最值钱的部分。尤其"deriveOrder 只能读取已确认草稿中的规范化字段，不得重新依赖模型猜测"这一条，把模型幻觉的影响彻底封在派生边界之外。

2. 不可变草稿版本 + 卡片版本闸门

"每轮合并产生不可变 DraftVersion、确认必须携带版本号、版本不匹配则拒绝"——这是解决"用户在多轮对话中点了旧卡片"这类经典并发问题的标准解法。migration 009 已经把 pre_order_drafts 的 UNIQUE(tenant_id, pre_order_id, draft_version) 和"仅一个 CURRENT"的部分唯一索引落地了，底座在。

3. 字段优先级是显式的

"人工修改 > 用户明确补充 > 已确认草稿 > 模型推断"——把冲突解决规则写成了有序链，而不是散落在 if-else 里。这条链本身就是最好的测试用例来源（见第四节）。

4. 会话选择优先级是"确定性序列"

1) 显式"继续补充" → 2) 引用消息 → 3) 消息含订单号 → 4) 群内唯一未过期会话 → 5) 相似度候选。前 4 条全是确定性的，第五条明确降级为"候选匹配 + 无法确定则 PRE_AMBIGUOUS"。这个"能确定就确定、不能确定就交给人工"的排序是正确的。

三、问题清单（分三级）

阻断级 必须在写 plan 前解决

B-1 归并载体缺失：pre_orders 的幂等粒度与目标矛盾

spec 引入了 OrderConversation 概念，但没有说明它将如何改变 pre_orders 的幂等键语义。现状：

-- migrations/003_preorder.sql
UNIQUE (tenant_id, group_id, msg_id)   -- 一消息一预订单

而 spec 要的是"产品 / 数量 / 地址分三轮 → 同一个预订单"。实现路径只有两条，spec 必须二选一并写明：

  • 方案 A（推荐）：新增 order_conversations 表，幂等键降为 (tenant_id, group_id, msg_id) 的事件级去重，预订单改由 session_id 派生。这是对比 003 的破坏性变更，需要新 migration + 回填脚本。
  • 方案 B：保留 msg 级 ID，靠 OrderConversation.session_id 做外部聚合，多轮 = 多条 pre_orders + 一个 conversation。但这与 spec 中"归并为同一预订单草稿"的表述不符，且会让 PRE_* 状态机含义失真。

为什么是阻断级：这个选择决定了 CreatePreOrder、wecomPreKey、pre_order_events、状态机归属全部四条主链的改法。选错方向，plan 里前 3 个 task 都要重写。

B-2 DraftVersion 里到底存"累积态"还是"增量"——承重语义未定义

spec 的例子是累积态：

Draft v1：product = C68
Draft v2：product = C68, quantity = 100
Draft v3：product = C68, quantity = 100, address = 上海

但代码里 CreatePreOrderDraftVersion 写入的 Candidate 字段，是本轮 parser 的输出（见 agent_default.go 第 55–59 行，直接传 candidates，即本轮 Parse 结果）。也就是说 v2 里并不会自动包含 v1 的 C68。

结论：spec 描述的"合并"这个动作，在代码里根本不存在——目前没有"读取当前草稿 + 应用补丁 + 写回累积态"的合并器。internal/agentorder/ 只有 policy.go（策略），没有 merger.go。

需要明确：① 每版 draft.candidate 存累积完整态，还是只存增量 diff（累积态可由回放重建）？② 合并器归谁（新包 internal/agentorder/merger.go？）？③ 合并器是"纯函数"还是"带 IO"——若纯，就能表驱动测；这是可测试性的关键。

B-3 状态机图与 PreOrderFSM 事实矛盾，spec 会给实现者画错图

spec §状态机调整 画的：

PRE_PENDING_CONFIRM
    ├─ 新消息补充 → 新 DraftVersion，回 PRE_COLLECTING   ← 这条边不存在

实际 internal/domain/preorder.go 里 PRE_PENDING_CONFIRM 的出边是：

StatePrePendingConfirm: {
    StatePreConfirmed, StatePreModified, StatePreIgnored, StatePreEscalated,
},

spec 自己也意识到问题，写了"如果暂时不扩展状态枚举，现有 PRE_INTENT_PARSING 可以临时承载 PRE_COLLECTING 语义"——但这个权宜之计不成立：PRE_INTENT_PARSING 的出边只有 PENDING_CONFIRM / AMBIGUOUS / IGNORED，既没有自环（继续收集），也没有从 PENDING_CONFIRM 回来的边。所以无论用哪个状态，"补充消息后回收集态"这条迁移都会被 domain.PreOrderFSM.Validate 直接拒绝。

修法：spec 必须同时给出 PreOrderFSM 的完整边表变更（新增 PRE_COLLECTING 及其出入边、以及 PENDING_CONFIRM → COLLECTING 的回退边），而不是只画一张目标图。

B-4 "旧卡片被拒绝"在 Temporal 语义下会终止 workflow，spec 未定义其存活

这是最隐蔽也最危险的一条。当前确认路径：

// internal/workflows/preorder.go  case "confirm":
if err := act(ctx, ActValidatePreDraft, ...).Get(ctx, nil); err != nil {
    return err        // ← Activity error 直接让 workflow 返回失败
}

ValidatePreOrderDraft 在版本冲突时返回 draft_version_conflict 错误。在 Temporal 里，这个 error 冒泡到 workflow 顶层 = workflow 执行失败终止，而不是"提示用户刷新卡片后继续等待"。于是：

  • 用户点了旧卡片 → 预订单 workflow 挂掉 → 之后即使点对卡片也没 workflow 接信号了。
  • spec 说"拒绝并要求刷新卡片"，但没定义拒绝后 workflow 是否存活。

正确语义应是：版本冲突是可恢复的业务拒绝——记录一次 STALE_CARD_REJECTED 审计，回发"卡片已过期请刷新"，workflow 继续回到选择器等待（continue 而非 return err）。只有真正的系统错误才 return。spec 需要明确这条，否则 plan 会照抄现在的错误写法。

重要级 会导致实现期分歧

W-1 "相似度候选匹配"（优先级 #5）是确定性裂缝

spec 通篇强调"确定性归并"，但优先级 #5 写的是"使用可配置的短时间窗口和字段相似度作为候选匹配"。相似度本质是启发式，与全文基调矛盾，且它直接决定了 PRE_AMBIGUOUS 的触发边界。

建议：把它明确定义为"仅生成候选项、必须经用户确认才可归并"，且默认阈值与"多候选即 AMBIGUOUS"的判定条件要写死；否则测试无法构造边界。

W-2 两套超时机制职责重叠：expires_at vs EscalateAfter

草稿表有 expires_at，workflow 有 24h EscalateAfter Timer。spec 分别提了"草稿过期率"和"超时升级"，但从没说两者关系：

  • 草稿 expires_at 到期后，草稿是作废？OrderConversation 转 EXPIRED？pre_order 转什么状态？
  • 24h Timer 升级到 PRE_ESCALATED 时，草稿是否过期？两个时间常量谁大谁小？

状态机里有 PRE_ESCALATED 但没有 PRE_EXPIRED，而 OrderConversation.status 枚举里又有 EXPIRED。两套实体的超时状态不咬合，是明确的语义空白。

W-3 并发控制对象与机制未定

spec 说"同一 session_id 同时只允许一个合并事务执行"。但代码锁的是 pre_orders 行（preorder_drafts.go 第 55 行 SELECT ... FOR UPDATE on pre_orders）。引入 OrderConversation 后：

  • 锁对象应是 conversation 还是 pre_order？两者若是 1:N（方案 B）就更复杂。
  • spec 同时提了"数据库锁或乐观版本号"——这两者是不同实现，plan 需要唯一答案。当前代码是悲观锁（FOR UPDATE）+ 版本重读，spec 应与之对齐或明确替换。

W-4 "原始消息必须先落库"缺少承载表

spec §消息表至少保存 列了 6 类字段（原文哈希、回复消息 ID、解析状态、重试次数、session_id…），但我核过全部 migrations/*.sql：不存在 inbound_messages / wecom_messages 之类的原始消息表。现有表只有 pre_orders（msg 级）和 pre_order_events（状态事件）。

这是新增表，spec 必须给出表名、主键与幂等键、以及与 pre_order_events 的边界（两者都记消息，别重复）。

W-5 correlation_id 生成规则随归并而变，未更新

代码里 deriveOrder 目前用 tenant:group:msg 拼 correlation（preorder.go 第 300 行）。归并之后"一条订单对应多条消息"，msg 已不再是有效标识。spec 要求"按 correlation_id 查完整链路"，却没定义它应该锚定到 session_id 还是根消息。不改就会导致链路查询在多轮场景下断链。

建议级 打磨项

  • S-1 监控指标"错误归并率"缺真相源——没有人工标注或影子对账就无法计算，需定义口径。
  • S-2 乱序消息"一律转人工"过重。企微会话存档按 seq 递增，乱序主要出现在回补/重放；建议分级：同窗口内乱序可缓冲等待，跨时间窗才转人工。
  • S-3 spec 未定义 OrderConversation 的并发上限（同一群/同一用户能同时开多少个会话），这是防滥用与资源边界的必要参数。
  • S-4 未说明"已确认会话拒绝吸收新消息"后，新消息应自动开新会话还是静默丢弃——当前措辞是"创建新会话或人工关联"，但自动创建需要客户归属判定，属未闭合逻辑。

四、你要的技巧：用 spec 派生测试用例

这个方法有个正式名字：Specification by Example / 验收测试矩阵（Acceptance Test Matrix）。核心洞察是——spec 里写不出 Given/When/Then 的句子，就是 spec 的漏洞。测试用例不是"顺带产出"，而是用来给 spec 做压力测试、把模糊地带照出来的探针。你记住的"把边界搞清楚"，机制就在这里。

4.1 六条转换规则（把 spec 条文机械地映射成用例）

spec 里的句式转换成的测试类型作用
"必须达到 …"正向用例证明能力存在
"明确不做 …"负向用例证明边界不可逾越（价值最高）
"优先级 1>2>3"边界用例命中第 N 条即停、第 N+1 条不触发
"短时间窗口 / 有限次数 / 24h"参数化边界⚠️ 模糊量词 = 找不到边界 = spec 漏洞
"无法确定 / 语义不明确"决策表穷举⚠️ 说"不明确"却不给判定 = spec 漏洞
"按 … 顺序处理"（7 步合并）序列/短路用例前步失败后续不得执行

五、建议的下一步（按优先级）

  1. 先补 B-2 的语义（最高优先）：明确 DraftVersion 存累积态还是增量，并定义合并器的契约与归属。这一条不解决，plan 第 1 个 task 就没法写。
  2. 再定 B-1 的数据模型：OrderConversation 与 pre_orders 的关系（方案 A/B 二选一）+ 新增 inbound 消息表（W-4）。这两个决定了 migration 009 之后要不要再加 010。
  3. 修正 B-3 的 FSM 边表，把 PreOrderFSM 的完整变更写进 spec；顺带解决 W-2 的 PRE_EXPIRED 缺失。
  4. 修 B-4 的 Temporal 语义：把版本冲突改成"可恢复拒绝"（continue），并补一条回归用例（TC-04）。这是一条真 bug 级修正，不改上线后会踩。
