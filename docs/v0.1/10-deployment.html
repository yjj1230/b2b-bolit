2 · 物理目录规划

/opt/b2b_pilot_v3/                  # 部署根目录
├── code/                          # 代码（git clone）
│   ├── cmd/{api,wecom,worker,sync}/
│   ├── internal/                  # domain/repo/workflows/authz/wecom/integration
│   ├── migrations/                # 001-005 幂等迁移
│   ├── schema.zed
│   └── docker-compose.yml
├── config/                        # 配置（不入 git 的敏感项）
│   ├── wecom-tenant.json          # 企微租户配置（corp_id/agent/密钥引用）
│   └── sync-feishu.json           # 飞书同步配置（0.1 新增）
├── data/                          # 数据卷（docker volumes 或 bind mount）
│   ├── pg/                        # PostgreSQL 数据（facts + events）
│   ├── temporal/                  # Temporal PG 后端数据
│   └── evidence/                  # 凭证/回单文件存储（租户隔离 + 静态加密）
├── logs/                          # 日志
│   ├── api/ wecom/ worker/ sync/
│   └── audit/                     # 审计日志（append-only，不入代码库）
├── secrets/                       # 敏感凭据（0600，仅当次运行）
│   ├── encoding_aes_key
│   ├── archive_private_keys/
│   └── feishu_app_secret
└── scripts/                       # 运维脚本（备份/回滚/对账）
  • 代码/配置分离：代码只含默认值与占位；真实配置放 config/（敏感项引用 secrets/）；
  • 敏感与参数分离：非敏感参数进版本化配置；敏感凭据只进当次运行目录（权限 0600、日志零回显、不入 git）——承诺冻结不冻结秘密；
  • 审计不入代码库：审计是机器本地事实，与代码生命周期不同（logs/audit/），避免提交噪音与多机冲突；
  • 凭证文件存储：evidence/ 与业务库分离（沿用 02 §8.4 文件路径引用模式 + 对象存储 SSE）。

5 · 飞书同步 Job（cmd/sync）

flowchart LR T["定时触发（cron / 间隔）"] --> P["拉取增量
飞书数据库 / 多维表 / 三方审批流"] P --> M["映射
flow_id → order_id 链路（legacy_flow_mapping）"] M --> V["校验
checksum + 幂等批次（migration_batches）"] V --> W["写入 PG
订单/审批/回单视图"] W --> L["留痕
批次日志 + 审计"]
  • 调度：容器内常驻定时器或宿主 cron；周期可配（建议 5m-1h 按业务时效需求）；
  • 数据源：① 飞书数据库（原订单/审批表）；② 飞书多维表（bitable_flow_records / customer_bitable_sync）；③ 飞书三方审批流（审批实例/任务）；
  • 单向只读：0.1 只同步不进、不回写——原审批流不停；商务在本系统流里看到飞书侧数据并操作（操作结果留本系统）；
  • 幂等：migration_batches（UNIQUE(tenant_id, source, checksum)）锚点，重跑不重复；
  • 映射：复用 02 §8 迁移布局——flow_id/stage_code/instance_id → legacy_flow_mapping；
  • 敏感边界：Open ID/访问令牌/原始表单 JSON 不迁移（02 §8.4 mapping/retention 冻结）；
  • 失败处理：单批次失败重试 + 告警，不阻塞后续批次；同步状态可在系统内查看。

6 · 0.1 上线步骤

  1. 调研冻结：程序员调研飞书侧结构（数据库/多维表/三方审批流部署），产出调研清单（见 11-migration.html §3）；
  2. 仓库准备：git clone 到 /opt/b2b_pilot_v3/code；配置 config/ 与 secrets/（0600）；
  3. 镜像构建：docker compose build（api/worker/wecom/sync 四 target）；
  4. 基础设施：docker compose up -d postgres spicedb temporal → migrate（001-005）→ spicedb-schema（seedrel 写 schema.zed + 关系基线）；
  5. 应用启动：docker compose up -d api worker wecom → 健康检查全绿（healthz / wecom/healthz）；
  6. 同步接入：配置 sync → 首跑全量 + 增量验证（抽样核对飞书 vs 本系统订单数）；
  7. 企微回调：企微后台配置回调 URL（HTTPS 反代）→ URL 验证通过 → 出站卡片冒烟；
  8. 商务试用：虹励账号开通 → 跑通一笔完整订单（下单→审价→备货→发货→开票→回单）；
  9. 验收：17 场景 walkthrough + N-01..N-10 测试 + 守门员/合并开票/仓库群回单专项验证；
  10. 上线：飞书原流程不动，0.1 平行流运行；使用中快速升级 0.2/0.3（文档驱动迭代）。

7 · 运维要点

项要求
备份PG 每日全量 + WAL 归档；evidence 卷增量备份；备份加密存储；恢复演练季度执行
日志应用日志按服务分目录（logs/）；审计日志 append-only（logs/audit/）不入代码库；日志保留 30 天
监控探针三件套（api/wecom/sync）；同步超期告警（migration_batches 最近成功时间 > 2×周期）；Temporal 队列深度
回滚数据库：PG 备份恢复 + 迁移回滚（001-005 幂等可重跑）；应用：docker compose 镜像回退；发布动作与代码同版本演化
安全红线（部署面）备份先行、默认 dry-run、禁止破坏性操作、操作审计、失败自动回滚（沿用 证据收敛式 Review V2 §第七幕 五条红线）
密钥轮换企微 EncodingAESKey / 存档私钥（publickey_ver 保留历史）/ 飞书 secret 定期轮换，轮换留痕

8 · 影子轨 compose（12-shadow-full-flow §7）

影子轨 S 随 v0.1 同发但独立环境、独立开关、独立回滚（D-010）：docker compose -p b2b-shadow -f docker-compose.shadow.yml up（专用 compose 项目/网络，自带 shadow-temporal 独立实例，与 A 轨零共享面）。端口全部只绑回环：shadow-postgres 15433 / shadow-spicedb 15052 / shadow-api 18082；唯一出网面是只读数据源与运维通道。命令：make shadow-up / shadow-down / shadow-audit / shadow-replay / shadow-reset-skipped。生命周期：运行到 v0.3 正式上线后撤销（归档 → 停栈 → drop b2b_shadow）；期间按 D-011 可多次发布影子系统（S 线高频工具/配置，F 线 workflow 影子先行）。上线步骤：R1 影子专用环境全量重放（S-01..S-08 全绿 + 基线报告）→ 正式上线 + 零出站/零回写哨兵 + 24h 稳定（G4 证据）。影子轨故障不影响 A 轨：docker compose -p b2b-shadow -f docker-compose.shadow.yml down。
