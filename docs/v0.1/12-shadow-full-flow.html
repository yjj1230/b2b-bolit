2 · 为什么现在做（v0.1 缺口 → v0.2/v0.3 承接）

2.1 当前 v0.1 的状态机空档

  • 代码侧：internal/domain 六台 FSM、OrderWorkflow 四段推进 + 13 个审批 Signal、repo 守恒事务、scripts/audit 审计链——已全部实现，但 v0.1 生产只用了桥接台账，飞书审批期间这些代码没有在真实业务数据上跑过。
  • 同步侧：cmd/sync + ApplySyncBatch 目前是快照 upsert 写 orders.state，不经过 FSM 校验——只能做视图，不能证明状态机能接住旧系统的真实路径。
  • 计划侧：发布计划v2 第 1 次（桥接）与第 2 次（角色迁入新系统办理）之间，没有任何机制回答「我们的全流程状态机能不能接住飞书真实业务」。影子轨就是这个验证器。

2.2 与 v0.2 设计 Preview 的承接

按 v0.2_设计_preview.html（讨论稿）与 docs/发布计划v2/渐进式发布计划v2.html 的最新讨论：v0.1 + 影子轨提前完成 v0.2 前的流程校验测试，安全系数大幅提高，因此 v0.2 = 数据正式迁入新系统（唯一状态机与数据真相），除销售 / 主管 / 董事长外全部岗位切换到企微体系，旧系统复杂流程冻结、只保留为三岗位新增的极简飞书审批；v0.3 = 企微体系发布完成：销售 / 主管 / 董事长迁入企微 + 全量数据 100% 迁完（四层对账）+ 影子撤销 + 旧系统只读归档 / 下线。影子轨是这两次发布的前置安全装置，并且按 D-010/D-011：运行到 v0.3 正式上线后撤销；v0.3 之前影子系统可以按验证需要多次发布（映射、种子、审计与重放工具），A 轨不因影子发布而重新发布。

5 · 数据流：摄入 → 翻译 → 信号 → 执行 → 审计

#步骤组件动作落库 / 产物
1只读摄入cmd/shadow-ingest配置驱动拉取 orders + stock_prepare_events + shipment_events + invoice_events + 审批任务结果；SanitizeRow 敏感剥离；批次 checksum 幂等orders 快照 + shadow_source_events
2影子建单cmd/shadow-feed每条 flow 的首个 ORD 事件 → 建影子订单（idempotency 搬源键）→ 幂等 StartWorkfloworders（state=ORD_REQUESTED）+ Workflow 启动
3事件翻译cmd/shadow-feed按 shadow-feed.json 把 source 事件映射为 Signal 名 + payload；未知动作 → UNMAPPED 分歧，不猜测shadow_signal_log（NEW → DELIVERED / FAILED）
4信号投递cmd/shadow-feed按 (flow_id, source_event_id) 幂等投递；同一 flow 事件按 occurred_at 串行Temporal Signal
5状态机执行cmd/shadow-worker真实 OrderWorkflow：FSM 校验 → repo 单事务写盘 → 守恒断言 → approval_tasks；影子模式抑制 Timer、接受 shadow-inject 分支信号；通知器 = mockorder_events / stock_prepares / shipments / invoices 全量影子事件链
6分歧捕获cmd/shadow-feed + scripts/shadow_audit非法迁移 / 未映射事件 / 链断裂 / 守恒违例 / 状态失配 / 卡住等待 → 写分歧表shadow_divergences
7覆盖率统计scripts/shadow_audit影子 order_events 的每步迁移对 79 边去重计数shadow_coverage
8每日报告cmd/shadow-audit（-interval + state-file 探针）覆盖率 / 分歧 / 状态对齐 / 卡住清单，写 markdown + JSONlogs/audit/shadow/shadow-audit-YYYYMMDD.md
影子模式（工作流最小改造）
OrderWorkflowParams 增加 Shadow bool：为 true 时 ApprovalRemindAfter / ApprovalEscalateAfter / ReceiptExceptionAfter 全部不调度；新增 shadow-only 控制信号 shadow-inject，由 feed 在旧系统出现「无回单超期进例外」等 timer 触发事件时注入等价分支。推进只认信号，不靠真实时间——保证同一事件序列可确定性重放。

映射三规则：

  • 白名单推进：只投递映射表里已确认的动作；未知 / 新动作写 UNMAPPED_EVENT 分歧，绝不猜测；

A.3 验收口径（回答「不影响生产业务库」）

  • 负向守卫全绿：把生产 DSN / 生产队列 / default namespace / official 企微 / bridge=true 依次喂给影子二进制，全部拒绝启动；
  • 网络不可达：影子容器无法解析并连接 A 轨任何主机名；影子与 A 轨共享面为零（D-010 独立环境）；
  • 迁移隔离：生产库执行主 migrate 后无任何 shadow_* 表；影子库才有 008 五表；
  • 零写证明：影子 R1 新单全集重放前后，生产库订单数 / 事件数 / 表清单抽样一致；写哨兵 7 天无告警；
  • A 轨无感：影子轨开/停/重放三个动作前后，桥接 API、生产 workflow 队列深度、生产 SpiceDB 授权判定均无异常（G4 证据）。

A.4 残余风险（不隐瞒）

  • 共享 Temporal 集群：namespace 提供逻辑隔离，但影子重放量大时可能占用集群资源——属于可用性风险，不写生产 PG；必要时升级为独立 Temporal 实例（SH-04 待决项）；
  • 蓄意绕行：持有生产凭据的人手动把生产 DSN 灌进影子容器可绕过守卫——护栏是「默认拒绝 + 权限最小化 + 操作审计」，不承诺防内鬼；
  • 宿主机端口：若生产 PG 继续绑 0.0.0.0，影子容器理论上可经宿主 IP 尝试连接——必须执行生产端口回环绑定/防火墙（A-04 验收项）；
  • pgAPI 凭据：影子只应持有只读 key；若误发写权限，影响面在 pgAPI/飞书侧而非生产 PG，仍属发布配置审计红线。
