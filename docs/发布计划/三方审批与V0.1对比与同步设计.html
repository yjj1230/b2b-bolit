0结论摘要（TL;DR）

① 业务语义高度同构

两套流程都是「下单→审价→终审(C/D)→备货→发货→开票/回单→归档」，节点一一映射（gap-analysis §2：ORD=已开单、STK=已备货、SHP=已发货、INV=已开票）。

② 结构差异仅 4 处

审价归属（旧系统在订单创建内 3 步审批 vs v0.1 独立 N2）；备货多「财务确认到款」闸门；开票节点数（旧系统 8 节点、5 深链不可达）；回单/凭证的位置与载体。

③ 方向性差异（最关键）

v0.1 原设计是平行流；你要的是 v0.1 把订单写进旧系统/飞书流。现有 v0.1 设计没有这条写路径，需要新增；新增开发量全部归 v0.1，旧系统仅一处针对性小改。

④ 数据兼容结论

不需要把 JSONL 迁入 PG 才能上线。只需做三件事（全在 v0.1 侧）：写方向（代理 OAuth + 既有接口）、读方向（cmd/sync 多维表源 + PG 直查）、5 项状态语义先拍板。

⑤ 上线节奏

v0.1 作为「下单入口 + 订单列表/状态视图」，飞书流全权续跑，销售助手获得完整体验闭环（下单→飞书审批→状态回显→驳回重提）。关键路径仍是企微备案域名。

⑥ 最终目标（用户确认）

以企微版流程取代飞书三方审批流：v0.1–v0.4 逐版迁移办理动作，0.5 完成两级终审迁入与真相源切换后飞书整体下线（历史只读归档 + 回滚通道）。完整路线见渐进式发布计划.html。

关键机制（决定"最小成本接入"的事实）

  • 主键体系：flow_id = SO-YYYYMMDD-XXXX（贯穿四环节）；instance_id = <order_id>-<14位时间戳>；stage_id = <flow_id>-<STAGE_CODE>-<seq>（submitExternalOrder.ts:218-321）。
  • 全链路由飞书回调驱动：POST /feishu/approval/action-callback 接收同意/拒绝/退回/撤回 → 推进本地 JSONL 状态、更新飞书实例、best-effort 同步多维表。无本地轮询。
  • 订单创建幂等：create_idempotency_key（8-200 字符）+ 内容指纹 + 内存去重 + 文件锁，重复提交返回既有订单。
  • 身份与鉴权：创建页需 OAuth 换取的 HMAC token（CREATE_ORDER_AUTH_SECRET，2h TTL，白名单）；机器通道 x-renheng-wecom-bridge header 当前硬编码只允许王杰并强制 approval_profile=WECOM_WANGJIE_TEST。
  • 审批人解析：data/approval_role_map.json 按角色 key 映射 open_id；提交人与主管同一人时主管自动通过；approval_profile 字段已存在。注意 auto_approve 只声明不赋值，实际不生效
  • 董事长触发：customer_level ∈ {C,D}（:1537），与金额无关。
  • 台账：多维表按 flow_id 建行/更新（flowBitableSync.ts）；JSONL 是生产真相，多维表是对账副本。
  • 开票深链现状：生产的开票实例首任务=盖章回传（无票模式先走会签再回传），通过后直接归档；「财务开票→上传发票→接收→回款跟进」5 节点代码存在但创建路径不产出，不可达。

4差异分析（决策视角）

4.1 结构差异 → 对"下单进飞书流"的影响

与下单本身相关的差异只有入口/平台差异（飞书 H5 vs 企微助手）。一旦订单在 v0.1 创建并桥接进旧系统，后续审价/终审/备货/发货/开票的差异全部由飞书流现有实现承担，v0.1 无需关心。因此对「v0.1 只做下单入口」而言业务差异不构成阻塞；真正要处理的是 v0.1 表单字段 ↔ 旧系统 SubmitOrderInput 的映射（§6.2）。

4.2 状态语义差异（T1.3 未对口径的 5 项，上线前必须拍板）

#待对口径项说明
1订单已撤回/作废（CANCELED）v0.1 ORD 无取消终态：用 ORD_REJECTED 兜底 or 新增 CANCELLED？
2发货单已取消/已驳回SHP 无取消/驳回态。
3待上传回单位置旧系统回单在 SHP 段（RECEIPT_PENDING）；T1.3 建议回单不独立成状态（receipt.go 分流 HAVE_RECEIPT/RECEIPT_EXCEPTION）。
4开票信息填写位置旧系统 INVOICE_INFO_FILL 在 SHP 段，T1.3 建议移 INV 段。
5待客户盖章回传代码有 CUSTOMER_ORDER_STAMP_RETURN 节点（附件可选）；以代码为准（invoiceApproval.ts:593-681）——T1.3 曾认为代码无此节点。
提醒：这 5 项不拍板，cmd/sync 的状态映射配置就无法冻结；但只要 v0.1 只做"下单+视图"，可先用「旧系统原始状态直存 payload + 视图层粗粒度映射」过渡（§6.3）。

4.4 对上线节奏的含义

旧系统已有已知缺陷（22 高/48 中/12 低），最相关：回款金额不参与业务判断、修改订单服务端不重判、48h 升级链未接线。这些缺陷在"飞书流续跑"模型下继续存在但不新增暴露面——v0.1 下单只新增"创建"入口，不触碰修改/回款逻辑。

结论：比"平行流"更稳

"v0.1 下单 + 飞书流续跑"比 v0.1 原"平行流"（商务在 v0.1 操作备货/发货/开票）更稳：原平行流要求商务操作与飞书流并行执行同一批节点（双执行、一致性靠单向同步兜底），而"下单+续跑"模型下旧系统是唯一执行者，不存在双执行一致性问题。

5.1 审批链路无感续跑（飞书侧视角）

结论：销售主管审批、董事长审批、以及后续备货/发货/开票审批，在飞书侧完全无感

它们与飞书 H5 下单的订单走同一套机制，审批人感知不到订单来自 v0.1（企微）。

机制证据（代码级）

  • ① 订单创建 = 同一入口：v0.1 调 POST /external-orders/create → submitExternalOrderFromFormSync → createExternalInstance（同一 FEISHU_APPROVAL_CODE）→ 审批机器人消息卡片 + 飞书审批中心待办。
  • ② 审批人解析 = 同一 role map：approval_role_map.json（TEST_*）决定审批人，与下单渠道无关。
  • ③ 后续节点自动推进：审批动作 → action-callback → 本地 JSONL 状态推进 → 自动创建备货/发货/开票实例；v0.1 全程不介入。
  • ④ 审批表单无渠道痕迹：external instance 的 i18n 只有订单号/客户/金额等；orders.jsonl 的 source 固定为 "external-orders-create-form"；不带桥接头时 approval_profile 为空。
  • ⑤ 身份链路透明：企微 user_id 只在 v0.1 内部；落到旧系统与飞书的身份 = OAuth 换到的飞书 open_id/user_id。

三个"有感觉"的边界（必须知晓，均非缺陷）

#边界说明处置（已确认）
1信息确认节点由提交人办理 销售助手下单后（若本人为提交人）需在飞书点一次「信息确认」——飞书 H5 下单同样如此，是旧流程既有第一步；代下单时由代办人确认。 已决策：旧系统针对性小改。办理需 approver_token（JSONL 中 manager_approver_view_token），该 token 下单响应不返回、多维表链接不带、submitter 视角拿不到；伪造回调需 FEISHU_ACTION_CALLBACK_TOKEN（禁止）。改动三点（集中 submitExternalOrder.ts + approval_role_map.json）：识别（幂等键 v0.1 前缀）→ 自动确认（系统内部直接调既有 decision 核心，审计等价提交人本人）→ profile 注入（V01_SALES_ASSISTANT 配真实审批人，与王杰解耦）。
2审批人 = 当前角色映射（王杰被配置进不该进的角色） 生产 role map 中主管/董事长 fallback 到 TEST_MANAGER=王杰；财务/开票 or-sign 组含王杰（附录 D）。 已决策：默认映射完全不理会、保持原样。背景：王杰/王鑫力=程序员不点审批；张有连=董事长（自动跳过主管=正确业务勿动）。唯一前置：V01 profile 必须在 approval_profiles 显式配置 TEST_SUPERVISOR（建议同时 TEST_CHAIRMAN）——profile 覆盖是 merge 非替换（approvalOrSign.ts:79-96），不配则仍 fallback 到王杰。
3驳回/重提在 v0.1 操作 驳回后销售助手在 v0.1 看原因、复制重提（reuse-data）。 已确认：其它用户零影响。驳回订单在旧系统所有视图照常可见（工作台/审批中心已办/详情页/对账台）。v0.1 对旧系统全部影响面=多一个下单入口 + cmd/sync 只读拉取 + 授权回调白名单 + 白名单追加虹励。
一句话：审批人（主管/董事长/财务/仓管）在飞书里看到的是标准待办、渠道透明零感知。已决策的旧系统小改让虹励在企微端完全无感，且与默认映射解耦；该小改只影响 v0.1 订单，不影响飞书 H5 用户。上线前需现场查证生产 role map 实际内容与现有滞留单（边界 2）。

6.5 风险与红线

红线（沿用旧系统 README）：不清空/覆盖 data/*.jsonl；测试服务不得读写生产 data 目录；桥接 secret 不进 Git；生产修复保留前后证据。
  • 风险 1：create 接口是浏览器表单接口（multipart），v0.1 以 Bearer 调用——高并发需确认旧系统锁/幂等能扛住（销售助手单人场景量级小无碍）。
  • 风险 2：企微备案域名未就绪 → 群聊入口不可用；备用 PC 订单后台/侧边栏走通数据线。
  • 风险 3：T3 调研（webhook 可行性）未完成前，实时性按轮询兜底，不阻塞。
  • 风险 4：开票阶段 4 个"销售/代办"节点处理人仍是飞书侧销售员，v0.1 不代做——需确认销售员会继续用飞书办理。
  • 风险 5（现状事实）：开票深链财务开票→回款跟进当前不可达，生产开票止于"盖章回传→归档"。若业务方期望这些环节真实生效，需旧系统单独排期修复，不要算进 v0.1 上线范围。
  • 风险 6（流程小修）：发布中主要流程不变、允许小修，优先在飞书端临时修补；唯一硬约束：0.5 真相源切换前流程必须冻结（附录 C D13）。
