# 渐进式发布计划 · 可行性验证报告

> 生成：2026-08-18 · 验证视角：**数据不可丢失、不可有不能解决的死路**；发布过程中主要流程不变、允许小修（飞书端可临时性修补）。
> 方法：逐版过一遍 + 命门代码验证 + 数据/死路专项审查。结论均有 `文件:行号` 证据。

---

## 0. 结论摘要

**计划成立，没有不可跨越的断点；但有 8 个「必须堵上的点」（P0），堵上即成立、堵不上则会在数据或流程上出问题。** 最关键的三条：

1. **受信办理通道已验证可行**——备货/发货/开票的 decision 接口只校验 `approver_token`（无飞书身份依赖、无 entry 限制），文件上传 multer 已就绪（`stockPrepares.ts:974`、`shipments.ts:1853`、`invoices.ts:772`）。执行迁移没有「鉴权死路」。
2. **0.5 真相源切换前，必须补一次 JSONL 级全量迁移（含事件链）**——v0.1–v0.4 的同步是「多维表摘要 + 快照末条」，事件链没进 PG；不补则审计历史丢失（数据丢失）。
3. **开票环节必须按「真实任务」定义**——「开票申请」是抄送不是办理任务、财务深链（上传发票/接收/回款跟进）当前不可达；v0.3 能迁的只有「盖章回传」这一个真实任务节点 + 财务「确认到款」。

## 2. 技术命门验证：受信办理通道（执行迁移的基础）

**结论：成立。** 新系统办理 → 受信端点 → 旧系统 decision 核心，这条链路在代码上完全通畅。

| 环节 | decision 鉴权 | 证据 | 文件上传 |
| --- | --- | --- | --- |
| 订单 | approver_token + task_id + entry=approval_center 免身份 | `externalOrders.ts:4965-5007` | 无 |
| 备货 | **仅 approver_token 匹配**（无身份/entry） | `stockPrepares.ts:963-977` | 无（字段型 extraData） |
| 发货 | 仅 approver_token 匹配 | `shipments.ts:1853-1871` | **receipt_files 必传**（回单节点，最多 10 个） |
| 开票 | 仅 approver_token 匹配 | `invoices.ts:772-789` | **invoice_files**（发票/盖章回传，最多 10 个） |

**两个需临时修补的缺陷（很小，属「飞书端临时性修补」范畴）：**

1. **operatorOpenId 是占位符**：备货/开票 decision 写死 `"(stock-prepare-web-approver)"` / `"(invoice-web-approver)"`（`stockPrepares.ts:1062`、`invoices.ts` decision 内）——审计「谁办的」不精确。受信端点应传真实 operator（新系统用户身份）。
2. **无并发锁**：备货/发货/开票 decision 无订单那样的内存锁（`activeOrderDecisionKeys`）——双通道（新系统 + 飞书审批中心残留待办）同时办理同一任务时有极小并发窗口。受信端点加一道幂等锁即可（临时修补）。

## 3. 逐版过一遍

### v0.1 销售助手（下单入口 + 信息确认自动 + 视图）

| 维度 | 结论 |
| --- | --- |
| 成立性 | ✅ 下单（OAuth 代理 + 既有创建接口）、信息确认自动（幂等键前缀识别 → 内部调 decision）、状态回显（自建单 PG 直查 + 详情跳 flows 页）——全部已验证可行 |
| 数据风险 | 无（自建单，不碰存量）；幂等键 + 旧系统幂等兜底 |
| 死路风险 | 无；唯一注意：信息确认自动通过的「消息时序」——应先自动通过、再发待办消息（或消息后补已办），否则虹励会收到一条「待办」卡片但实际已通过（体验矛盾，非死路） |
| 需补 | ① V01 profile 必须显式配 TEST_SUPERVISOR（merge 语义，否则 fallback 王杰）；② 白名单加虹励；③ 授权回调白名单 |

| 维度 | 结论 |

### 0.5 两级终审迁入 + 真相源切换（取代完成）

| 维度 | 结论 |
| --- | --- |
| 成立性 | ⚠️ **这不是普通一版，是一次系统切换**：需要新系统审批台（主管/董事长 UI + 通知 + 超时）+ 环节编排接管 + 一次性数据迁移 + 切换仪式 |
| 数据风险 | 🔴 **最大风险点**：真相源从 JSONL → PG。必须「先同步完成 → 冻结旧系统写 → 终审对账 → 宣告切换」，严禁先停旧系统再迁移；切换前补一次 JSONL 级全量（含事件链） |
| 死路风险 | 🔴 **进行中订单**（切换时刻处于中间状态的单）去向必须明确：冻结旧系统接收新单，存量单在旧系统走完，新单走新系统；新系统状态机必须接住所有中间状态（T1.3 的 5 项未对口径必须切换前拍板） |

## 4. 数据不丢失 · 专项（7 个风险点 + 保护）

| # | 风险点 | 丢失后果 | 保护措施 |
| --- | --- | --- | --- |
| D1 | 0.5 真相源切换一次性迁移 | 订单/状态/历史丢失 | 先同步完成→冻结写→终审对账→切换；严禁反向顺序 |
| D2 | 事件链未进 PG | 审计史丢失（谁何时做了什么） | 0.5 前补 JSONL 级全量迁移（orders + order_events 等，非多维表摘要） |
| D3 | 附件（合同/出库单/回单/发票） | 业务凭证丢失 | 0.5 前明确归属：旧系统保留只读 + 新系统链接，或迁对象存储；严禁停机即丢 |
| D4 | open_id 历史身份 | 审批史无法追溯人 | 飞书 open_id → 企微 user_id 映射表永久保留 |
| D5 | 同步仅快照末条 | 中间状态史丢失 | cmd/sync 按「快照链取末条 + 事件链全量」双轨；事件链不能丢 |
| D6 | 新系统办理「以为成功」但受信通道失败 | 新系统 PG 与旧系统真相不一致 | 新系统以「受信通道成功回执」为准落库；失败重试 + 对账 |
| D7 | 多维表源 vs JSONL 源信息差异 | 状态/字段不完整 | 多维表只作列表摘要；详情/对账以 flows 页或 JSONL 导出为准 |

## 5. 死路 · 专项（8 个风险点 + 兜底）

| # | 死路 | 后果 | 兜底 |
| --- | --- | --- | --- |
| S1 | 存量待办无规则 | 迁移后某订单卡死在旧待办 | 「新单新办法、存量单飞书走完」；迁移开关按 flow_id 批次生效 |
| S2 | 开票环节按文档节点名迁 | 迁到不存在的任务 | 按真实任务定义：v0.3 迁「确认到款」+「盖章回传」；财务深链若业务需要则先在飞书端补接线（临时修补）或明确不做 |
| S3 | 0.5 后旧系统停机、flows 页/附件不可用 | 详情/附件死路 | 0.5 前置：新系统详情页 + 附件查看就绪；或旧系统保留只读运行 |
| S4 | 进行中订单切换时无处可去 | 切换时刻的单卡死 | 冻结新单、存量走完、新系统状态机接住所有中间状态（T1.3 五项目拍板） |
| S5 | 双通道并发办理 | 重复推进/状态错乱 | 受信端点加幂等锁（临时修补）；旧系统 task 已办检测兜底 |
| S6 | 超时提醒失联 | 迁出环节商务已不飞书，提醒发到飞书无人看 | v0.2 起新系统待办清单 + 超时机制；或明确接受飞书提醒继续发（可控） |
| S7 | 信息确认自动通过的消息时序 | 收到「待办」却已通过 | 先自动通过再发消息，或消息后补已办更新 |
| S8 | 流程小修与迁移打架 | 迁移中流程还在变，映射错乱 | 0.5 切换前冻结流程（业务修正暂停）；受信通道按 task_id 粒度天然适应小修 |

| 项 | 结论 |
| --- | --- |
| 允许范围 | 节点增删、字段调整、顺序微调——发布过程中允许，且优先在飞书端临时修补（飞书是执行真相，改一处即全局生效） |
| 新系统如何跟随 | 同步字段映射（cmd/sync 配置驱动）、状态映射（T1.3 表）、受信通道 extraData 字段映射——三者都要「配置驱动」，小修只改配置不改代码 |

| **冻结点** | **0.5 真相源切换前，流程必须冻结**（业务修正暂停一段时间），否则切换时流程还在变 = 数据错乱死路 |

## 8. 最终结论

1. **发布计划成立，无不可跨越的技术断点**——受信办理通道（执行迁移的命门）已验证：三个 decision 接口只需 approver_token、支持文件上传，无飞书身份依赖。
2. **最大的工程风险在 0.5**（不是 v0.1-v0.4）：真相源切换 = 一次性数据迁移（含事件链）+ 新系统审批台 + 环节编排接管 + 切换仪式。它应作为「切换项目」单独立项，而非普通一版。
3. **最大的数据风险**：事件链与附件的归属——v0.1-v0.4 的摘要同步不覆盖它们，0.5 前必须补齐，否则审计史与业务凭证丢失。
4. **最大的死路风险**：存量待办 + 进行中订单 + 开票环节真实任务——三条都已有明确兜底方案（S1/S4/S2）。
5. **流程小修**：允许且可控，唯一硬约束是 0.5 前冻结流程；受信通道按 task_id 粒度天然兼容节点级小修。

**一句话**：按 P0-1 到 P0-8 的顺序逐条堵上，本发布计划即可按 v0.1 → v0.4 → 0.5 的节奏安全推进，数据不丢、无死路。
