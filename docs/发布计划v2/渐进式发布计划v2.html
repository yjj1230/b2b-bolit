0 · 结论摘要（TL;DR）

三次发布成立，但每刀都更重。压缩的关键不是把五周的事硬塞进三周，而是改变「双执行」策略：第 2 次发布把商务、财务、仓管一次迁入，但他们办理的每一笔都通过受信办理通道写回旧飞书系统，旧系统继续当真相源；第 3 次发布把销售、主管、董事长一次迁入，同时执行一次性数据切换，新系统才成为真相源。

三句话记住三刀：

  • 第 1 刀（销售助理）：新系统只做「下单入口 + 状态视图」，订单写进旧飞书流，后续环节旧系统照跑。这一刀与原 v0.1 完全一致。
  • 第 2 刀（商务 + 财务 + 仓管）：把原 v0.2 + v0.3 合并。商务办备货、财务确认到款、仓管办发货和回单，全部在新系统操作，但结果经受信通道落回旧系统。旧系统仍是真相源，飞书审批中心仍可见可办（存量单）。
  • 第 3 刀（销售 + 切换）：把原 v0.4 + 0.5 合并。销售办开票信息与盖章回传，主管/董事长迁入新系统审批台；随后执行「冻结旧系统 → 全量迁移 → 对账 → 切换」，新系统成为唯一真相源，飞书三方审批流整体下线。

最重要的约束：第 3 次发布不是普通版本，是一次系统切换项目，必须单独演练；第 2 次发布前必须把「受信办理通道」补齐（真实操作人 + 幂等锁）；三次发布全程沿用同一原则——数据不丢、无死路、旧系统尽量少改。

3 · 第 2 次发布：商务 + 财务 + 仓管接入

3.1 本次发布做什么（原 v0.2 + v0.3 合并）

三个角色一次发布，但每个角色有独立灰度开关；底层共用同一条「受信办理通道」。旧系统仍然是真相源，新系统是执行入口；每笔办理都以「受信通道成功」为准落库。

角色迁入环节（新系统操作）经旧系统哪个 decision 接口落地
商务备货「填写发货仓」：选仓/自提、收件人、电话、收货地址 → 通过/驳回POST /stock-prepares/:id/decision（business task，字段型 extraData，无文件）
财务款到类订单「确认到款」→ 通过/驳回；到款状态回显POST /stock-prepares/:id/decision（finance task）
仓管① 发货「确认已经发货」（数量守恒）；② 上传回单（receipt_files 必传，最多 10 个）POST /shipments/:id/decision（warehouse task / receipt task，multipart 已就绪）

本次不做：开票「盖章回传」留到第 3 次（办理人是销售/代办，不是本次角色）；财务深链（上传发票/接收/回款跟进）当前旧系统不可达，本次不做，切换后再由新系统全权承接。

3.4 三角色一次发布的「合」与「分」

合

  • 同一条受信通道，同一套鉴权（approver_token + task_id）
  • 同一套幂等/重试/对账机制
  • 同一次发布窗口，减少发布次数

分

  • 按角色灰度开关：商务先开，财务/仓管跟进
  • 按 flow_id 批次生效：新单新办法，存量单飞书走完
  • 三角色各自验收，不互相阻塞

风险控制

  • 开票范围先说清：本次只做确认到款，不做盖章回传/上传发票
  • 仓管金额不可见（剥价）
  • 商务待办按 approver_open_ids 过滤，不能串角色

3.5 存量待办规则（本次发布前必须定稿）

规则：新单新办法、存量单飞书走完。第 2 次发布上线的时刻，旧系统里已有的 PENDING 待办（商务填写发货仓/财务确认到款/仓库发货）继续在飞书办完；只有发布后新建的订单才走新系统执行。迁移开关按 flow_id 批次生效，不做存量待办搬运。

3.6 验收标准

角色验收项通过标准
商务备货办理新系统选仓 + 收货地址 → 通过 → 受信通道成功 → 旧系统生成发货单给仓管；驳回通知销售
财务确认到款款到类订单在新系统确认到款 → 旧系统状态推进 → 新系统回显到款
仓管确认发货新系统填本次发货数量 → 超发拦截（输入 6 应发 5 → 拒绝）→ 通过后旧系统发货状态更新
仓管上传回单新系统传回单文件 → 受信通道 multipart 直传旧系统 → 旧系统 receipt_files 可查
全局幂等/重试同一任务重复提交 → 幂等回执；受信通道失败 → 新系统不落「已办」、可重试
全局双通道并发新系统与飞书残留待办同时办同一任务 → 一方成功、另一方 ALREADY，不产生双状态

3.7 本次发布的回滚与兜底

  • 回滚：按角色开关关闭新系统办理入口，该角色回飞书办；旧系统不暂停、不回滚。
  • 数据兜底：真相仍在旧系统 JSONL；新系统 PG 只是执行视图，可随时从 pgAPI/多维表重建。
  • 附件兜底：回单文件真相在旧系统，新系统只存链接；旧系统不可用时走手动补登。

4 · 第 3 次发布：销售接入 + 全部数据切换

4.1 本次发布做什么（原 v0.4 + 0.5 合并）

这是整个计划里最重的一刀：既是最后一批角色迁入，又是真相源切换。必须先完成角色迁入，等销售/主管/董事长在新系统跑通验收，再执行切换仪式。

子阶段内容
A. 销售环节迁入销售：填写开票信息（shipment invoice-info task）、盖章回传（invoice stamp-return task）；驳回/重提体验闭环
B. 两级终审迁入销售主管：审价；董事长：C/D 级终审；新系统审批台 + 通知 + 超时提醒
C. 全量数据迁移旧系统 JSONL（orders/order_events/stock/shipment/invoice 全家族）→ 新系统 PG；含事件链，不做摘要式快照
D. 切换仪式冻结旧系统写 → 终审对账 → 切换开关 → 旧系统只读归档，飞书审批流下线

4.2 切换时序（不能乱）

flowchart TB STEP1["① 全量迁移：JSONL → PG
orders + order_events + stock/shipment/invoice 事件链"] --> STEP2["② 预对账：订单数 / 状态 / 事件链 / 附件 四层对账"] STEP2 --> STEP3["③ 冻结旧系统：停新单、停办理入口；存量单收口"] STEP3 --> STEP4["④ 终审对账：业务方抽单确认，差异清零"] STEP4 --> STEP5["⑤ 切换开关：新系统 PG 为唯一真相源，停受信通道"] STEP5 --> STEP6["⑥ 旧系统只读归档：flows/附件可查，飞书审批流下线"] STEP6 --> STEP7["⑦ 观察期：每日对账，保留回滚通道"]

顺序不能反：严禁先停旧系统再迁移。先迁移、先对账、后冻结、再切换。每次演练都要走完整七步。

风险控制措施

10 · 验收标准

10.1 第 1 次发布验收（销售助理体验闭环）

见 §2.4 六项体验清单；硬指标：测试账号授权 → 下单成功 → 飞书实例出现 → 新系统 PG 有 flow_id/instance_id；虹励真实下单 1–2 笔全流程通过。

10.2 第 2 次发布验收（三角色执行闭环）

见 §3.6；硬指标：商务备货、财务到款、仓管发货/回单各至少 1 笔真实订单经受信通道成功；同一 task 重复提交幂等；双通道并发一方 ALREADY。

10.3 第 3 次发布验收（切换闭环）

见 §4.5；硬指标：订单数 / 状态 / 事件链 / 附件四层对账 100% 一致；切换与回滚各演练一次；观察期 3 天每日对账无差异。

11 · 明确不做（防范围蔓延）

  • 不修旧系统任何 bug / 深链：开票财务深链、auto_approve、修改校验、回款判断、48h 升级链等，旧系统程序员职责；新系统只规避不触碰。
  • 旧系统唯一改动：仍只有两处——① 第 1 次的幂等键前缀自动确认 + V01 profile 注入；② 第 2 次的受信端点补丁（真实 operator + 幂等锁）。除此之外旧系统零代码改动。
  • 第 1 次不做：不迁移 JSONL；不做备货/发货/开票执行；自动下单继续移出；锁库存不做。
  • 第 2 次不做：不做开票盖章回传（留第 3 次）；不做财务深链；不做库存锁定。
  • 第 3 次不做：不删旧系统历史数据（只读归档）；不在切换当天改流程（流程在切换前冻结）。
  • 全期不做：不新增旧系统导出端点 / webhook / 桥接泛化；不直接写旧系统 JSONL 文件。
