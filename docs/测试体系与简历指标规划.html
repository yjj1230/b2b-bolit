五、实施路线图（按投入产出比排序）

P0 · 先让门禁变绿（半天，简历数字从"扣分"变"加分"）

  1. 补 repo 层 SQL 失败分支：workflow_outbox.go、agent_trace.go、 reconciliation.go 的 pgx scan error / 约束冲突路径，用现成的 failing_store 模式。
  2. 补 workflows 的 Timer 与补偿分支：复用 TestSuite 虚拟时间（既有 resume_test.go 范式）。
  3. 补 agentorder/policy.go 的规则矩阵：13 条 require × 4 个 DecisionStatus， 表驱动一组用例即可从 75.6% 拉到接近 100%（代价极低，收益极高）。
  4. 补 bridge/wecom 的剩余错误分支。

验收：make cover exit 0，internal ≥ 85%；目标 90%。

P1 · 新建 L5 AI 评测（1–1.5 天，产出最值钱的数字）

  1. 建 tests/testdata/intent_eval.jsonl：字段 {text, expect_sku, expect_qty, label}， 覆盖四类：明确单 SKU / 多 SKU 歧义 / 无 SKU 闲聊 / 边界（数量缺失、单位换算、协议价不一致、超信用额度）。
  2. 写 internal/wecom/eval_test.go（去掉 deferred 标签）：跑评测集，输出 Precision / Recall / F1 / 拒答准确率 / 误建单率（关键：被误判为可自动下单的无关消息数必须为 0）。
  3. 把 LLMParser 用可替换的 Complete 打桩，跑同一评测集对比 MockParser vs LLMParser —— 这直接产出「规则基线 vs LLM 提升」的对比数字，是 AI 岗简历的高价值叙事。

验收：输出一份评测报告（含混淆矩阵），指标可写进简历；误建单率必须为 0（AI 安全红线）。

P2 · 新建 L4 性能基准（1 天）

  1. internal/api/bench_test.go：BenchmarkCreateOrder / BenchmarkSignalApprove / BenchmarkShipment，走 httptest + 真 PG。
  2. 用 -benchmem 抓 allocs/op；用 scripts/concurrency 升级为吞吐压测 （固定时长，统计 QPS + P50/P95/P99）。

验收：产出延迟分布表；简历可写「订单创建 P95 = xx ms @ xx QPS」。

为什么这个顺序
P0 让已有能力变成可信数字（覆盖率是面试官最容易质疑的）； P1 填最值钱的空白（AI 指标，且工作量中小）； P2 补叙事完整性（性能是后端/应用岗的常规期待，但工作量最大且容易被追问细节）。

诚实原则（面试防守要点）
  • 覆盖率写"语句覆盖率"，别写"代码质量"；同时主动说明"覆盖率 100% ≠ 故障注入等价性 100%" —— 项目文档里已有这个诚实声明，直接沿用会加分。
  • 并发数字写清上下文（"16 并发 / 备货 100 / 30 件每次"），否则面试官会怀疑是编的。
  • AI 指标必须能说明评测集怎么来、多少条、标注标准 —— 说不清就不要写。
