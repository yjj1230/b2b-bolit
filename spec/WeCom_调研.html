0. 结论与路线选择

必须先修正的根本错误

企业微信聊天工具栏可以承载 H5 页面，也可以关联微信小程序，但它们是两套不同的开发、认证和发布链路。微信小程序的 dist/weapp 不是静态网页，不能把 pages/index/index.html 当作侧边栏 URL。

前端运行时企业微信内置 WebView微信小程序运行时

本项目决策：以 H5 自建应用作为客户联系聊天工具栏主入口。订单、备货、发货和权限规则仍由 Go BFF、Temporal、SpiceDB 与业务数据库负责；企微只提供成员身份、会话上下文和交互入口。

身份与上下文不是同一件事

OAuth 回答“当前操作人是谁”；getCurExternalContact/Chat 回答“当前会话面对谁”。两者都必须存在并在服务端重新授权。浏览器上传的 principal_id、tenant_id 或 customer_id 不能作为可信事实。

4. 企业微信管理后台配置

  1. 创建自建应用。记录 CorpID、AgentID；通过受控方式获取 Secret。Secret 只进入服务端密钥系统，禁止发送到群聊、工单正文或前端仓库。
  2. 配置应用可见范围。先限定测试成员/部门；生产灰度按白名单逐步扩大。可见范围不是业务授权，业务 API 仍需 ReBAC。
  3. 开通客户联系能力。确认测试成员具备客户联系功能；在客户联系 API 权限配置中把该应用设为可调用应用。否则上下文接口会返回 no permission。
  4. 配置可信域名。填写 H5 页面域名，完成域名归属验证。生产必须 HTTPS；官方要求可信域名有 ICP 备案。不要填写路径、协议或临时随机域名。
  5. 配置网页授权回调域。OAuth 重定向域必须与应用对应；auth/getuserinfo 使用的 access token 必须来自同一应用。
  6. 配置企业可信 IP。如管理后台要求，为调用企微服务端 API 的固定出口 IP 配置白名单。不要填开发者个人动态 IP 作为生产方案。
  7. 配置到聊天工具栏。新增页面名称“备货管理”，选择网页，填稳定 HTTPS URL，例如 https://wecom-test.example.com/sidebar。不要指向 dist/weapp。
  8. 按需配置回调。消息、审批或客户联系事件需要回调时，配置 URL、Token、EncodingAESKey；保存配置证据并验证 GET 握手与 POST 解密。
配置完成的最小证据

应用详情、可见范围、客户联系权限、可信域名、回调域、可信 IP、聊天工具栏 URL、回调验证成功页面各一份截图；同时记录 CorpID/AgentID，但对 Secret、Token、AESKey 做完整遮蔽。

4.1 URL 与域名规则

  • JS-SDK 签名 URL 必须是当前页面完整 URL 去掉 # 及其后内容；不得 URL encode 后再参与签名。
  • 页面域名必须命中应用可信域名。SPA 使用 History Router 时，每个实际 URL 都应可由服务器回落到 index.html。
  • OAuth redirect_uri 必须 URL encode；回调后校验 state，并只允许回到服务端白名单内的业务路径。
  • 不要把 Secret 放在 URL。CorpID/AgentID 不是密钥，但仍建议由服务端环境配置下发，避免跨企业参数混用。

5. H5 前端开发

5.1 使用官方新版 SDK

npm install @wecom/jssdk

import * as ww from '@wecom/jssdk'

官方当前同时提供 npm 与 CDN 方式，并明确建议旧版 jweixin-1.2.0.js 项目迁移到 ww.register。用户提供的 wecom-sidebar-jssdk 最后主要更新停留在 2021 年，可用于理解旧版封装和 Mock 思路，不应作为新项目默认依赖。

5.2 OAuth 与业务 Session

sequenceDiagram
  actor M as 企微成员
  participant H as H5
  participant B as Go BFF
  participant W as 企微 OAuth/Open API
  M->>H: 从聊天工具栏打开页面
  H->>B: GET /wecom/session
  alt 无有效业务 Session
    B-->>H: 401 + oauth_start_url
    H->>B: GET /wecom/oauth/start?return_to=/sidebar
    B-->>M: 302 到企微 OAuth（带 state）
    W-->>B: callback?code=...&state=...
    B->>W: auth/getuserinfo(access_token, code)
    W-->>B: userid
    B->>B: 绑定 principal，签发 HttpOnly Session
    B-->>H: 302 /sidebar
  end
  H->>B: GET /wecom/session
  B-->>H: 当前成员显示信息 + 能力摘要
  • 静默授权使用 snsapi_base，只在确需头像等敏感信息时使用 snsapi_privateinfo。
  • OAuth code 单次使用，官方说明 5 分钟过期。服务端必须校验 state，阻断登录 CSRF。
  • 业务 Session 推荐使用 HttpOnly; Secure; SameSite=Lax Cookie；不要把长期 Token 放进 localStorage。
  • return_to 必须是站内相对路径或严格白名单 URL，避免开放重定向。

5.3 JS-SDK 注册

import * as ww from '@wecom/jssdk'

async function fetchSignature(kind, url) {
  const response = await fetch('/api/wecom/js-sdk/sign', {
    method: 'POST',
    credentials: 'include',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ kind, url })
  })
  if (!response.ok) throw new Error('signature request failed')
  return response.json()
}

export function registerWeCom({ corpId, agentId }) {
  ww.register({
    corpId,
    agentId,
    jsApiList: [
      'getContext',
      'getCurExternalContact',
      'getCurExternalChat'
    ],
    getConfigSignature: (url) => fetchSignature('corp', url),
    getAgentConfigSignature: (url) => fetchSignature('agent', url),
    onConfigFail: (error) => reportSdkError('config', error),
    onAgentConfigFail: (error) => reportSdkError('agent_config', error)
  })
}
签名服务必须限制来源

服务端只为已登录用户、受信任 Origin 和允许的页面 URL 签名。企业 ticket 与应用 ticket 均只在后端缓存；绝不能把 ticket、access_token 或 Secret 下发前端。官方的 ww.getSignature(ticket) 仅供本地快速调试。

5.4 单聊与群聊上下文必须分流

export async function resolveEntryContext() {
  const { entry } = await ww.getContext()

  if (entry === 'single_chat_tools') {
    const { userId } = await ww.getCurExternalContact()
    return { entry, externalUserId: userId }
  }

  if (entry === 'group_chat_tools') {
    const { chatId } = await ww.getCurExternalChat()
    return { entry, chatId }
  }

  return { entry: entry || 'normal' }
}

不要在群聊里同时调用客户 ID 接口，也不要在单聊里调用客户群接口。官方入口与最低版本如下：

接口入口应用要求官方最低版本
ww.getContext所有入口，用于先判断 entry按接口要求注册企业微信 3.0.24
ww.getCurExternalContactsingle_chat_tools应用身份 + 客户联系功能权限单聊工具栏 2.8.10
ww.getCurExternalChatgroup_chat_tools应用身份 + 客户联系功能权限2.8.17

5.5 初始化应是状态机，不是定时器

推荐状态：booting → authenticating → registering_sdk → resolving_context → loading_data → ready，以及可恢复的 no_context / unmapped / forbidden / sdk_error。不要用固定 setTimeout(1000) 或 localStorage 轮询 external_userid；它会产生旧客户串话和难以复现的竞态。

5.6 首屏产品契约

  • 群聊入口：显示当前客户名称、已生效订单、备货额度与发货进度。
  • 单聊入口：显示该外部联系人所属客户及受授权数据。
  • 工作台入口：没有会话上下文，只展示“我的备货单/我的待办”，不得自动猜客户。
  • 无映射：明确提示选择客户或联系管理员，选择后仍需服务端授权。
  • 所有写操作再次授权；页面成功打开不是后续命令的授权凭证。

5.7 多模块与微前端治理

MoChat、OpenSCRM 和 2021 年的 qiankun 实践都把侧边栏、工作台、管理后台与服务端拆开。这种结构适合多个团队长期维护多个业务模块，但不是单一 Pilot 的默认起点。只有独立发布、技术栈隔离或团队边界带来的收益明确大于运行时复杂度时，才引入微前端。

  • 主壳统一负责 OAuth、业务 Session、ww.register、entry 分流、错误上报和版本诊断；子应用不得各自重复刷新 token/ticket。
  • 向子应用传最小、短生命周期的上下文视图或服务端 context handle。不要传 Secret/ticket/token，也不要把原始 SDK 对象和客户 ID 存入可持久化全局状态。
  • 每个子应用固定资源基址、路由前缀、CSP、权限清单和独立版本；发布时验证 publicPath、跨域、缓存和旧壳兼容性。
  • Hash Router 只是减少签名 URL 变化的一种工程选择，不是企微官方要求。无论 Hash 或 History，都要用真实当前 URL 验证签名，并覆盖前进、后退、刷新和深链。
  • 壳或子应用卸载时清理事件监听、请求和敏感内存状态；切换当前会话后必须重新解析上下文，禁止沿用上一客户。

6.1 推荐端点

6.2 Access Token 与两类 Ticket

凭证获取用途缓存键建议
应用 access_token/cgi-bin/gettoken?corpid&corpsecretOAuth 换身份、获取 ticket、调用业务 APIcorp_id + agent_id

正常有效期通常为 7200 秒，以返回的 expires_in 为准，并提前留安全窗口刷新。企微可能提前使 token 失效，因此收到明确的凭证失效错误时只允许一次受控刷新重试。使用 singleflight/分布式锁避免多实例同时刷新。

不要每次页面打开都取 ticket

官方对 ticket 获取有严格频率限制：一小时内每企业最多 400 次，单应用最多 100 次。必须集中缓存，并记录命中率、刷新次数和企微错误码。

6.3 签名算法

canonical =
  "jsapi_ticket=" + ticket +
  "&noncestr=" + nonce +
  "&timestamp=" + unixSeconds +
  "&url=" + pageURLWithoutFragment

signature = SHA1(canonical)

参数顺序固定，不做 URL encode。服务端分别选择企业 ticket 或应用 ticket。日志只记录 URL 的 origin/path、ticket 类型、耗时和结果，禁止记录 ticket、Secret、access_token 或完整 OAuth code。

6.4 上下文绑定与授权

  1. 从 HttpOnly Session 得到 corp_id + userid，映射内部 principal 与 tenant。
  2. 从 SDK 请求得到当前 external_userid 或 chatId，只作为“待解析上下文”。
  3. 在服务端检查该标识属于当前企业且映射有效；必要时通过企微客户/客户群 API 刷新。
  4. 解析内部 customer 后，执行 SpiceDB 关系授权与字段裁剪。
  5. 业务命令使用服务端绑定的 principal/tenant/customer，忽略客户端同名字段。

6.5 回调可靠性

  • GET 验证：按企微算法校验 msg_signature，AES 解密 echostr，校验 ReceiveID，返回解密后的明文。
  • POST 事件：校验签名后解密；先落原始事件摘要和处理状态，再执行业务。
  • 不要假设每类回调都有统一 event_id。按事件类型使用稳定业务键，例如 SpNo + status + update_time，或 payload hash + 时间桶；数据库唯一键兜底。
  • 回调快速返回，耗时工作进入队列/Outbox；失败可重试、可巡检、可人工补偿。
  • 审批状态必须支持主动查询巡检，不能把回调当唯一事实来源。

第三方 SDK 必须固定版本和校验和，检查许可证、维护频率、接口覆盖、错误码透传、缓存并发、提前失效、超时重试、回调 ReceiveID 校验及日志脱敏。项目 README 的“自动管理 token”不能替代压测、故障注入和源码审计。

7. 本地开发与真实企微联调

7.1 推荐模式：稳定测试域名 + HTTPS 反向代理

企业微信不会把 localhost 当作可信域名。推荐长期配置一个测试域名，由受控代理把请求转发到本机或共享开发环境：

企业微信聊天工具栏:
  https://wecom-test.example.com/sidebar

代理:
  https://wecom-test.example.com  ->  http://127.0.0.1:5173
  https://wecom-test.example.com/api -> http://127.0.0.1:8080

社区资料常用 Whistle、hosts 或 ngrok/frp。选择时遵循：

  • 优先 HTTPS 代理；移动端不会读取开发机 hosts，单纯 hosts 方案只适合桌面端。
  • 代理证书只安装在受控测试设备，结束后撤销系统代理和证书信任。
  • 临时穿透 URL 会变化，意味着重新配置可信域名和验证；不要暴露管理接口和调试数据。
  • 测试域与生产域使用完全不同的 Secret、Cookie 域、数据库和客户数据。

7.2 分层开发

层运行环境可验证不可替代
浏览器 Mock普通 ChromeUI、状态机、错误态、接口契约真实 SDK 注册与入口上下文
Go Fake Adapter本地服务OAuth/映射/授权/回调业务逻辑企微错误码、限流、加密差异
企微桌面端真实测试企业WebView、开发者工具、单聊/群聊入口移动端系统差异
企微移动端iOS/Android 真机真实触控、网络、相机、上传和返回行为桌面端布局与缓存

7.3 联调顺序

  1. 先让普通浏览器 Mock 路径通过，不调用真实 SDK。
  2. 验证 OAuth start/callback、业务 Cookie 与 CSRF 防护。
  3. 验证企业签名和应用签名端点，确保 URL、ticket 类型与 AgentID 对齐。
  4. 在企微工作台入口验证 entry=normal 的安全降级。
  5. 在客户单聊工具栏验证 external_userid。
  6. 在客户群工具栏验证 chatId。
  7. 验证无权限成员、无映射客户、被撤销关系和旧页面返回。

7.4 代理环境退出检查

社区的 Whistle 方案能把稳定测试域代理到本机，但 HTTPS 解密依赖本机代理与受信任 CA，属于高权限调试手段：

  • 只在隔离测试设备和测试企业使用，代理规则限定测试域名，不捕获邮箱、生产 API 或其他敏感流量。
  • 联调前记录代理、证书、DNS/hosts 和企微客户端版本；更新规则后重启企微并清理 WebView 缓存再复测。
  • 联调结束后关闭系统 HTTP/HTTPS 代理，移除 Whistle CA 信任和临时 hosts/穿透规则，再验证正常网络。
  • OpenSCRM 的 ?debug=1 强制登录属于其项目自己的开发功能，不能复制为本项目的生产身份绕过入口。

8. 测试与验收

8.1 自动化测试

  • 签名黄金向量：固定 ticket/nonce/timestamp/URL，断言 SHA-1。
  • URL 变体：query 顺序、中文编码、末尾斜杠、History 路径、hash 路由。
  • Token/Ticket 缓存：并发刷新、提前失效、45009 限流、超时与单次重试。
  • OAuth：state 不匹配、code 重放、回调域错误、开放重定向。
  • 上下文：single/group/normal/unsupported；缺映射、跨 corp、关系撤销。
  • 回调：签名错误、密文篡改、ReceiveID 不匹配、重复投递、乱序和处理崩溃恢复。

9. H5 发布、灰度与回滚

H5 不走微信小程序审核

H5 的发布对象是 Web 资产和 BFF。微信公众平台的“上传代码 → 体验版 → 审核 → 发布”只适用于微信小程序路线。

  1. 构建不可变产物。记录 commit、依赖锁文件、构建时间和前端版本；静态文件使用内容 hash。
  2. 部署测试环境。跑健康检查、OAuth smoke、签名黄金向量和真实企微测试群 UAT。
  3. 生产预热。确认 access token/ticket 缓存、DNS/TLS、域名验证文件和服务端出口 IP。
  4. 灰度。通过服务端 Feature Flag、用户白名单或新 URL 灰度，不在客户端硬编码企业名单。
  5. 观察。比较 OAuth 成功率、SDK 注册失败率、上下文成功率、首屏 p95、403 和企微 errcode。
  6. 全量或回滚。回滚 Web 版本与 API 兼容层；数据库变更使用向前兼容迁移，避免前端回滚后不可用。

若修改聊天工具栏 URL，保留旧 URL 的兼容重定向或维护页，直到所有客户端缓存和入口配置确认更新。重定向不得丢失 OAuth state，也不得跳到未签名域名。

10.2 应急顺序

  1. 判断是入口配置、Web 资产、OAuth、SDK、上下文、授权还是业务 API。
  2. 按 trace_id 串联前端、BFF、企微 API 和业务流程日志。
  3. 安全失败优先：无法确认身份/上下文时拒绝写操作，不降级为全租户数据。
  4. 企微限流/不可达时使用有界退避和熔断；不要无限重试。
  5. 必要时切只读模式或维护页；恢复后执行审批、回调和业务状态对账。

10.3 密钥轮换

不要假设企微所有 Secret 都支持新旧值并行。轮换前先确认管理后台对该凭证的实际能力：

  1. 盘点 Secret、回调 Token、EncodingAESKey、Cookie 签名密钥和内部 API 密钥的消费者。
  2. 对支持双 key 的内部密钥先部署“读新旧、写新”；对企微单值凭证准备短时切换窗口。
  3. 更新 KMS/Secret Manager，滚动重启，验证 token/ticket 刷新和回调。
  4. 撤销旧密钥，检查日志和仓库泄漏，保存轮换证据。

10.4 退役

  • 先将聊天工具栏切换为只读告知页，再撤入口和可见范围。
  • 撤销客户联系 API 权限、可信 IP、回调 URL 和应用 Secret。
  • 清理 token/ticket 缓存、会话 Cookie、测试成员与测试群。
  • 按数据保留策略删除 external_userid/chatId 映射；保留必要审计与审批记录。
  • 归档最终配置、版本、数据处置证明和 Owner 签字。

13. 微信小程序备选路线

只有在明确选择微信小程序运行时后，才使用以下流程：

  1. 在微信公众平台注册小程序，获得 AppID。
  2. 用微信开发者工具和企微插件开发；企微专有能力使用 wx.qy.*。
  3. 调用 wx.qy.login 获取 5 分钟 code；服务端使用关联应用的 access token 调用企微 jscode2session。
  4. 开发者工具上传；配置企微体验版成员；完成真机测试。
  5. 提交小程序审核、发布并关联到企业微信；配置页面路径而不是 HTML URL。
小程序路线仍需独立解决可信上下文

Taro 的 Taro.login() 不能替代客户群上下文获取。必须在真实企微入口调用对应 wx.qy.getContext/getCurExternalChat/getCurExternalContact，并由服务端绑定成员身份、客户上下文和业务授权。
