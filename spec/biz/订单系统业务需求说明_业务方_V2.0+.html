一、版本说明及与V1.0的区别

V2.0+是当前有效的完整业务需求版本，在V2.0基础上继续补充发货数据承接、分批回单和客户订单统一查询需求。产品设计和技术评估应以V2.0+为主要依据，V1.0和V2.0仅用于追溯前期讨论过程。

二、业务目标与建设原则

新系统最终要成为一个真正服务销售和商务的订单工具：销售下单快、信息准确、进度可查、资料好找；商务能够统一接收全公司订单，掌握库存和发货，处理异常并形成完整数据。

核心目标包括：

  1. 销售能够通过合同、历史订单或人工方式快速创建订单，减少重复录入。
  2. 商务能够查看全公司订单，并从价格审批完成后统一承接合同、库存、选仓、发货、回单、开票和资料跟踪。
  3. 不同部门可以保留必要的前端审批差异，但订单必须沉淀到统一订单总表，进入统一的后续履约和数据统计体系。
  4. 库存、批号、包装、实际出库、质检单、物流、回单、发票和回款能够围绕同一笔订单关联。
  5. 系统以自动提醒、自动带出和自动汇总减少人工工作，但关键实际结果必须由责任岗位确认，不能用流程动作代替业务事实。
  6. 历史未完成订单能够继续办理，新旧系统切换不能造成订单、附件和责任人断层。
业务说明：核心原则：订单提交不等于已履约，出库单发给仓库不等于已发货，发票上传不等于已推送，只有实际业务结果被确认后，系统状态才可以变化。

三、业务范围和整体流程

3.1 订单主流程

  1. 客户通过合同、微信、邮件、标准申请单或客户系统提出需求。
  2. 销售本人或销售代办人创建订单。
  3. 系统自动带出历史信息并检查明显异常。
  4. 销售总监审核价格。
  5. 商务接收订单，核对订单依据、数量、交期和发货要求。
  6. 商务查询库存、在途和预计到仓情况，选择一个或多个仓库。
  7. 仓库确认任务、批号和实际可发数量，完成实际出库及发货。
  8. 系统记录实际发货数量、物流、批号、质检单、实际运费和签收情况。
  9. 按正常回单路径或经批准的无回单例外路径发起开票。
  10. 财务开票，发票自动关联订单并通知销售。
  11. 财务登记回款，销售查看并跟进客户，盖章合同等资料完成归档。
  12. 发货、开票、回款及必要资料满足关闭条件后，订单闭环。

3.2 与订单并行的供应和费用流程

  • 仓库调货和区域仓备货：根据未发订单、未来预计需求、现有库存、在途库存和历史发货情况安排。
  • 批次质检资料：杨源向区域仓发货形成在途批次时，系统提醒质检部门上传对应质检单。
  • 运费及仓储费：仓库按月提供回单原件和费用明细，商务核对后向财务办理报销。
  • 管理报表：以实际发货数据为准，按客户、销售、产品、部门、仓库和时间自动汇总。

3.3 订单状态

新系统至少应区分草稿、待价格审批、审批退回、待商务处理、待分配仓库、待仓库确认、待发货、部分发货、已发货、待回单、待开票确认、开票处理中、部分开票、已开票、部分回款、已回款、已完成、已取消和异常状态。

整单状态应根据产品明细、仓库任务、发货批次、开票和回款的实际结果自动汇总，不能由某一个节点被点击后直接跳成完成状态。

五、订单来源与统一订单总表

5.1 当前订单来源

  • 销售或代办人在现有审批中下单；
  • 客户正式合同；
  • 客户微信或微信群消息；
  • 邮件及标准Word发货申请；
  • 客户自有系统下载的订单或合同；
  • 造纸、油田、农药等其他部门的独立审批；
  • 历史订单再次发起。

大型客户可能要求销售或商务同时在客户自有系统中确认订单、下载文件、反馈发货和处理发票。新系统应记录需要完成的外部系统事项和办理状态，避免公司内部订单完成但客户系统遗漏操作。

客户下单前要求的报价单应作为独立业务资料或前置任务处理，可以使用模板生成，但不能把报价单直接当成正式订单。

5.2 统一承接要求

其他部门当前使用不同的独立审批，并不代表这些订单不由商务处理。订单审批完成后，商务仍需制作出库单、通知发货、跟进资料并进行数据汇总。

新系统应做到：

  1. 不同业务可以使用不同的下单表单或审批规则。
  2. 审批完成后形成统一的标准订单记录和唯一订单编号。
  3. 所有订单进入同一套商务、库存、仓库、发货、回单、开票和回款处理体系。
  4. 所有订单进入统一订单总表，不能继续分散在各部门独立数据表中。
  5. 保留订单来源、所属部门、原审批编号和原始附件，便于追溯。
  6. 数据汇总不再要求商务到多个审批表和邮件中逐笔查找。

六、销售下单及查询需求

6.1 下单角色

系统同时支持销售本人下单和销售助理代下单，并记录实际创建人、归属销售、代办关系、创建时间和修改记录。代办关系应可配置，不能将人员姓名写死。

6.2 下单方式

  • 合同下单：上传合同后提取客户、供方、合同编号、产品、数量、价格、地址、账期、包装和交期，生成草稿供销售确认。
  • 文件下单：上传邮件Word订单、标准申请单或客户系统文件后生成草稿。
  • 老客户再次下单：选择历史订单复制内容，仅修改本次变化的信息。
  • 人工下单：保留完整人工填写能力。销售可以输入产品库中暂时没有的产品型号，首次下单提交后自动补充到产品库，后续订单可以直接选择。新型号应保留首次录入来源，并进入后台待核对清单，由产品数据维护人员检查是否属于已有型号、别名或确需新增的产品，避免重复型号长期累积。

6.3 客户历史信息自动带出

选择客户后，系统应根据客户、产品和交易主体组合带出：

  • 常用交易供方；
  • 账期；
  • 常购产品和最近成交价格；
  • 多个收货地址及联系人；
  • 包装类型；
  • 发货要求和历史备注。

销售下单页面以简单、清晰为主，不要求自动展开历史订单记录或历史发货仓库。历史信息只能作为建议值，销售可以根据本次客户需求修改，并由系统突出显示与历史明显不同的字段。

6.4 订单核心字段

  • 客户标准名称；
  • 订单归属销售、创建人和所属部门；
  • 交易供方主体、账期、是否需要开票；
  • 合同编号及订单来源；
  • 客户原始产品名称、产品型号、数量、单价和金额；
  • 包装类型；
  • 收货地址、联系人和联系电话；
  • 要求到货日期；
  • 发货及特殊要求；
  • 原始合同、订单文件或其他下单依据。

6.5 提交前自动检查

系统应对交易主体、价格、数量、日期、地址、包装、账期和短期重复订单进行检查。与历史习惯差异较大时标红提醒销售确认，但在没有明确禁止规则时不应直接阻断提交。

6.6 销售最关心的信息

销售应在一个订单页面中直接查看：

  • 审批是否通过及退回原因；
  • 盖章合同及客户回传合同；
  • 当前发货仓库和仓库变化；
  • 各仓可用库存及在途预计到仓时间；
  • 计划发货、实际发货和剩余未发数量；
  • 发货时间、物流信息和预计到货时间；
  • 质检单及需要的产品资料；
  • 回单、开票和发票文件；
  • 回款状态。

销售以手机使用为主，合同、质检单和发票必须能够快速查看、下载和再次转发。

七、价格审批及销售向商务交接

  1. 销售正式提交订单后，由销售总监审核价格。
  2. 审批退回或拒绝时必须填写原因，并明确告诉销售如何处理。
  3. 订单退回修改后，需要重新提交相应审批，确保价格和订单信息重新审核。
  4. 只有价格审批完成后，订单才进入商务节点。
  5. 商务不能直接覆盖销售提交的客户需求、价格和数量。发现问题时，应通过退回、评论或订单变更流程通知销售处理。
  6. 订单进入商务前，客户、产品、数量、地址、交期、包装和特殊要求应完整。未填写额外要求时，商务按常规方式处理。

八、商务订单处理需求

8.1 商务数据权限

商务部承担全公司订单统筹职责，必须查看全公司全部订单，而不是只查看本人创建、本人经办或少数销售的订单。

商务需要查看价格、金额、账期、合同、库存、出库、物流、回单、质检单、开票、发票、回款和费用数据，并按客户、销售、部门、产品、仓库、日期、状态及异常类型查询。

8.2 商务收到订单后的处理顺序

  1. 查看销售总监审批结果和完整订单依据。
  2. 核对客户、供方、产品、数量、交期、地址、包装和特殊要求。
  3. 判断合同和随货资料是否齐全。
  4. 查看各仓现有库存、可用库存、已占用库存和在途库存。
  5. 系统在商务选择仓库时展示该客户及相关产品的历史发货仓库，并结合成本、距离、交期、当前库存和在途库存给出建议仓库，由商务人工审核无误后确认一个或多个仓库。
  6. 按产品明细和数量分配仓库，生成仓库待办。
  7. 跟踪仓库确认、实际出库、批号、物流和预计到货时间。
  8. 跟踪分批发货后的剩余未发数量，处理缺货、换仓和调货。
  9. 跟踪质检单、回单和其他订单资料。
  10. 根据业务规则衔接开票、发票推送、回款及合同归档。
  11. 处理异常并形成可供管理层查看的数据。

目前成都、东莞等仓库的部分订单还需要商务下载出库单、在仓库系统中进行预出库、将出库单发送到工作群，再根据实际批号查找质检单。新系统应将这些动作形成可追踪任务；暂时无法直接对接仓库系统时，也必须记录预出库、资料发送和仓库确认状态。

8.3 商务工作台

商务每天需要集中查看：

  • 已录入但尚未分配销售的化百道客户线索；
  • 今日新进入商务的订单；
  • 尚未选择仓库的订单；
  • 仓库未确认的订单；
  • 今日实际发货明细；
  • 已下单未发货、部分发货和剩余未发订单；
  • 库存不足和在途延迟订单；
  • 长时间未发货或疑似漏发订单；
  • 缺批号、缺质检单、缺回单订单；
  • 待开票、部分开票和开票异常订单；
  • 已开票未推送、已开票未回款订单；
  • 待核对运费、回单原件和报销事项；
  • 其他部门进入统一履约流程的订单。

8.4 化百道客户线索录入及分配

商务部还承担化百道客户线索的录入工作。目前商务从微信群收到客户线索后，需要人工录入飞书线索表单；表单提交后自动推送给销售总监，由销售总监分配销售人员，再自动推送给对应销售。该工作虽然发生在正式下单之前，但会影响后续销售跟进、客户归属和订单来源，也属于商务实际工作量。

当前流程为：

业务说明：微信群收到化百道客户线索 → 商务人工整理并录入飞书线索表单 → 自动推送销售总监 → 销售总监分配销售员 → 自动推送对应销售员

新系统应支持：

  1. 商务新增化百道客户线索，并保留微信群原始消息、截图或附件。
  2. 线索至少记录客户或公司名称、联系人、联系方式、地区、产品需求、线索来源、收到时间、备注和录入人。
  3. 提交后自动生成销售总监待分配任务，不再依赖商务另行提醒。
  4. 销售总监选择负责销售后，系统自动更新线索负责人并通知对应销售。
  5. 销售收到线索后可以确认接收，并记录联系、有效、无效、持续跟进或已转客户等状态。
  6. 商务能够查看线索是否已分配、由谁负责和当前处理状态，但不需要反复人工询问销售。
  7. 对相同公司、联系人或联系电话进行重复线索提醒，避免多次录入和重复分配。
  8. 有效线索后续转为正式客户或形成订单时，应保留原线索来源和负责人关系，便于统计化百道线索的转化结果。

九、多仓库、分批发货及节点转交

9.1 多仓库和产品明细分配

  1. 商务选择仓库时支持多选。
  2. 每条产品明细可以指定发货仓库和分配数量。
  3. 同一产品的数据结构应支持拆分到多个仓库，是否在第一阶段开放由业务确认。
  4. 系统按仓库生成独立待办，每个仓库只处理分配给本仓的明细。
  5. 各仓分别记录实际发货数量、批号、物流、运费和状态。
  6. 整单汇总各仓计划量、累计已发量和剩余未发量。

9.2 分批发货

每次发货必须作为独立发货批次记录：

  • 原订单数量；
  • 本次计划发货量；
  • 本次实际发货量；
  • 累计已发量；
  • 剩余未发量；
  • 发货仓库、库存批号和包装；
  • 实际发货时间、物流信息和预计到货时间；
  • 实际运费；
  • 回单及开票关联状态。

第一次发货后，订单不能被直接标记为全部完成。系统应继续形成剩余未发任务和提醒。

9.3 办理人和仓库转交

  • 当前办理人可以将任务转交给具备权限的人员；
  • 原仓库无法发货时，仓管可发起转交给其他仓库人员；
  • 转交前应确认新仓库可以承接，必要时由商务确认；
  • 转交必须填写原因并记录原办理人、新办理人、时间和仓库变化；
  • 新办理人立即收到完整待办，原办理人的待办关闭；
  • 转交不得重复创建订单或重复占用库存。

十、库存、批号及在途管理

10.1 库存表最小必备字段

库存必须至少按“仓库＋产品型号＋批号＋包装类型”管理，并具备以下必填字段：

字段业务要求
产品型号保留实际库存产品型号，并能够关联标准统计产品
批号每批库存和实际发货必须能够识别批号，用于关联质检单
包装类型不同包装不能只汇总成一个库存数量
数量记录当前实际数量，库存扣减以实际出库为准

系统还应计算或记录仓库、可用库存、已占用库存、在途数量、预计入库时间、最后更新时间和数据责任人。

10.2 成都仓库当前风险

目前成都仓库库存表没有批号，不能提供按批次拆分的库存；库存表提供不及时；商务无法准确知道仓库是否已经实际发货，通常在出库单交给仓库后就默认订单已经发出，实际存在漏发订单但商务未及时发现的风险。

新系统必须解决：

  1. 成都仓库入库和出库均记录批号、包装和实际数量。
  2. 库存长时间未更新时提醒仓管和商务。
  3. 出库单发送只能代表“待仓库办理”，不能自动代表“已发货”。
  4. 仓管必须确认实际发货数量、批号、时间和物流信息后，订单才能变为已发货。
  5. 超过计划发货时间仍未确认时，进入疑似漏发或超时异常清单。

10.3 库存实时变化规则

  • 订单分配仓库后，根据确认规则占用库存；
  • 仓库实际发货后，按实际出库数量扣减库存；
  • 订单取消、换仓或减少数量时，释放未实际出库的占用库存；
  • 仓库调货发出后，调出仓减少可用库存并形成在途库存；
  • 调入仓签收后，在途库存转为实际库存；
  • 任何负库存、批号缺失、库存长期未更新、账实差异或在途超期应形成异常提醒。

10.4 低库存及库存异常提醒

系统应支持按仓库和产品设置安全库存或最低库存提醒，并提示：

  • 当前可用库存低于安全值；
  • 已有未发订单但库存不足；
  • 在途库存无法满足预计交期；
  • 某批次数量异常或即将用完；
  • 同一批号包装信息冲突；
  • 调货或入库超过预计时间未签收；
  • 库存表超过规定时间未更新。

十一、仓库备货及仓间调货

11.1 当前决策方式

成都、东莞等区域仓的备货和仓库之间调货，目前主要由宋主任根据以下情况决定：

  • 已下单但尚未发货的订单；
  • 销售预计的未来订单需求；
  • 各仓现有库存和在途库存；
  • 固定区域销售的客户需求；
  • 每月持续发货的老客户和大客户需求；
  • 历史实际发货台账。

东莞仓主要服务广东区域的固定销售及客户，成都仓主要服务四川区域，长兴仓主要服务浙江一带。该对应关系应支持后台配置，不应写死在程序中。

杨源向区域仓补货通常按整车安排，每车约33至34吨。该数据可作为备货和运输组合的参考参数，但应允许根据实际情况调整。

11.2 新系统备货建议能力

系统应综合以下数据形成备货参考，而不是直接代替负责人作最终决定：

  1. 当前实际库存、可用库存和在途库存。
  2. 已确认订单的剩余未发数量及交期。
  3. 销售填报的未来预计需求。
  4. 各区域、销售、客户和产品的历史实际发货量。
  5. 固定老客户、大客户的周期性需求。
  6. 安全库存和整车装载参考。

商务或负责人确认备货计划后，系统生成仓间调货或补货任务，并跟踪调出、在途、签收和入库全过程。

十二、实际发货、物流和漏发防控

12.1 发货确认

仓库只有完成以下信息后，发货任务才可标记为已发货：

  • 实际发货产品和数量；
  • 发货批号；
  • 包装类型；
  • 实际发货时间；
  • 物流或司机信息；
  • 预计到货时间；
  • 实际运费或后补状态；
  • 出库单及需要的随货资料。

12.2 防止漏发

  • 出库单已生成但仓库未确认发货的订单持续显示为待发货；
  • 到达计划发货时间仍未确认时自动提醒仓管和商务；
  • 商务工作台单独显示“已通知仓库但未确认发货”的订单；
  • 销售只在仓库完成实际发货确认后收到发货通知；
  • 订单撤回或紧急取消时，仓库、物流调度和相关人员收到强提醒并停止后续操作。

12.3 现有发货文件自动识别系统的承接

目前商务登记发货情况使用的是部署在服务器上的系统。工作人员在微信群上传出库单或相关文件后，服务器按照既定逻辑自动识别并提取数据，再汇总上传到飞书。这项能力已经减少了商务手工登记工作，新系统应优先承接和复用，不应无依据地全部重做。

新系统需要补齐的是订单关联，而不仅是继续生成一张发货数据表：

  1. 每条自动提取的发货记录必须关联订单编号、订单产品明细和发货批次编号。
  2. 同一订单分多次发货时，每次识别结果分别生成一条发货批次记录。
  3. 保存微信群原始文件、识别结果、数据来源、上传时间、识别时间和后续人工修改记录。
  4. 通过订单号、客户、产品、仓库、数量和发货日期等信息自动匹配订单。
  5. 自动匹配结果需要设置匹配状态，包括已匹配、待确认、匹配失败和疑似重复。
  6. 无法准确匹配时进入“待匹配发货记录”清单，由商务选择对应订单及产品明细后确认，不能形成与订单无关的孤立数据。
  7. 同一文件重复上传或同一发货记录重复推送时，应识别并提示，避免重复扣减库存和重复统计发货量。
  8. 现有系统向飞书同步的数据，应逐步调整为向新系统统一订单中心同步，或通过明确的数据接口保持一致。
业务说明：业务要求：自动识别是否成功和订单是否完成履约是两件事。只有发货记录与具体订单及发货批次正确关联，并由仓库确认实际结果后，才能更新订单发货状态。

十三、运费、纸质回单及仓储费报销

商务部目前还负责两个仓库的运费报销和回单原件整理。仓库每月将上月全部纸质回单原件寄给商务，商务需要按日期整理分类，并将回单与仓库提供的运费明细表逐笔核对。核对无误后，再向财务办理运输费和仓储费报销。

13.1 每次发货需要记录的费用信息

  • 关联订单和发货批次；
  • 发货仓库；
  • 物流公司、车辆或司机；
  • 发货日期和到货日期；
  • 发货数量；
  • 实际运费；
  • 仓储费或其他费用；
  • 电子回单状态；
  • 纸质回单原件是否收到；
  • 费用明细是否核对；
  • 报销申请及财务处理状态。

13.2 月度核对需求

系统应按仓库和月份自动形成费用核对清单，支持：

  1. 将仓库运费明细与系统实际发货记录进行匹配。
  2. 标识缺少订单、金额不一致、数量不一致、重复收费和缺少回单原件等异常。
  3. 按日期、订单和仓库整理回单原件目录。
  4. 汇总当月运输费和仓储费。
  5. 记录商务核对人、核对时间、报销提交时间和财务处理结果。

实际运费应作为订单履约成本数据保留，后续可按客户、产品、销售、地区和仓库分析。

十四、批号、质检单及产品资料

  1. 质检单必须按实际发货批号匹配，建立“产品型号—批号—质检单—发货批次”的关系。
  2. 杨源向成都、东莞或其他仓库发货形成新在途批次时，系统应提醒质检部门上传对应质检单。
  3. 新批次未上传质检单时，形成待办和异常提醒。
  4. 仓库确认实际发货批号后，系统自动检索并关联对应质检单。
  5. 批次库存全部发完后，质检单从当前待办中退出，但仍需长期归档，供历史订单查询。
  6. MSDS、TDS等非每单必需资料进入产品资料库，销售按需查找和发送。

十五、回单、开票、发票和回款

15.1 回单

电子回单和纸质回单原件需要分别记录。电子回单用于签收、开票和异常判断，纸质原件用于月度费用核对和财务资料整理。

回单无法及时取得时，不能让订单无限期卡在开票前。系统应支持：

  • 有回单正常开票；
  • 无回单例外开票申请；
  • 填写原因并关联实际出库、物流、客户要求及销售商务确认等依据；
  • 开票后继续补回单；
  • 查询无回单已开票订单。

具体替代材料、审批人、金额和客户范围由财务及管理层确认，技术实现不能写死为必须上传回单。

15.2 分批发货的回单上传规则

回单不能只绑定整张订单，应绑定到每一次实际发货批次。一笔订单分三次发货，就应形成三条发货批次记录，并分别上传、核对和跟踪对应回单。

每次上传回单时，应关联或确认：

  • 客户和订单编号；
  • 发货批次编号；
  • 发货仓库和实际发货日期；
  • 本次发货产品及实际发货数量；
  • 客户实际签收数量；
  • 回单文件；
  • 是否存在少收、拒收、破包或损耗；
  • 电子回单状态；
  • 纸质回单原件状态；
  • 上传人、上传时间和核对人。

系统可以根据客户、产品、数量、仓库和日期自动推荐对应的发货批次，但最终需要上传人员确认。无法准确匹配时，回单进入“待匹配回单”清单，不得直接挂在客户名下或错误关联整张订单。

一个发货批次应允许上传多份文件，以支持回单正反面、多页回单、多个收货地点、后补清晰扫描件以及月底收到的纸质原件。补充、替换或作废回单必须保留版本记录。

订单层面自动汇总：

  • 订单总数量；
  • 累计实际发货数量；
  • 已取得回单的数量；
  • 尚未取得回单的数量；
  • 存在签收差异的数量；
  • 回单总体状态。

回单总体状态至少包括未上传、部分回单、已上传待核对、全部回单、数量存在差异、无回单例外申请中、无回单已批准开票和后补回单完成。

开票判断应以发货批次对应的实际签收数量或经过批准的例外数量为依据，不能因为整张订单中上传过一张回单，就默认所有分批发货都已取得回单。

15.3 开票申请

当前自动生成的开票申请仍可能出现不需要开票却生成任务、应开票订单遗漏、数量金额错误、可合并订单被拆开以及开票品名不准确等问题，大量判断依赖宋主任个人经验。新系统上线前需要将这些经验整理为可确认、可维护的业务规则。

  • 区分需要开票、无需开票和特殊开票业务；
  • 支持部分发货、分次开票和经批准的先开票业务；
  • 支持同公司、同产品、同单价等符合规则的多订单合并开票；
  • 发票和订单支持一对多、多对一关系；
  • 开票品名通过标准产品及财务规则映射，减少依赖个人经验；
  • 开票数量不得超过实际签收数量、实际发货数量或例外批准数量。

15.4 发票推送

  • 出纳上传发票后自动触发匹配和通知；
  • 优先通过订单号、合同号、客户和开票信息关联；
  • 无法匹配的发票进入异常清单；
  • 发票自动推送当前归属销售，不再依赖商务逐张点击；
  • 订单页面长期保留发票查看、下载和再次发送入口；
  • 客户负责人调整后，后续发票接收人同步更新并保留变更记录。

15.5 回款

  • 财务负责回款登记和应收管理；
  • 销售负责客户催款并直接查看自己客户的回款状态；
  • 商务可以查看全公司订单的回款结果，但不应承担大量人工查询和转发；
  • 已开票未回款、部分回款和逾期订单形成待跟进清单。

十六、合同及订单资料闭环

  • 合同上传后与具体订单关联，不仅按客户归档；
  • 支持系统生成合同、公司盖章合同和客户回传盖章合同三个版本；
  • 销售能够在手机端查看和下载盖章合同；
  • 部分订单先发货后补合同，系统需要继续跟踪客户回传；
  • 出库单、质检单、回单、发票及必要产品资料均在订单页面统一查找；
  • 订单关闭条件中应包含哪些合同和资料，由业务按订单类型配置。

十七、客户档案、产品名称清洗及统计口径

17.1 客户档案及负责人

客户档案需要通过系统内部唯一标识解决客户名称重复问题，但业务人员下单时不需要填写或查看客户编号。同时解决负责人缺失、新老客户状态不准确和销售离职后无人交接的问题。

客户档案至少包括：

  • 客户标准名称、曾用名称和开票名称；
  • 当前归属销售、历史负责人及交接记录；
  • 多个收货地址、联系人及联系电话；
  • 开票资料、开票要求和账期；
  • 常用交易供方；
  • 常购产品、历史价格、包装及发货习惯；
  • 历史订单、合同、发票和回款记录；
  • 客户等级及其维护依据。

新客户首次下单时应沉淀完整档案，后续订单自动复用。销售离职或客户转交时，应通过标准交接流程同步更新客户负责人、未完成订单权限、待办任务和发票接收人，并保留历史记录。

客户资料的新增、合并、负责人转交和等级调整需要明确维护责任人，不能长期依赖销售个人口头通知商务。

17.2 客户全景查询及订单资料绑定

目前同一客户的信息分散在审批、邮件、微信群、服务器发货系统、飞书多维表、财务表和文件资料中。即使能够找到客户名称，也无法快速判断某份合同、出库单、回单或发票具体属于哪一笔订单，商务需要跨多个平台反复查找和核对。

新系统应建立以下业务关系：

业务说明：客户 → 订单 → 订单产品明细 → 发货批次 → 出库单、批号、质检单、物流、实际运费及回单 → 开票申请及发票 → 回款记录

资料必须按实际业务归属进行绑定：

  • 客户基本资料、联系人、地址、账期和历史习惯归属于客户档案；
  • 客户下单文件、销售订单、合同及价格审批归属于具体订单；
  • 出库单、实际批号、质检单、物流、运费和回单归属于具体发货批次；
  • 发票作为独立记录关联一笔或多笔订单及对应开票数量；
  • 回款记录关联客户、发票和相关订单，并允许处理一笔回款对应多笔订单的情况。

系统应提供客户全景页面。选择一个客户后，能够集中查看：

  • 客户基本资料、当前销售和历史负责人；
  • 联系人、多个收货地址、开票资料、账期和交易主体；
  • 全部订单及当前状态；
  • 未发货、部分发货和已发货情况；
  • 每次发货对应的仓库、批号、物流、运费和回单；
  • 合同、出库单、质检单和其他资料；
  • 已开票、未开票及发票下载入口；
  • 已回款、未回款、部分回款和逾期情况；
  • 当前异常和需要处理的事项。

客户全景页面是统一查询入口，但不能将所有资料只挂在客户名称下。用户从客户页面进入后，必须能够继续定位到具体订单和具体发货批次。

系统还应支持按客户名称、订单编号、合同编号、原审批编号、发货批次、产品、发票号码和销售人员进行统一搜索，减少商务在多个平台之间查找信息。

当前发货记录保留的是销售下单时填写的原始产品名称，可能包含品牌名、产品全称、简称、客户叫法或不同型号写法。业务执行时必须保留原始名称，但经营分析时需要汇总到标准产品型号。

17.3 产品数据结构

  • 销售原始产品名称；
  • 客户使用的产品名称；
  • 品牌名；
  • 产品全称；
  • 产品简称或别名；
  • 实际产品型号；
  • 标准统计产品型号；
  • 产品类别、应用领域和所属部门；
  • 开票品名；
  • 标准包装类型。

17.4 产品型号对应表

系统需要维护产品名称及型号映射表，将多个销售名称映射为同一标准统计产品。订单和发货记录保留原始名称，报表默认按标准产品汇总，同时允许追溯原始订单写法。

无法匹配的新名称进入待清洗清单，由明确的数据维护人员确认，不能由系统自行错误合并。

十八、数据汇总及管理报表

目前发货数据来自多个订单入口和数据表，单价还可能保存在邮件或附件中。商务在登记和分析时需要到多个地方查找，并人工将不同产品名称归并为同一型号，工作量较大。

新系统应基于统一订单总表和实际发货批次自动形成：

  • 最近5日及当月实际发货数量；
  • 已下单未发货、部分发货和剩余未发数量；
  • 按客户、销售、部门、仓库、区域和产品统计；
  • 原始产品名称和标准产品型号双口径查询；
  • 含税、不含税金额及单价；
  • 实际运费、仓储费和履约成本；
  • 已开票、未开票、已回款和未回款数据；
  • 回单、质检单、合同和发票缺失情况；
  • 超时、漏发、库存不足和其他异常订单。

管理报表应以实际发货结果为主要口径，同时保留订单数量和剩余未发数量，避免把已下单误认为已实现销售。

二十、权限、通知及状态要求

20.1 权限原则

  • 销售查看自己负责的客户和订单，并可查看价格、合同、发货、发票和回款状态；
  • 代办人查看授权销售范围；
  • 商务查看全公司全部订单及履约信息；
  • 仓库只查看本仓任务所需的客户、地址、产品、数量、包装和发货要求，不查看价格和金额；
  • 质检查看相关产品和批次；
  • 财务查看开票、费用、应收和回款所需信息；
  • 管理层查看全公司数据和例外事项；
  • 所有修改、撤回、转交、换仓、例外开票和数据清洗均保留日志。

20.2 关键通知

  • 销售：价格通过或退回、到账、仓库确定或变化、超时未发、实际发货、开票待确认、发票已开和回款到账；
  • 商务：新订单进入、仓库未确认、发货超时、库存不足、批号或资料缺失、回单超时、发票匹配失败和费用核对异常；
  • 仓库：新发货任务、订单变更或取消、任务转交、在途到仓待签收；
  • 质检：新在途或入库批次需要上传质检单；
  • 财务：开票申请、例外开票、费用报销、发票异常和回款待登记。

通知应能跳转到具体订单或任务，并显示需要办理的事项，不能只有笼统消息。

二十一、历史数据及新旧系统切换

21.1 老系统处理原则

老系统在新系统正式切换前继续支持正常下单，只处理影响业务继续运行的必要维护，不再承担新功能建设。

21.2 历史订单范围

新系统必须考虑来自现有审批、其他部门审批、邮件台账和独立数据表中的未完成订单，包括：

  • 未发货或部分发货；
  • 已通知仓库但未确认发货；
  • 未回单；
  • 未开票或部分开票；
  • 已开票未回款或部分回款；
  • 缺少合同、质检单、回单或发票；
  • 正在办理费用核对和报销。

21.3 切换要求

  • 保留原订单号、原审批编号、来源部门和附件；
  • 明确每笔订单的当前状态和剩余事项；
  • 明确归属销售、当前商务负责人和仓库任务；
  • 防止同一订单从多个数据表重复迁移；
  • 新旧系统并行期间明确唯一录入位置和数据截止时间；
  • 历史未完成订单在新系统中可以继续发货、开票、回款和补资料，不能只作为只读记录。

二十二、新系统建设顺序

这里的优先级是新系统建设顺序，不再是老系统问题修复顺序。

第一阶段：测试环境完整主链路

先在测试环境搭建并确认所有必要角色、权限、字段、状态和节点：

业务说明：销售/代办创建订单 → 自动检查 → 销售总监价格审批 → 商务接单 → 多仓分配 → 仓库确认和转交 → 实际出库 → 回单或例外 → 开票 → 发票 → 回款 → 合同及资料归档 → 订单关闭

同时让其他部门订单能够进入统一订单总表。第一阶段重点是流程完整、责任明确、数据可以从头走到尾。

第二阶段：库存和发货可信

  • 库存按产品型号、批号、包装和数量管理；
  • 实际入库、占用、出库和在途联动；
  • 多仓、分批、换仓和转交；
  • 发货必须由仓库确认，建立漏发和超时提醒；
  • 批号与质检单自动关联。

第三阶段：回单、开票、发票和回款闭环

  • 正常回单和无回单例外；
  • 部分、合并和特殊开票；
  • 发票自动关联和推送；
  • 销售直接查看回款；
  • 合同及订单资料归档。

第四阶段：商务效率及经营数据

  • 商务工作台；
  • 化百道客户线索录入、分配和处理状态跟踪；
  • 仓库备货和调货参考；
  • 运费、纸质回单及仓储费月度核对；
  • 产品型号映射和数据清洗；
  • 自动形成发货、销售、费用、开票和回款报表。

第五阶段：进一步自动化

  • 合同和订单文件智能提取；
  • 历史习惯智能带出和异常识别；
  • 备货建议和库存预测；
  • 质检数据自动生成标准质检单；
  • 在业务规则稳定后评估与大客户外部系统的数据对接。

二十三、仍需确认的业务规则

  1. 同一产品在第一阶段是否开放拆分到多个仓库。
  2. 各仓库存更新时限、责任人及盘点频率。
  3. 成都仓批号数据如何补齐，历史库存按什么时间点初始化。
  4. 仓库发货确认的必填信息和超时标准。
  5. 仓间调货、区域仓备货的发起人、确认人和审批规则。
  6. 各仓库安全库存和低库存阈值如何设定。
  7. 新在途批次质检单由哪个岗位负责上传，缺失时是否允许发货。
  8. 两个需要商务办理运费报销的具体仓库、费用项目及财务所需附件。
  9. 无回单开票的替代依据、审批人、金额和客户范围。
  10. 不开票、合并开票、先开票及开票品名的具体财务规则。
  11. 产品型号对应表由谁维护，新产品和新别名如何审核。
  12. 各特殊部门在新系统中的前端审批差异和统一字段范围。
  13. 历史数据迁移范围、核对责任人和正式切换时间。

二十四、业务验收重点

  • 销售和代办人能够快速创建正确归属的订单；
  • 产品库不存在的新型号能够首次录入并自动补入，后续订单可以直接选择；
  • 销售总监价格审批稳定执行，退回原因清楚；
  • 化百道客户线索提交后能够自动流转给销售总监分配，并推送对应销售；
  • 商务可以查看和管理全公司及各部门订单；
  • 所有来源订单能够进入统一订单总表；
  • 多个产品能够分配到多个仓库并生成独立任务；
  • 库存按产品型号、批号、包装和数量准确查询；
  • 出库单发送后不会被错误标记为已发货；
  • 仓库确认实际数量和批号后才扣减库存并通知销售；
  • 分批发货后能够持续跟踪剩余未发数量；
  • 服务器自动识别的发货记录能够正确关联订单、产品明细和发货批次；
  • 自动匹配失败和疑似重复的发货数据能够进入人工处理清单；
  • 在途、调货、签收和区域仓入库能够形成闭环；
  • 新批次能够提醒质检上传并自动关联质检单；
  • 运费、回单原件、仓储费和报销能够按订单及月份核对；
  • 无回单订单能够按批准规则申请开票；
  • 分批发货的回单能够分别上传并汇总为部分回单或全部回单；
  • 发票能够正确关联、推送并长期查询；
  • 销售能够直接查看合同、发货、发票和回款；
  • 商务能够从客户全景页面定位到具体订单、发货批次和相关资料；
  • 原始产品名称能够保留，管理报表能够按标准型号汇总；
  • 历史未完成订单能够在新系统继续办理；
  • 异常、转交、撤回、换仓和关键修改均有完整记录。

二十五、最终目标

新系统最终应形成以下完整业务闭环：

业务说明：化百道客户线索录入与销售分配 → 多来源订单统一承接 → 销售快速下单 → 自动校验 → 价格审批 → 商务统一接单 → 库存及在途查询 → 多仓分配 → 仓库真实发货确认 → 批号与质检单关联 → 物流及回单管理 → 开票及发票推送 → 回款跟踪 → 合同归档 → 费用核对及经营分析

通过统一订单、库存、批次、发货和财务相关数据，减少销售重复填写，减少商务跨表查找、人工催办、人工转发和人工汇总，同时降低价格错误、库存失真、订单漏发、批号缺失、回单卡票、发票遗漏及统计口径不一致等风险。
