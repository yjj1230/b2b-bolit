销售订单业财 POC：业务流程及需求拆解 V1.1

文档定位：基于《飞书三方审批 销售订单业财流程 POC 流程说明》，从业务方视角说明销售订单主流程及 ORD、STK、SHP、INV 四个环节。每个环节先明确新系统应达到的核心目标，再展示分支流程、角色和信息，最后将业务流程问题、组织执行问题、产品优化问题放回对应环节，说明现状、建议方案和优先级。
使用对象：老板及业务负责人、管理层、产品经理、技术开发团队、销售、商务、仓库和财务相关人员。
版本说明：V1.1 根据业务方反馈调整文档结构，删除已明确或不需要讨论的问题，不再将流程图与问题分类分开呈现。

一、问题分类及责任边界

本文仍将问题区分为三类，但不再单独集中罗列，而是放在四个业务环节中分别说明。

分类 判断标准 主要处理责任 产品技术边界
业务流程问题 流程缺失、现有流程不适应真实业务，或例外、变更规则尚未定义 老板、业务负责人、财务或相关部门负责人拍板 规则确认后才能固化，技术不能代替业务决定
组织执行问题 流程和责任方向基本明确，但受内部执行、外部协作、信息回传时效等影响 管理层明确执行要求、协作方式、时限及异常升级 产品可提醒、留痕和展示异常，不能消除所有外部客观时差
产品优化问题 业务流程基本明确，但页面、权限、状态、通知、附件、数据关联或自动化不能有效支撑 产品经理和技术团队 根据业务目标设计方案，并由业务按真实场景验收

优先级定义：

优先级 含义 处理原则
P0 主链路无法正确走通，可能造成错单、错发、重复办理、开票回款被卡或状态失真 完整 POC 验收和新系统上线前必须解决
P1 主流程可以运行，但存在明显人工工作量、查询困难、跨部门等待或高频异常 主链路稳定后优先建设
P2 进一步提升自动化、体验和管理分析 基础流程和数据稳定后实施

二、销售订单业务主流程

当前 POC 以一个主流程编号串联四个审批环节，不是四套互相独立的流程：

  1. ORD 销售订单创建审批：订单发起、信息确认、主管审批，产出正式合同。
  2. STK 备货审批：根据销售下单时填写的账期或结算方式，进入相应的备货、到款确认和选仓流程，产出出库单。
  3. SHP 发货审批：仓库办理发货、记录本批发货信息、处理回单及开票信息；分批发货时，剩余数量进入下一批备货和发货。
  4. INV 开票审批：根据正常回单或经批准的例外依据形成开票处理，关联发票并完成后续资料办理。

    B -->|审批通过并形成正式合同| C[STK 备货审批]
    C -->|确定发货仓并生成出库单| D[SHP 发货审批]
    D -->|本批发货完成| E{是否还有剩余未发数量}
    E -->|有| C
    E -->|无| F{回单或例外依据是否满足}
    F -->|满足| G[INV 开票审批]
    F -->|暂不满足| H[继续跟踪回单或补充例外材料]
    H --> F
    G --> I[发票关联与销售查询]
    I --> J[资料办理完成并归档]

2.2 四个环节总览

环节 业务起点 核心办理内容 环节主要产出 下一步
ORD 销售员或代办人提交订单 信息确认、主管审批、合同处理 审批通过的销售订单、正式合同 进入 STK
STK ORD 完成 按账期判断节点、确认到款、商务选仓 发货仓、仓库任务、出库单 进入 SHP
SHP STK 完成 仓库发货、分批、实际发货信息、回单及开票信息 发货批次、剩余未发量、回单或例外材料 返回 STK 或进入 INV
INV SHP 满足开票条件 开票申请、无票办理、真实开票、发票关联及资料办理 开票结果、发票附件及相关资料 后续归档

三、ORD 销售订单创建审批

3.1 本环节核心目标

即使没有任何现有系统，新系统在 ORD 环节也应做到：

  1. 支持销售员本人和授权代办人快速创建订单，准确记录实际提交人和归属销售。
  2. 一次性收集后续商务、仓库和财务真正需要的订单信息及附件，避免重复询问和线下转发。
  3. 保证信息确认、主管审批、退回、修改和再次提交的流程状态真实、不可重复推进。
  4. 审批通过后形成可供销售下载、商务查看和后续环节使用的正式合同。
  5. 销售能够通过订单看板快速查看自己的订单、产品、数量、发货状态、合同和发票。

3.3 涉及角色及需要的信息

角色 本环节职责 需要查看或填写的信息
销售员 确认客户真实需求、订单归属及后续跟进 下单日期、客户名称、产品名称、数量、价格、账期、地址、包装、交期、特殊要求、合同或下单依据
销售代办人 根据授权替指定销售创建订单 与销售相同的订单字段，并明确实际创建人和归属销售
销售主管 审核订单及价格信息 客户、产品、数量、单价、金额、账期、合同和审批意见
商务 在 ORD 通过后承接完整订单 客户、产品、数量、价格、账期、地址、交期、包装、特殊发货要求及全部相关附件

3.4 当前问题、建议方案及优先级

ORD-01｜业务流程问题｜退回、撤回、修改和再次提交的边界｜P0
  • 当前 POC：节点拒绝后当前阶段终止，提交人可以基于原数据修改后再次提交；订单进入后续阶段后支持整单撤销或作废，历史记录和附件不删除。
  • 现存问题：订单进入不同阶段后，哪些字段仍可修改、修改后从哪个节点重新审批、已经生成的合同如何处理，需要按环节形成明确规则。
  • 建议方案：在 ORD 明确客户、产品、数量、价格、账期、地址、交期等核心字段的修改范围；核心字段变化后重新进入相应审批；旧合同和旧审批记录保留但标记失效。
  • 验收标准：撤回或退回后不会出现旧待办继续推进、旧合同仍被当作有效合同或重复生成订单。
ORD-02｜组织执行问题｜客户、销售归属和产品等基础数据需要持续维护｜P1
  • 当前情况：客户负责人变化、代办关系、产品新增或名称变化会直接影响订单归属和后续发票推送。
  • 现存问题：如果基础数据没有及时更新，系统会按照错误数据正确执行，最终仍产生错误结果。
  • 建议方案：明确客户负责人交接、代办授权、产品新增和产品名称核对的责任岗位；系统保留变更记录和待维护清单。
  • 产品边界：产品可以提供权限、日志和提醒，不能自行判断现实中客户应归属哪位销售。
ORD-03｜产品优化问题｜销售订单创建和订单看板设计｜P1
  • 销售创建订单目标：页面简单、信息清晰，支持合同或文件生成草稿、历史信息建议、历史订单再次发起和人工填写。
  • 订单看板最少展示：
    • 下单日期；
    • 客户名称；
    • 产品名称或型号；
    • 数量；
    • 发货状态或当前办理节点。
  • 筛选建议：客户名称、月份或时间范围、发货状态、开票情况。
  • 附件入口：盖章合同可从订单行或详情页直接点开、下载；发票开具后，可从同一订单直接点开、下载。
  • 设计原则：销售进入看板首先是快速找到订单并判断是否已发货、是否已开票，而不是展示大量审批技术字段或仅展示订单金额。
  • 验收标准：销售可以在手机端通过客户或时间快速找到订单，直接看到产品和数量，并在少量操作内下载合同和发票。
ORD-04｜产品优化问题｜当前处理人、task_id 和旧待办防重复｜P0
  • 当前 POC 基础：系统通过当前 task_id、当前处理人和节点状态校验是否可以办理。
  • 需要保证：非当前处理人只读；已办理任务和旧链接只读；重复点击不重复创建订单或跳过后续节点；退回后新任务与旧任务明确区分。
  • 验收标准：多角色、多次点击、刷新、撤回重提和旧链接访问均不会造成审批跳过或重复流转。

3.5 ORD 需求优先级汇总

优先级 需求
P0 修改重提规则；任务与处理人校验；旧待办防重复；核心附件向后续环节传递
P1 销售快速下单；销售订单看板；合同和发票直接下载；基础数据维护提醒
P2 合同及订单文件智能识别、历史异常智能提醒

四、STK 备货审批

4.1 本环节核心目标

新系统在 STK 环节应做到：

  1. 根据销售下单时填写的账期或结算方式，自动进入正确的备货和到款确认节点。
  2. 让商务能够在一个页面查看订单产品、数量、交期、地址、包装、库存和在途信息，准确选择发货仓库。
  3. 支持一笔订单多个产品分配给不同仓库，并为各仓库生成明确、独立的发货任务。
  4. 商务确认仓库后生成正确的出库单，并将合同编号、产品、数量和发货要求传入 SHP。
  5. 分批发货仍有剩余数量时，能够继续形成下一批备货任务，但不重复计算主订单金额和数量。

4.2 STK 分支流程图

flowchart TD

    B -->|款到发货| C[财务确认到款]
    B -->|账期或其他已明确方式| D[进入商务选仓]
    C --> D
    D --> E[商务查看产品、数量、库存和在途]
    E --> F{是否需要多个仓库}
    F -->|否| G[选择单一发货仓]
    F -->|是| H[按产品明细和数量分配仓库]
    G --> I[生成仓库任务和出库单]
    H --> I
    I --> J[进入 SHP 发货审批]

4.3 涉及角色及需要的信息

角色 本环节职责 需要查看或填写的信息
销售员/代办人 在 ORD 下单时准确填写账期、交期和发货要求 账期、是否款到发货、要求到货时间、地址和特殊要求
财务 对款到发货订单确认实际到款 客户、订单、应到金额、实际到款和确认结果
商务 核对订单、查看库存和在途、确认发货仓 客户、合同、产品、数量、包装、交期、各仓库存、在途、历史仓库和发货要求
仓库 接收分配到本仓的下一步任务 本仓负责的产品明细和数量，不在 STK 环节查看价格与金额

4.4 当前问题、建议方案及优先级

STK-01｜业务流程问题｜多仓、分批和主订单之间的数据关系｜P0
  • 当前 POC：商务填写发货仓后生成出库单；分批发货有剩余数量时返回 STK。
  • 现存问题：一个订单多个产品可能需要多个仓库；分批返回 STK 时如果直接形成新的独立订单，可能导致数量、金额和报表重复。
  • 建议方案：保留一个主订单，STK 按仓库和批次生成子任务；主订单持续汇总订单总量、各仓分配量、累计已发量和剩余未发量。
  • 需要确认：同一产品首期是否允许拆分给多个仓库。
  • 验收标准：多仓和分批后主订单金额不重复，各仓任务和剩余数量均准确可追溯。
STK-02｜组织执行问题｜到款确认需要及时反映真实到账结果｜P1
  • 业务规则：款到发货订单需要财务确认到款；账期等其他明确业务按对应路径处理。
  • 现存问题：规则本身明确，但实际到账后如果节点未及时更新，会增加销售和商务等待时间。
  • 建议方案：明确到款确认的办理时限和替岗方式；系统对长时间未办理事项提醒财务和相关管理人员。
  • 验收标准：真实到账后能在规定时间内完成确认，销售和商务看到一致状态。
STK-03｜组织执行问题｜商务选仓依赖各仓库存及时准确维护｜P0
  • 当前情况：商务选择仓库需要依赖阳原、长兴、东莞、成都四个仓库的库存数据。
  • 现存问题：如果库存缺少产品型号、批号、包装或数量，或长期不更新，商务无法准确判断该仓是否有货和何时可发。
  • 建议方案：明确各仓库存维护人员、更新时限和盘点机制；系统展示库存最后更新时间和责任人，超时进入异常清单。
  • 验收标准：商务选仓时可以判断每个仓库实际库存、可用库存和数据新鲜度。
STK-04｜产品优化问题｜多仓库及产品明细分仓｜P0
  • 现存问题：单一发货仓字段无法支撑多个产品由不同仓库发货，容易出现截图后在微信群额外通知其他仓管的情况。
  • 建议方案：商务选择仓库时支持多选；每条产品明细指定发货仓库和数量；各仓分别生成待办和出库信息。
  • 验收标准：一笔订单的多个产品可以准确分配给阳原、长兴、东莞或成都，各仓只看到并办理本仓明细。
STK-05｜产品优化问题｜库存、在途和建议仓库集中展示｜P1
  • 商务需要查看：实际库存、可用库存、已占用库存、在途数量、预计到仓时间、数据更新时间。
  • 建议方案：选仓页面集中展示四个仓库信息，并结合客户地区、历史发货仓库、库存、在途和交期给出建议仓库，最终由商务确认。
  • 验收标准：商务无需跨多个库存表和微信记录查询，即可完成选仓判断。

4.5 STK 需求优先级汇总

优先级 需求
P0 主订单与多仓、分批关系；产品明细分仓；各仓任务独立；库存基础数据可信
P1 到款超时提醒；库存和在途集中展示；历史仓库与建议仓库
P2 备货建议、库存预测和仓间调货建议

五、SHP 发货审批

5.1 本环节核心目标

新系统在 SHP 环节应做到：

  1. 仓管只看到完成发货所需的信息，不能看到订单单价和金额，但必须看到合同编号。
  2. 仓库能够清楚知道本仓需要发什么产品、多少数量、什么包装、发往哪里及有哪些特殊要求。
  3. 每次实际发货形成独立发货批次，分批后持续保留剩余未发任务。
  4. 支持仓库或办理人无法继续办理时进行有原因、有记录、有通知的转交或换仓。
  5. 真实反映回单由外部司机或相关外部人员回传所产生的时间差，不能因为回单暂时未取得而让所有订单永久卡在开票前。
  6. 发货、回单和开票衔接围绕同一发货批次进行，保证实际发货量、签收量和可开票量可以追溯。

5.4 当前问题、建议方案及优先级

SHP-01｜业务流程问题｜回单存在客观回传时差，需要正常与例外两条开票路径｜P0
  • 真实业务场景：货物送达后，回单由外部司机、物流人员或相关外部人员先取得，再回传给公司内部仓管或业务人员。外部人员无法保证立即回传，因此存在客观时间差。
  • 问题性质：不是内部责任不清，也不是简单要求某个内部岗位及时上传就能解决；如果系统坚持“只有上传回单才能开票”，会因外部回传时差影响开票和回款。
  • 建议方案：
    1. 有回单时，按正常路径核对签收量并进入开票；
    2. 回单暂未回传但客户确已收货时，允许按财务和管理层确认的替代依据发起无回单例外开票；
    3. 明确例外申请人、审批人、可用材料、客户或金额范围；
    4. 开票后继续保留后补回单任务。
  • 验收标准：系统既不取消回单管理，也不会让符合例外条件的订单长期卡住。
SHP-02｜业务流程问题｜订单变更、撤回、取消和发货后处理规则｜P0
  • 当前 POC：支持撤回、拒绝和整单撤销或作废。
  • 现存问题：仓库收到任务后，销售如果修改地址、数量、发货要求或撤回订单，需要明确是否停止发货、是否重新选仓、是否释放任务以及通知哪些人员。
  • 建议方案：按“仓库未接单、已接单未发货、部分发货、全部发货”分别定义变更方式；涉及发货的重要变化向仓库、商务和销售强提醒并保留日志。
  • 验收标准：被撤回或取消的订单不会继续发货，已部分发货订单保留真实已发记录。
SHP-03｜组织执行/外部协作问题｜回单回传时效受外部人员影响｜P0
  • 当前情况：公司内部可以催促和跟踪，但回单首先掌握在外部司机、物流或相关外部人员手中，无法保证实时回传。
  • 现存影响：内部仓管或商务收到回单的时间不确定，造成回单状态、开票时间和客户实收数据存在延迟。
  • 建议方案：按仓库和物流方式记录预计回单时限；超过时限自动提醒内部跟进人；无法及时取得时进入例外开票判断，而不是将问题描述为“内部责任不清”。
  • 产品边界：系统可以提醒、记录和提供例外路径，但无法强制外部司机实时传回资料。
SHP-04｜产品优化问题｜分批发货、剩余任务和转交｜P0
  • 建议方案：每次发货形成独立批次，记录原订单数量、本次计划量、本次实际量、累计已发量、剩余量、仓库、批号、包装、物流和发货时间。
  • 转交要求：当前仓库无法发货时，可以填写原因后转交具备权限的仓库或办理人；商务和销售收到仓库变化通知；原待办关闭，新待办生效。
  • 验收标准：第一次部分发货后不会把整单标记完成，转交不会重复创建订单或重复计算数量。
SHP-05｜产品优化问题｜仓管页面的信息与权限设计｜P0
  • 必须展示：
    • 客户或公司基础名称；
    • 合同编号；
    • 收货地址、联系人和联系电话；
    • 产品名称或型号；
    • 数量；
    • 包装类型；
    • 要求发货或到货时间；
    • 发货要求、特殊备注；
    • 出库单及需要随货的附件。
  • 不得展示：产品单价、订单金额。
  • 页面目标：仓管进入页面后可以直接判断“给谁发、发什么、发多少、送到哪里、有什么要求”，不需要再向商务索要订单信息。
  • 验收标准：仓管账号无法查看价格和金额，但可以看到合同编号及完成发货所需的全部信息。
SHP-06｜产品优化问题｜回单按发货批次关联｜P0
  • 现存问题：一笔订单可能多仓或分批发货，回单如果只挂在整张订单下，无法判断对应哪次发货和可开票数量。
  • 建议方案：回单绑定具体发货批次；一个批次支持多份回单文件、补充扫描件和版本记录；记录本次实际签收量和签收差异。
  • 验收标准：任何回单都能追溯到订单、仓库、本次发货量和实际签收量。

5.5 SHP 需求优先级汇总

优先级 需求
P0 回单正常/例外路径；分批发货；剩余任务；转交换仓；撤回强提醒；仓管权限和信息；回单按批次关联
P1 回单超时跟踪；物流信息；预计到货；销售发货通知；发货异常工作台
P2 物流状态自动对接、自动识别回单和签收差异

六、INV 开票审批

6.1 本环节核心目标

新系统在 INV 环节应做到：

  1. 正确承接有回单正常开票和经批准的无回单例外开票。
  2. 区分“开票申请已生成或已抄送”和“财务已经真实开票”，不能将通知动作当作完成结果。
  3. 支持无需开票、合并开票、分批或部分开票等已经确认的业务规则。
  4. 发票开出后正确关联订单，自动通知当前销售或授权代管人。
  5. 销售能够从订单看板或订单详情直接查看和下载发票。

    B -->|有回单| C[按实际签收信息生成开票申请]
    B -->|无回单但例外批准| D[按批准数量和材料生成开票申请]
    B -->|无需开票| E[无票销售办理]

    G -->|失败或信息有误| I[进入开票异常处理]
    H --> J[推送当前销售或代管人]
    J --> K[销售查看、下载和发送发票]
    E --> L[进入后续资料办理]
    K --> L

6.3 涉及角色及需要的信息

角色 本环节职责 需要查看或填写的信息
销售员/提交人 确认客户开票要求，必要时发起无回单例外 客户、开票主体、产品、数量、金额、合同编号、开票要求和例外依据
商务 查看全公司开票状态、处理匹配异常并衔接订单资料 订单、发货批次、回单、签收量、开票申请和发票状态
财务/出纳 根据有效开票申请实际开票并上传结果 客户开票资料、产品或开票品名、数量、金额、合同编号、回单或批准的例外依据
销售主管/管理层 按业务规则处理例外或特殊事项 无回单原因、替代材料、订单和客户风险信息

6.4 当前问题、建议方案及优先级

INV-01｜业务流程问题｜开票申请抄送不等于真实开票完成｜P0
  • 当前 POC：需要开票时生成开票申请抄送，抄送人不承担审批推进动作。
  • 现存问题：如果系统只知道申请已抄送，不知道财务是否已接收、已开票或开票失败，INV 状态就无法反映真实结果。
  • 建议方案：明确财务实际办理或结果回传节点；状态至少区分待开票、开票处理中、已开票、开票失败和无需开票。
  • 验收标准：只有财务确认或真实发票上传并关联成功后，订单才能显示已开票。
INV-02｜业务流程问题｜合并、部分、无票和开票品名规则需要书面化｜P0
  • 当前 POC：支持同客户合并开票和无票销售办理。
  • 现存问题：能够合并的客户、产品、单价、主体、税率和时间范围，以及分批开票和开票品名规则，需要由财务和业务负责人统一确认。
  • 建议方案：形成可维护规则表；系统按照规则推荐，特殊情况由有权限人员确认并保留原因。
  • 验收标准：系统生成的开票建议与财务规则一致，异常和人工调整可追溯。
INV-03｜组织执行问题｜客户负责人变化及发票代管关系需要及时维护｜P1
  • 当前情况：销售离职、客户转交或存在发票代管人时，发票实际接收人可能与历史订单归属人不同。
  • 现存问题：如果人员关系没有同步更新，发票可能推送给错误人员或无人处理。
  • 建议方案：销售管理者通过正式交接维护当前客户负责人和发票代管人；系统保留历史人员和变更记录。
  • 验收标准：后续发票自动发送给当前有效销售或代管人，历史订单仍可追溯原负责人。
INV-04｜产品优化问题｜真实开票状态、发票关联和销售下载｜P1
  • 建议方案：发票优先按订单号、合同编号、客户和开票信息匹配订单；匹配失败进入异常清单；匹配成功后自动通知当前销售或代管人。
  • 销售使用要求：销售订单看板显示开票情况；发票附件可以从订单直接点开和下载，后续仍能快速找到并再次发送。
  • 验收标准：发票上传不等于已推送；系统能够区分匹配、推送和销售可查询状态。

6.5 INV 需求优先级汇总

优先级 需求
P0 回单例外规则承接；真实开票完成证据；合并、部分、无票及品名规则
P1 发票自动匹配；当前销售或代管人推送；订单中直接查看下载；开票异常清单
P2 更复杂的自动合并建议、财务规则智能检查和应收分析

七、跨四个环节的共同要求

7.1 主流程与子流程状态

  • 一个主流程编号串联 ORD、STK、SHP、INV。
  • 主流程状态由四个环节以及真实业务结果汇总，不能因为某个待办被点击就直接完成。
  • 订单、备货、发货批次、回单、开票记录和发票之间必须可以互相追溯。
  • 多维表用于管理查看，但不能单独作为业务状态的唯一判断依据。

7.2 权限原则

角色 权限原则
销售员 查看本人客户和订单，可查看价格、合同、发货、开票和发票
代办人 查看授权销售范围，并区分实际提交人和归属销售
商务 查看全公司订单及完整履约信息
仓管 只查看本仓任务及完成发货所需信息；不查看单价和金额；必须查看合同编号
财务 查看开票和到款所需客户、产品、金额、合同及相关依据
管理层 查看全公司流程、异常和规则执行情况

7.3 附件归属

  • 系统合同、客户合同及下单依据归属于具体订单。
  • 出库单、实际发货信息和回单归属于具体仓库任务或发货批次。
  • 开票申请和发票归属于具体开票记录，并关联一笔或多笔订单。
  • 销售能够从订单直接找到合同和发票；仓管能够从本仓任务找到出库单和随货资料。

7.4 通知和日志

  • 通知必须说明发生了什么、由谁办理、是否需要立即处理，并跳转到具体订单或任务。
  • 撤回、拒绝、再次提交、转交、换仓、回单例外和关键字段修改必须保留操作日志。
  • 旧待办关闭后不得继续推进；同步异常不能改变真实业务记录。

八、建议给开发团队的任务顺序

8.1 P0：完整走通并保证正确性

  1. 主订单与 ORD、STK、SHP、INV 四个环节的状态关系。
  2. 当前处理人、task_id、旧待办只读和重复提交防护。
  3. 退回、撤回、修改、重提和整单作废规则。
  4. 多仓及产品明细分配。
  5. 发货批次、分批、剩余未发数量、转交和换仓。
  6. 仓管页面信息及价格、金额权限隔离。
  7. 回单按批次关联以及正常/例外开票路径。
  8. 区分开票申请和真实开票结果。
  9. 仓库办理人员可以将当前发货任务转交给具备权限的其他仓库办理人员；转交时必须填写原因，记录原办理人、新办理人和转交时间，通知商务及相关人员，并关闭原办理人的旧待办，避免重复办理。

8.2 P1：提升销售、商务、仓库和财务效率

  1. 销售快速下单和订单看板。
  2. 合同和发票从订单直接查看、下载。
  3. 库存、在途和建议仓库集中展示。
  4. 商务全公司订单和异常工作台。
  5. 回单超时跟踪和开票异常处理。
  6. 发票自动匹配及当前销售或代管人推送。
  7. 权限、通知、附件和操作日志完善。

8.3 P2：进一步自动化

  1. 合同及订单文件自动提取。
  2. 历史订单信息自动带出和异常识别。
  3. 备货建议、库存预测和仓间调货建议。
  4. 自动识别回单、物流状态和签收差异。
  5. 产品名称映射及经营分析。

九、单个问题的补充模板

后续从销售、商务、仓库和财务访谈中发现的新问题，应直接补充到对应 ORD、STK、SHP 或 INV 环节，不再单独放入脱离流程的问题清单。

[环节-编号]｜[问题类型]｜[问题名称]｜[优先级]
  • 业务场景：什么角色在什么情况下处理什么订单。
  • 当前流程：该环节现在如何流转。
  • 当前操作：实际线上或线下如何办理。
  • 问题描述：具体问题和发生条件。
  • 业务影响：影响下单、交付、库存、开票、回款、资料还是数据。
  • 建议方案：业务希望新系统达到的结果。
  • 需要确认或责任人：谁拍板规则或负责执行。
  • 优先级及理由：P0/P1/P2。
  • 验收标准：用什么真实业务结果判断完成。

十、文档目标

阅读者首先看到一条完整的销售订单主线，再进入 ORD、STK、SHP、INV 四个环节。每个环节都能连续看到：

核心目标 → 分支流程图 → 涉及角色和信息 → 当前业务问题 → 问题类型 → 建议方案 → 优先级 → 验收标准

通过这种结构，老板和业务负责人可以先处理必须拍板的业务流程问题，管理层可以明确组织执行要求，产品和技术团队可以直接识别真正需要开发的功能及前置条件，避免流程、管理和产品需求混在一起造成理解割裂和重复返工。
