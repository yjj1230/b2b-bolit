A Design Philosophy · 一门设计哲学

Code Graph Engineering —— 以代码为图，以图为镜

一门指导如何用代码描述业务、如何用图谱加速理解的设计哲学。它的立场只有一句话：业务是一张图——代码是这张图唯一可执行、可验证、可溯源的文本形式；图工具（code-review-graph）把代码重新显式成图，让业务理解从"读代码"变成"查图"。而这一切——建模、抽取、验证、协作——每一步都遵循 Graph Engineering。

📚 方法：Graph Engineering（知识图谱 × 任务图） 🧭 案例：晚餐 · 订单 · 代码自身 🛠️ 工具：code-review-graph ⏱️ 阅读：6 分钟
"Prompt engineers steered the model's words. Loop engineers steered its iterations. Graph engineers steer its topology." — codejunkie99/graph-engineering。本哲学把这句话落到工程实处：拓扑，就是你的业务如何被代码结构化，以及图工具如何把这种结构还给你。

00 为什么需要一门哲学

三个症状，一个诊断。

📋 症状一

业务不可执行

业务事实散在文档、会议、Excel 里。它们被"阅读"，而不是被"运行"——没人能验证它对不对。

🧩 症状二

代码不可理解

代码写出来了，但拓扑是隐式的：新人要两周才画出调用关系，老代码没人敢动。

🕸️ 症状三

工具缺方法论

图工具很强大，但"什么时候建图、建什么图、怎么验证"——没有哲学来回答。

🎯 处方

一门哲学

先问"业务以什么结构存在"，再写代码；让工具把结构显式化；让理解变成可查询的动作。

💡 三件事，一个根因 业务不可执行、代码不可理解、工具缺方法论——看似三件事，其实是同一件事：缺少一门关于"结构"的哲学。Graph Engineering 正是这门哲学：它不问"模型说什么"，而问"智能体穿越什么结构"。在本哲学的语境里，结构就是：业务如何被代码表达，代码如何被图工具显式化。

01 核心命题：业务是图，代码是图的文本形式

三个命题，层层递进，构成整个哲学的骨架。

  1. 业务的本质是关系结构。任何业务都可以分解为实体、关系与约束——客户与订单、模块与依赖、规则与边界。这就是一张图：节点是实体，边是关系，约束是边上的规则。业务理解，就是读懂这张图。
  2. 代码是这张图唯一可执行的文本形式。类型 = 实体，函数签名 = 关系声明，调用与数据流 = 关系实例，类型系统 = 约束。编译与测试是机器对这张图的验证——文档会被误读，代码不会：它要么跑，要么不跑。
  3. 图工具把代码的拓扑显式化。code-review-graph 用解析器确定性抽取节点与边，用符号解析做融合，用图查询提供服务。业务理解从"人肉读代码"变成"机器查图"——快一个数量级，且每一条边都有出处。

💡 为什么是代码，而不是文档或流程图？ 因为只有代码同时具备四种性质：可执行（跑起来验证）、可验证（编译与测试）、可溯源（git 记录了每一步）、可机器读取（解析器零歧义）。文档只满足"可读"，表格只满足"可查"——它们描述的图无法被机器验证，也无法被图工具抽取。

02 半边一 · 知识图谱：类型即本体

知识图谱最贵的一步是本体建模。好消息：它早就在你的代码库里——叫架构设计。

在知识图谱工程里，本体（schema）决定一切：实体类型、关系类型、约束、一致性。本哲学的主张是：代码世界的本体建模早已存在，它叫架构设计。类型系统就是本体；函数签名就是关系的 domain/range 声明；编译器就是一致性检查器。差别只有一个：知识图谱工程师手写 ontology.yaml，代码工程师用类型与接口声明同一件事——前者只给机器看，后者给机器和人一起看。

能力问题：本体与需求的公共语言

知识图谱方法论要求先写 10–20 个能力问题（competency questions）作为本体的规格与测试。本哲学把它原样搬进代码：先写"这个业务必须回答的问题"，再定模块边界，再写类型；测试用例就是能力问题的机器化。能力问题不通过，是本体设计错了，而不是代码写错了——这个归因顺序，能省掉大量返工。

02.1 · 9 阶段流水线的代码版

知识图谱工程有一条完整的 9 阶段施工流水线。本哲学逐阶段给出代码世界的对应物，并标出"谁来做"——你会发现，后半条流水线已经可以被工具接管：

#图谱工程阶段代码世界的对应谁来做
1Scope 范围划定仓库边界；写下能力问题清单人（架构师）
2Representation 表示选语言与模块组织；决定状态与事件如何编码人
3Ontology 本体类型系统、接口、领域模型（最持久，最不能省）人
4Entities 实体类、函数、文件——解析器确定性抽取，不烧 LLM、不幻觉code-review-graph
5Relations 关系调用、继承、导入、数据流——每条边都来自真实代码code-review-graph
6Events 事件事件处理器、消息订阅、回调code-review-graph
7Quality Gate 质量闸门编译、测试、lint、CI——按模块独立设卡，带数字说话CI + 人
8Fusion 融合符号解析去重；重构合并重复实现（可回滚：git）工具 + 重构
9Serve 服务图查询：flows / communities / impact radius / knowledge gapscode-review-graph
⚠️ 三个死因（图谱工程课程结论的代码版转译） ① 没有本体就开抽 → 代码版：没有架构就开写，满图 Concept/Thing 节点 = 一坨无法归类的工具类；② 跳过融合 → 复制粘贴的重复实现、同名异义，多跳查询在重复实体边界自信地答错；③ 跳过质量闸门 → 没有 CI，规模一大精度就崩。课程结论原样成立：不许跳过 3 本体与 8 融合——对应代码世界：架构评审与重构，一天都不能省。

03 半边二 · 任务图：开发即执行

知识图谱管"记住什么"，任务图管"怎么干"。开发一个业务系统本身，就是一个任务图。

任务图是 DAG——节点是任务，边是执行依赖。从规划、实现、评审、合并到发布，软件开发处处是依赖与闸门。Graph Engineering 的四条规则不是抽象理论，它们是工程实践的镜子：

规则图谱语境工程实践
① 删除假边只有当工作真的流过，箭头才是真的死代码、隐式耦合、虚假依赖是假边——删掉它们，模块才能并行
② 菱形模式拆分 → 并行工人 → 独立验证 → 单一负责人合并拆分任务 → 并行实现 → 独立评审（reviewer 不看实现者草稿）→ 单负责人合并
③ 停止规则只在"互不读对方结果"的碎片上并行只并行真正独立的模块；顺序依赖的活（A→B→C 数据链）硬拆必输
④ 人类闸门人是一个节点，不是旁观者合并请求、发布、回滚——只在错误代价昂贵的边上设闸

💡 停止规则有实验证据 Google DeepMind × MIT 的 180 组受控配置：可拆分工作上，团队胜率约 80%；而每一个多智能体配置在顺序任务上都输（退化 39–70%）。工程同理：更多人手不是策略，工作的形状才是——先画任务图，再决定哪里并行。判断标准就一句：这两件事会不会互相等？不会，才一起干。

04 组合拳：code × 图工具 × 哲学

三件套，各司其职，构成一个自洽的闭环。

本哲学最终收敛为一套组合拳。三者不是并列的工具，而是同一哲学的三个落点：

✍️ 落点一 · 写

code —— 业务的本体与事实

类型是实体，签名是关系，测试是能力问题。代码是这张图的书写——它同时写给机器（可执行）和人（可读）。

🔍 落点二 · 读

code-review-graph —— 抽取、融合、服务

解析器确定性建图，符号解析融合，图查询回答业务问题。它是这张图的阅读器——把隐式拓扑变成可查询的显式结构。

🧭 落点三 · 法

graph engineering —— 全过程的设计哲学

先建模后抽取、先融合后存储、每阶段验证、任务图四规则。它规定这张图的法——什么时候建、建什么、怎么验证。

💡 为什么这套组合拳可靠：抽取是确定性的 图里的每一条边都来自真实代码——解析器不幻觉、不编造、不猜测。LLM 只出现在最后一层：把图查询结果组织成自然语言。可溯源，因为边就是代码；可验证，因为代码会编译、会测试。这正是知识图谱工程"每条事实带溯源"铁律的免费实现——源头是代码，溯源就是代码本身。

05.1 · 案例一 · 晚餐：Graph 与 Task Graph 的分野

四个客人（一个花生过敏、一个素食、一个不吃辣）、四道菜、若干食材与厨具、一个死线（19:00 开饭）。同一批对象，两张图——左边回答"世界是什么样"，右边回答"活怎么干完"：

💡 两张图合体的瞬间 Graph 里"花生过敏客人 → 必须避开 → 花生酱"这条珊瑚红虚线，直接在 Task Graph 里生成"检查过敏原"这个琥珀色人闸门；"烤蔬菜需要烤箱"生成"预热烤箱"并建立前置依赖；"19:00 开饭"成为所有任务共享的停止规则。关系决定约束，约束决定任务——这就是两张图之间唯一的桥，也是 Graph Engineering 的全部秘密。

把晚餐写成代码，两张图是同一份代码的两个视图：

# 晚餐的代码化：Graph 与 Task Graph 是同一份代码的两个视图
class Guest:                    # 实体：客人（本体）
    allergy: str | None          # 约束：过敏史
class Dish:                     # 实体：菜品
    ingredients: list[Ingredient]  # 关系：使用
    requires: list[Appliance]      # 关系：需要（厨具）
def check_allergens(guests, dishes) -> bool:  # 任务：检查过敏原
    ...                            # 人类闸门：由人确认后返回 True
# 任务图：cut() → {stew(), roast(), boil(), fry()} 并行 → check_allergens() → serve(19:00)

05.2 · 案例二 · 订单：关系如何变成活

一张 ToB 订单——客户、产品、合同、折扣、交付、验收、发票、回款、售后。业务层的验证重点是：地图上的一条关系，会派生出任务图上一件必须做的活：

关系地图上的事实派生的任务闸门
合同：70% 验收后付款验收通过 → 自动开票 → 跟踪回款客户验收（人）
折扣 12% 超出销售权限提交销售总监审批审批（人）
交付日期固定，资源有限倒排计划；校验库存与产能变更需人工确认

06 十二戒律

把哲学压成十二条可执行的准则。四组，每组三条。

以图写码 · 建模

#准则为什么
1先写能力问题，再定架构业务必须回答的问题清单，就是模块边界的规格——问题写不出来，边界一定画错。
2类型即本体，签名即关系实体用类型表达，关系写进函数签名——domain/range 由编译器守护，不是由注释承诺。
3显式关系优于注释承诺用调用、数据流、接口表达关系；注释只解释"为什么"，不承诺"是什么"——承诺会被机器抽取，注释不会。

以图验证 · 质量

#准则为什么
4编译与类型检查是第一个质量闸门便宜、确定、每提交必跑——它是图谱"每阶段验证"的最廉价实现。
5测试是能力问题的机器化每个能力问题对应至少一个测试；问题不通过，是本体错了，不是代码错了。
6消灭假边死代码、循环依赖、隐式全局状态是假边——删掉它们，图才可信，模块才能并行。

用代码写业务

code-review-graph 把隐式拓扑显式化：理解从"读代码"变成"查图"，快一个数量级，每条边都有出处。

业务的图，写在代码里；代码的图，由工具显式化；工具的设计，由哲学约束。
写、查、循——三个动作，一个闭环。
