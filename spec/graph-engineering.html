01 什么是 Graph Engineering

一句话定义：设计 AI 智能体穿越的结构，而非其提示词。

传统上，我们通过提示词工程（Prompt Engineering）影响模型“说什么”，通过循环工程（Loop Engineering）控制智能体“如何反复尝试”。而 Graph Engineering（图谱工程） 把设计对象再提高一层：智能体所穿越的拓扑结构——它记住什么、任务如何被拆分与汇合、谁验证谁。

半边 1 · 记忆

知识图谱 Knowledge Graphs

智能体记住什么。节点是实体与事实，边是带时间与溯源的关系。流水线：本体建模 → 抽取 → 融合 → 服务给 LLM。

半边 2 · 工作

任务图 Task Graphs

智能体如何工作。节点是任务，边是执行依赖。模式：并行扇出（fan-out）、独立验证者、停止规则（stop rule）、人类闸门（human gate）。

核心心智模型

💡 知识图谱是有 schema 的产品，不是一堆三元组的堆砌。 A knowledge graph is a product with a schema, not a pile of triples.——先建模后抽取（Model before extracting）、先融合后存储（Fuse before storing）、每个阶段都验证（Verify at every stage）。

时代里程碑对 Graph Engineering 的贡献
1960s语义网络（Semantic Networks）最早的“节点=概念、边=关系”图式表示，奠定了图作为知识载体的直觉。
1970s–80s专家系统、产生式规则、框架系统规则与框架让“结构化的知识”可被机器推理，第一次大规模商业化。
1990s描述逻辑（Description Logic）、本体给知识图加上形式语义：子类推理、一致性检查，Ontology 成为规范。
1998–2004语义网：RDF / RDFS / OWLW3C 标准让知识图可互操作；RDF 三元组成为知识交换的事实格式。
2012Google Knowledge Graph“知识图谱”成为大众词汇；证明“图驱动的问答”在亿级规模可行。
2019东南大学《知识图谱》研究生课程把散落的学术成果整理成完整课程体系：表示 → 抽取 → 融合 → 推理 → 存储。
2023–24LLM 时代：GraphRAG、KG×LLM图谱给 LLM 提供可溯源的事实（防幻觉），LLM 反过来驱动抽取与融合（自动化）。
2025Graph Engineering 作为命名学科课程蒸馏为 9 阶段流水线 + 任务图编排规则，成为智能体工程师的“施工手册”。
🧭 从“数据”到“结构”的范式跃迁 早期工作解决“如何把知识存进图里”；LLM 时代解决“如何让智能体穿越图来工作”。Graph Engineering 正是这一跃迁的产物：结构本身成为工程对象。

#阶段一句话目的关键规则
1Scope 范围定义领域与要回答的问题，判断是否真的需要图问题需要“聚合”而非“遍历”→ 那是数据库，不是图
2Representation 表示选择知识载体（属性图 / RDF-OWL / JSON-SQLite）现在就决定每个事实如何携带时间与溯源——事后补几乎不可能
3Ontology 本体设计 schema：实体类型、关系类型、domain/range最难、最持久；用 10–20 个能力问题（competency questions）当规格与测试
4Entities 实体按源类型抽取实体结构化数据用确定性映射（不烧 LLM）；开放域才用 LLM；每条带证据句
5Relations 关系在“已通过 4 的实体”之间抽取关系关系抽取永远不许发明新实体；代码校验 domain/range；共现 ≠ 断言
6Events 事件抽取“发生了什么”（触发器 + 类型化参数）事件是头等节点；绝不把 4 参数事件压平成 6 条成对边
7Quality Gate 质量闸门每类源独立验收：精度/召回率 + 置信区间“假设我的数字是虚高的，直到抽样证明不是”
8Fusion 融合去重、对齐、合并（blocking → matching → merge）成败关键；错误合并远比漏合并更伤；合并必须可回滚
9Serve to LLMs 服务把图接进智能体（GraphRAG 检索）并证明胜过向量检索多跳问题必须赢，否则图谱不配它的维护成本

本体的最小示例：从“能力问题”出发

课程强调：先写能力问题，再设计 schema，最后才是抽取。一个只含 Person / Service / Incident 三种实体、两条关系、一种事件的最小本体，就能完整回答下面的问题——克制添加，直到某个能力问题要求为止。

severity 严重度| S
图 5 · 能力问题：“哪些工程师贡献过上个季度出事故的服务？”
# ontology.yaml —— 项目单一事实源，抽取 prompt 逐字嵌入
entities:
  Person:   { desc: 工程师或经理,        ex: [Jane Doe] }
  Service:  { desc: 可部署的软件单元,     ex: [payments-api] }
  Incident: { desc: 生产故障事件,        ex: [INC-4012] }
relations:
  CONTRIBUTED_TO: { domain: Person,  range: Service }
  AFFECTED:       { domain: Incident, range: Service, attrs: [severity] }
events:
  Incident: { trigger: outage/alert,
              args: [service, start_time, resolved_time, severity] }
⚠️ 三个最常见的死因（课程原话的现代转译） ① 没有本体就开抽 → 满图 Concept/Thing 节点；② 跳过融合 → 多跳查询自信地答错（路径在重复实体边界断裂）；③ 跳过质量闸门 → 精度随规模崩塌而无人知晓。课程明确：不许跳过 03 本体与 08 融合。

01.3 任务图：另一半

知识图谱管“记住什么”，任务图管“怎么干”。节点=任务，边=执行依赖。

任务图是 DAG（有向无环图）——同一模式在数据基础设施上运行了几十年（Airflow、Prefect、Temporal），如今被应用到智能体（LangGraph、CrewAI、AutoGen）。模式的“老”是优点：放心把业务交给有数十年生产历史的机器。

图 6 · 菱形模式（diamond pattern）——正经系统最终收敛的形状
规则内容要点
① 删除假边只有当工作真的流过，箭头才是真的“摘要这个文件，然后查我的日历”——日历从不读摘要，边是假的。删掉它俩就能并行。手工流水线通常藏有 2–3 条假边，这是零成本的第一个优化。
② 菱形模式拆分 → 并行工人 → 独立验证 → 单一负责人合并验证节点不可谈判：模型在自己上下文里给自己打分，会漏掉大部分自己的错误。给每个验证者不同的问题（对吗？新吗？源是真的吗？）——多样化的怀疑者能抓住相同怀疑者抓不到的错。
③ 停止规则只在“能拆成互不读对方结果的任务”上多智能体并行DeepMind × MIT 180 组受控配置：可拆分工作上团队胜率约 80%；而每一个多智能体配置在顺序任务上都输（退化 39–70%）。无协调的智能体把彼此的错误放大 17.2×；单一协调者把合并握在手里，降到 4.4×。更多智能体不是策略，工作的形状才是。
④ 人类闸门人类是一个节点，不是旁观者把审批放在错误代价昂贵的边上（发送、发布、退款、删除、部署），而不是每步都设闸。处处设闸 → 人成瓶颈；处处不设 → 没人看。用不可争辩的数字（跑过的测试、到账的钱）评判系统，别信它自报。

停止规则的决策程序

  1. 问：我的工作在哪里能拆成“永不互读对方结果”的碎片？
  2. 只拆那里。其余顺序的部分留给单个智能体。
  3. 绝不让发现物在没有单一合并负责人的情况下汇合。

四条护栏（Guardrails）

护栏防止什么
每个循环设最大轮数上限防止“永远重试”的失控循环烧穿上下文与预算
每个文件只有一位写者防止两个任务同时改动同一工件导致合并冲突与互相覆盖
路由写在书面步骤里模型填充任务内容，而不是规划结构——拓扑由人设计，内容由智能体生成
可派生智能体的数量硬上限防止“智能体再派智能体”的指数爆炸

03 Graph Engineering vs Loop Engineering

两者常常被混为一谈，但设计对象完全不同。

Loop Engineering（循环工程）治理智能体的迭代周期——经典的 PDCA / act-observe-plan 循环：计划 → 执行 → 检查 → 调整 → 再循环，关注的是“每一轮如何变得更好、如何收敛”。Graph Engineering（图谱工程）治理结构——记忆与工作的拓扑，关注的是“智能体穿越什么样的图”。

flowchart TB subgraph LOOP["Loop Engineering —— 循环（cyclic）"] direction LR A1["Plan 计划"] --> B1["Do 执行"] B1 --> C1["Check 检查"] C1 --> D1["Act 调整"] D1 --> A1 end subgraph GRAPH["Graph Engineering —— 有向无环拓扑（acyclic DAG）"] direction LR S["split 拆分"] --> W["workers 并行"] W --> V["verify 独立验证"] V --> M["merge 单一合并"] M --> E["end 交付"] end
图 7 · 循环（反馈回路）vs 拓扑（单向流水线）——同一批智能体，两种设计对象
维度Graph Engineering 图谱工程Loop Engineering 循环工程 推断*
操控对象 智能体的拓扑（记忆结构 + 任务结构） 智能体的迭代（循环节奏）
设计单元 图 / DAG：节点=实体或任务，边=关系或依赖 循环：计划 → 执行 → 检查 → 调整
核心问题 “智能体穿越什么结构？哪里拆、哪里并、谁验证？” “每一轮如何改进？循环会不会收敛？”
时间形态 一次设计、反复执行的结构（acyclic） 反复绕圈、逐轮逼近（cyclic）
典型失败 拓扑错误：并行浪费、记忆断裂、错误放大 17.2× 循环卡死：不收敛、空转重试、把失败当进步
何时使用 任务可拆分 / 多智能体编排 / 跨会话长期记忆 单智能体持续打磨 / 迭代式改进 / 反思自省
代表工具 Neo4j、Kùzu（记忆）；LangGraph、CrewAI、Airflow（任务） PDCA 循环、act-observe-plan、反射（reflection）、retry 策略
二者的关系 不是二选一：图谱决定结构，循环决定结构内每个节点的运转——菱形模式里的每个 worker 内部，就是一个 loop。
* 诚实标注 本文未能获取 Loop Engineering 的独立权威定义（检索源超时）。对比表中的循环工程一侧，系依据 graph-engineering 源材料的对照框架（“Loop engineers steered its iterations”）与标准 PDCA / act-observe-plan 概念推断而来，非独立权威来源。图谱工程一侧则完全来自已核实的原始材料。

04 最佳实践

从 SKILL.md 工作规则与全部参考文件蒸馏出的可执行准则。

十二条铁律

#准则为什么
1Schema 先行（先建模后抽取）无本体抽取是头号死因——满图 Concept/Thing 节点，重抽成本翻倍。
2每条事实带溯源没有证据跨度的三元组 = “带额外步骤的幻觉”。溯源在融合后补 = 几乎不可能。
3先融合后存储存储前消解重复；否则多跳查询在重复实体边界自信地答错。
4每个阶段都验证质量闸门按源类型独立设卡，精度/召回率带置信区间，不靠感觉。
5增量优于一次性大爆炸图即记忆循环：每会话后小步抽取+融合；定期做全图清理与置信度重评。
6关系动词要精确ACQUIRED / CITES / DEPENDS_ON，绝不 RELATED_TO / HAS_LINK——模糊动词让每个下游查询都含糊。
7常一起查的类型就合并反之：一个类型要靠限定属性区分用法（role: author/editor）就拆成两条关系。
8本体文件是单一事实源ontology.yaml 随项目保存，每个抽取 prompt 逐字嵌入它。
9结构化数据用确定性代码数据库/CSV/API 直接列映射（D2R 思路），用 NLP/LLM 处理已经结构化的数据是经典浪费。
10LLM 是流水线里的组件，不是流水线LLM 嵌入各阶段内部，外围包上验证（domain/range 校验、证据引用、人工复核带）。
11合并要可回滚，宁缺毋滥只在置信度极高时自动合并；错误合并静默融合两个实体的全部边集，比漏合并伤得多。记录 merged_from。
12矛盾事实两条都留冲突时保留双方 + 时间 + 溯源，检索时优先新者——事实会变（“在某公司任职”会过期），图应记录变化而非对抗变化。

症状原因修复
满图 Concept/Thing 节点没建模就抽取先做阶段 3 本体，再重抽
同一个人是 4 个节点跳过了规范化命名规则在本体中定义规则；跑融合
自信的错误关系把“共现”当“断言”证据引用要求 + domain/range 校验
事件被压平成“边的汤”没有事件 schema头等事件节点 + 参数 schema
规模一大精度就崩跨文档类型的 prompt 漂移按源类型独立 prompt；每源独立闸门

05 实例使用案例

四个真实场景：两个管“记忆”，一个管“因果”，一个管“编排”。

案例 A · GraphRAG 多跳问答（知识图谱 → LLM）

问题：“哪些工程师在上季度出过事故的服务上贡献过？”——这需要跨 Person → Service → Incident 的多跳路径，纯向量检索答不了。GraphRAG 的做法：实体链接查询 → 扩展 k 跳子图（k=1–2，超过 2 跳不加排序就是噪音）→ 把路径序列化为紧凑三元组（按头实体分组、去重、带溯源）→ 交给 LLM 叙述。答案引用图谱事实，而不是“氛围”。

flowchart LR Q["❓ 多跳问题"] --> EL["🔗 实体链接"] EL --> EX["🕸️ k-hop 子图扩展
k=1–2"] EX --> SE["📄 序列化三元组
带时间+溯源"] SE --> LLM["🤖 LLM 叙述答案
引用图内事实"]
图 8 · GraphRAG 检索链路

案例 B · 图即记忆循环（跨会话智能体）

智能体要跨会话积累知识，但上下文窗口有限。模式：每会话/任务结束后，用同一本体对新信息做抽取（阶段 4–6）→ 增量融合进既有图（阶段 8）→ 会话开始时按需 GraphRAG 检索，而不是把整图倒进上下文。矛盾事实两条都留，检索时优先新的；定期做清理。

flowchart LR S["📝 会话结束"] --> E["🧠 抽取新知识
同一本体"] E --> F["🧩 增量融合进图谱"] F --> G[("🗄️ 知识图谱
时间+溯源")] G --> R["🔍 GraphRAG 按需检索"] R --> S
图 9 · 跨会话记忆的闭环

案例 C · 事理图谱：回答“什么导致什么”

普通知识图谱回答“什么与什么相关”；事件逻辑图（事理图谱）回答“什么导致什么”——节点是事件，边是因果/时序/条件关系。典型：金融领域“加息 → 债市抛售 → 收益率上升 → 股市回调”。查询可以沿因果链从结果反向走回去。

flowchart LR A["📈 利率上调"] -->|causes| B["📉 债市抛售"] B -->|causes| C["📊 收益率上升"] C -->|causes| D["📉 股市回调"] D -->|causes| E["🏢 企业融资成本上升"]
图 10 · 事理图谱：因果链（区分“被报道为原因”与“仅仅共现”）

案例 D · 多智能体任务图编排（研究 / 草稿 / 验证）

把“写一份竞品调研报告”按菱形模式编排：拆分出三个独立研究角度并行 → 独立审稿人验证（正确性、时效性、来源真实性，各问各的）→ 单一主笔整合。DeepMind × MIT 的证据支持这一形态：可拆分工作约 80% 胜率，顺序工作则全军覆没——所以只拆能拆的。

flowchart LR P["📋 研究主题拆分"] --> R1["🔍 角度 A 研究"] P --> R2["🔍 角度 B 研究"] P --> R3["🔍 角度 C 研究"] R1 --> V["🧐 独立审稿
正确性/时效性/来源"] R2 --> V R3 --> V V --> M["✍️ 主笔整合"] M --> O["📄 调研报告"]

知识表示选型对照

表示何时选择代价
属性图 Property Graph
Neo4j / Kùzu / NetworkX		产品与智能体记忆的默认选择；节点/边带任意键值属性没有形式语义，一致性靠你自己维护
RDF/OWL 三元组需要与既有本体互操作、合规要求、需要描述逻辑推理（子类、一致性检查）冗长；边属性要 reification；工具链更陡
JSON/SQLite 中的类型化边<5 万节点、单一应用、智能体本地记忆查询能力封顶；多跳查询变慢/变频繁时再迁移

知识图谱 × 大模型：双向赋能

KG → LLM

图给模型“事实地基”

· GraphRAG：实体链接 → k 跳扩展 → 子图序列化进上下文

· 多跳问题检索路径而非邻域——路径就是答案骨架

· 社区摘要：离线聚类概括，回答“大主题是什么”

· 答案可引用图内事实，降低幻觉

LLM → KG

模型给图“施工队”

· 本体归纳：3–5 份代表文档 → 提议类型 → 人工修剪（绝不自动接受，会过拟合样本）

· 抽取：带本体约束 + 证据引用的 LLM prompt

· 融合仲裁：只处理中等置信区间的模糊对

· 关键框架：LLM 是流水线内的组件，带验证包裹——不是流水线的替代品
