1. 需求摘要

一句话定义：出纳批量上传发票后，系统自动识别并匹配客户，财务/业务人员人工核对通过后，在每日 16:00 将发票 PDF 和“发票请查收”自动发送到对应客户企微群；没有客户群时，通知销售建群，并完整记录每张发票的推送状态。

本次要做

  • 保留现有“批量上传 + 自动识别/匹配 + 人工核对”能力。
  • 增加客户企微群的匹配与直推能力。
  • 统一每日 16:00 处理已审核的待推送发票。
  • 展示已推送、未推送、推送失败和待建群记录。
  • 支持失败重试、补推和操作留痕，避免重复发送。

本次不改变

  • 不改变税务系统的开票和下载方式。
  • 不要求出纳逐张录入发票信息，仍以批量上传为主。
  • 人工核对仍是推送前的必要环节，不做未经确认的全自动外发。

2. 业务背景与要解决的问题

目前总部和上海分公司出纳从税务系统下载发票文件包，再把发票 PDF 批量上传到飞书多维表。插件会自动识别发票信息并匹配销售员，之后由人工核对，销售员逐个点击推送，飞书机器人按日期汇总后发给销售员，由销售员自行下载并转发。

业务现在希望新增“企微直推客户”模式：发票经过人工核对后，直接发到对应客户企微群，减少人工下载、转发和逐群发送的工作量，同时让财务可以清楚知道哪些发票已推送、哪些仍未推送。

现有痛点

  • 人工下载、转发动作重复，处理量随发票数量线性增加。
  • 销售员作为中间环节，容易出现忘记转发、转发延迟或发错群。
  • 推送结果缺少统一状态，未推送记录需要人工排查。
  • 暂无客户群时，缺少明确的责任人和后续补推机制。

期望结果

  • 把“发票 → 客户 → 客户企微群”关系沉淀为可追踪数据。
  • 把人工精力集中在核对和异常处理，自动化完成外发动作。
  • 每天固定时间统一处理，业务节奏可预期。
  • 每张发票都有明确状态、失败原因和下一步动作。

3. 角色与职责

角色主要动作关注结果
出纳从税务系统下载文件包，批量上传发票 PDF。上传成功，文件未遗漏，来源公司正确。
系统/插件识别发票字段，匹配客户、销售员和客户企微群，生成待核对记录。识别准确、匹配关系可追溯，异常有原因。
财务/业务核对人核对发票信息和归属关系；通过后进入推送批次。只把确认无误的发票发给客户。
销售无客户群时建群或补充群信息；处理异常匹配。客户群可用，待建群记录最终闭环。
客户企微群接收发票 PDF 与固定文案。客户能收到并下载正确发票。

4. Before：现在实际执行的流程

下面这张图还原的是目前真实发生的业务动作：开票申请先由系统自动生成初稿，宋主任修改后交给出纳；出纳按开票申请内容到税务系统开票并人工下载文件包，文件包包含每张发票和对应开票申请。之后出纳再批量上传到飞书多维表，系统识别和匹配，销售员收到后还要自行下载，再人工转发到客户。

人工动作系统动作蓝色框：外部系统/客户虚线之外的动作不在现有系统自动完成范围内
Before 的核心问题：发票在系统内完成识别和汇总后，仍要经过“销售员逐个点击 → 销售员下载 → 销售员人工转发”这段链路；客户是否收到、何时收到、是否漏发，都依赖人工执行，系统也难以形成准确的已推送/未推送状态。

5. After：目标业务流程（企微直推客户）

建议将“每日 16:00 统一推送”产品化为一个批次任务：只有完成人工核对、且已找到客户企微群的记录进入推送批次。系统自动发送后写回结果，未满足条件的记录保留在异常列表中。

人工动作系统动作异常分支
推荐的操作入口：在发票列表增加“批量推送”按钮和“定时任务”两种入口。每日 16:00 自动执行一次；人工核对完成后也可以对单张或选中记录进行“立即推送/补推”，但仍需满足审核通过和客户群有效两个前置条件。

6. 异常与补偿流程

异常状态可闭环状态所有异常都不能静默丢弃，必须保留原因、时间和处理人
异常场景系统处理人工下一步
发票字段识别失败状态=识别异常，展示原始文件和失败原因。人工补充/修正字段后重新校验。
客户匹配失败或匹配多个客户状态=待确认归属，不进入推送批次。选择正确客户，必要时通知销售确认。
人工核对不通过状态=核对退回，记录退回原因。修正数据后再次提交核对。
没有客户企微群状态=待建群，通知对应销售。销售建群并回填群 ID，记录进入下一次推送。
企微发送失败状态=推送失败，保存错误码/错误消息。系统按策略重试；仍失败时人工补推。
重复触发推送按“发票号码 + 推送批次/渠道”做幂等校验，避免重复发送。仅在明确需要时执行“强制补推”，并保留操作记录。

7. 业务规则与状态

核心业务规则

  1. 总部和上海分公司出纳可以在任意时间批量上传，系统按文件逐张建立发票记录。
  2. 只有“人工核对通过”的记录才允许进入推送批次。
  3. 每日 16:00 统一执行推送；当日 16:00 后新上传且已审核的记录进入下一批次，具体截止时间由产研确认。
  4. 发送内容至少包含发票 PDF 附件和固定文案：“发票请查收”。
  5. 发送成功后写入推送时间、推送渠道、目标群和操作/任务标识。
  6. 没有客户群、群 ID 无效或发送失败的记录，必须可筛选、可重试、可补推。

建议状态机

待识别 → 待核对 → 核对通过 → 待推送 → 已推送

识别异常、待确认归属、核对退回、待建群、推送失败均为可回到主链路的异常状态。

状态名称可按现有多维表字段兼容调整，但必须能区分“未推送”和“推送失败”，不能只用一个空值表示。

8. 数据与页面建议

8.1 发票记录字段

字段用途建议必填/来源
发票 PDF发送给客户的附件。必填，出纳上传。
发票号码、开票日期、金额、税额、价税合计核对和追踪。系统识别，可人工修正。
客户名称确定发票归属和推送目标。系统匹配，人工确认。
销售员异常通知和客户群维护责任人。系统匹配，人工确认。
客户企微群 ID / 群名称确定发送目标。系统匹配或销售补录。
核对状态、核对人、核对时间控制推送前置条件，形成审计记录。人工操作产生。
推送状态、推送时间、推送渠道查询已推送/未推送。系统写回。
失败原因、重试次数、最后重试时间异常处理和运营排查。系统写回。

8.2 页面/视图建议

  • 全部发票：支持按开票日期、公司、客户、销售员、推送状态筛选。
  • 待核对：展示识别结果、客户匹配结果和 PDF 预览/下载入口。
  • 待推送：只展示核对通过且客户群有效的记录，支持批量推送和查看预计发送数量。
  • 异常处理：集中展示识别异常、待建群、推送失败和核对退回，提供对应处理按钮。
  • 推送记录：展示发送时间、目标群、发送结果和失败原因，支持按批次查询。

9. 产研验收标准

编号验收项验收口径
AC-01批量上传出纳一次上传多张 PDF 后，每张文件均建立独立记录，且可追溯到原文件。
AC-02自动匹配系统完成发票字段识别，并给出客户、销售员、客户群匹配结果；失败时明确展示原因。
AC-03人工核对门禁未核对通过的记录无法进入推送批次；退回原因可查看。
AC-04定时推送每日 16:00 自动处理符合条件的记录，并生成推送批次。
AC-05消息内容客户企微群收到正确的发票 PDF，并包含“发票请查收”文案。
AC-06无群分支没有有效客户群时不发送，状态变为“待建群”，对应销售收到通知。
AC-07状态追踪可按条件查出已推送、待推送、待建群、推送失败记录，并显示最新处理时间。
AC-08失败补偿发送失败记录保留失败原因，支持重试或人工补推，不产生不可解释的丢单。
AC-09幂等重复点击或任务重跑不会默认重复发送同一张发票；强制补推必须有明确操作记录。

10. 待确认事项

以下事项不影响流程理解，但会影响产品和技术落地，需要在评审时定稿：
  1. 同一客户同一天有多张发票时，是合并为一条群消息发送多个附件，还是每张发票单独发送？
  2. 16:00 是系统自动发送，还是由人工在 16:00 点击“批量推送”确认后发送？建议采用“自动批次 + 可人工暂停/补推”。
  3. 企微客户群的识别方式是什么：通过客户名称匹配、群 ID 维护表，还是由销售在系统内绑定？
  4. “暂无群”通知发送给销售的渠道是什么：飞书消息、企微消息、邮件，还是系统待办？
  5. 推送失败的自动重试次数、间隔和最终告警对象是什么？
  6. 发票是否允许在推送成功后再次修改附件或关键信息？如允许，是否需要重新核对并补推？
  7. 客户企微群是否存在合规或权限限制，例如群机器人、外部联系人群、附件大小和消息频率限制？

附：给产研同学的场景描述

财务完成开票后，出纳从税务系统下载本次开票文件包并批量上传发票 PDF。系统自动识别发票信息，并根据客户名称等信息匹配客户、销售员和客户企微群。财务/业务人员在推送前进行人工核对，确认无误后，记录进入当天 16:00 的推送批次。批次执行时，系统将发票 PDF 和“发票请查收”发送到对应客户企微群，并把结果写回发票记录。如果没有客户群、匹配不明确或发送失败，系统不应静默跳过，而应进入对应异常状态，通知责任人并支持后续补推。最终，业务人员可以按日期、客户、销售员和状态查看每张发票当前处于什么环节。
本文档根据飞书知识库页面《发票自动化推送》整理，页面原始需求包含“自动匹配客户名称、人工核对后推送到客户群、每日 16:00 统一推送、查看已推送/未推送发票、无群时通知销售建群”等信息。流程中的“建议”与“待确认事项”用于帮助产研评审，不代表已经确定的产品决策。
