Verification methodology · version 2.0

ZK × Graph Engineering 闭环验证方案

目标不是宣称“证明 AI 写的每一行都正确”，而是在不做逐行源码审查的前提下，把需求、架构、实现、运行结果与风险接受绑定成一条可复现、可追溯、可独立挑战的证据链。

核心：规约先行拓扑：实现与验证并行决策：按风险分级结果：有界保证，不做绝对承诺
v2 的核心修正：你可以不读代码，但不能不定义正确性；可以把代码隔离在验证边界之外，但不能把测试报告误称为密码学证明；可以自动合并低风险变更，但高风险系统仍必须对意图和剩余风险做人工决策。

00对现有方案的审计结论

原方案的方向成立：Graph Engineering 很适合把“不可读的实现”投影成可验证结构。但有八处需要实质修改，否则“全绿”会制造虚假的确定感。

必须修改 标题与结论

“不读一行代码，验证 AI 写的每一行”无法成立。有限测试与结构图不能证明任意程序的全部语义。改为“免逐行审查的有界保证”，且每个结论都必须写清范围、假设、保证等级与剩余风险。

必须修改 ZKP 对应

源码不是被密码学隐藏的 witness，CI 也不是零知识 verifier。更准确的叫法是代码隔离 / 选择性披露。Git hash 只是内容寻址；只有受保护引用、签名证明和外部日志共同存在时，才形成防替换的版本绑定。

必须修改 阶段拓扑

测试设计不能在实现完成后才开始。阶段 ④“实现”和阶段 ⑤“挑战设计”必须从架构节点并行分叉，由隔离上下文或独立验证者完成，再在阶段 ⑥汇合。这才符合 Graph Engineering 的菱形模式。

必须修改 独立性

如果同一个 AI 写规格、代码、测试和最终总结，闭环只是自证。必须隔离实现者与验证者的上下文、权限和输入；隐藏挑战在实现冻结前提交摘要，在执行时才揭示给验证环境。

必须修改 图的保真度

“类型 = 本体、签名 = 关系”是有用的启发，不是普遍等式。动态调用、反射、配置、SQL、消息、基础设施和运行时路由都会逃出静态代码图。需要显式追踪映射与运行图补证。

必须修改 完备性

能力问题遍历返回非空，只证明“存在一条结构路径”，不证明业务答案正确。原“业务完备性”应改为声明范围内的业务符合性；只有有限状态模型或形式化内核可使用更强的完备性措辞。

新增 可信计算基

编译器、图抽取器、测试框架、oracle、CI 镜像、策略引擎、签名密钥都可能出错或被篡改。必须列出 TCB（Trusted Computing Base）、固定版本、做自测，并让证据绑定验证器摘要。

新增 运行闭环

合并不是闭环终点。环境差异、真实数据和外部依赖只会在运行时出现。需要金丝雀、业务不变量、SLO、异常预算和自动回滚，让运行证据反哺 Meta 与图。

应保留的核心能力问题先行、世界知识与任务拓扑双视角、确定性抽图、预期图与实际图比对、属性/模型验证、证据汇总和风险边上的人类闸门。这些是原方案最有价值的骨架。

01先定义“保证”到底是什么

正确性不是代码自身的属性，而是“实现相对于某份规约、在某组环境与假设下”的关系。

不可实现的命题所有代码路径 × 所有输入 × 所有环境 × 所有未来依赖 都正确。对一般程序，这既无法通过有限测试得到，也不能靠代码图得到。

v2 只接受如下形式的可审计声明：

AssuranceClaim :=
  subject_artifact_digest
  + specification_digest
  + environment_digest
  + verifier_set_digest
  + covered_properties
  + excluded_properties
  + assumptions
  + evidence_results
  + residual_risk
  + assurance_level
术语v2 的精确定义不代表什么
免读代码产品负责人不做逐行源码审查；实现仅进入隔离构建与验证环境源码从未被机器、验证器或受权专家访问
通过已声明门禁对同一制品摘要全部满足，且无未接受的高风险例外软件绝对无 bug
符合性已声明的结构、行为、非功能属性与可观察结果满足规约遗漏需求也被验证
证据可复现验证运行的结构化、可溯源产物密码学意义上的“程序正确性证明”
闭环生产信号能触发假设、规约、挑战和图的修订CI 全绿后流程结束

02威胁模型与信任边界

先假设系统会怎样“骗过全绿”，再设计验证。这里的攻击者未必有恶意，也可能只是同源偏差、工具盲区或环境漂移。

威胁典型失效v2 控制
同源自证AI 按自己的错误理解同时写实现和测试实现者/验证者隔离；独立 oracle；隐藏挑战；对抗性 reviewer
规格投机为了让代码通过而修改 Meta、约束或阈值规格先冻结；protected path；变更需要重新审批并使旧证据失效
测试过拟合只针对已知样例写分支生成式、变形、差分与隐藏测试；变异分数验证测试强度
报告伪造/错配拿旧报告证明新提交每份证据绑定源码、制品、规格、环境和验证器摘要
抽图盲区反射、运行时注入、消息路由不在静态图中静态图 + 构建图 + 运行图；对盲区设 coverage debt 和阻断阈值
验证器缺陷规则引擎或 oracle 本身错误验证器版本锁定、自测语料、交叉验证、故障注入、双实现比对
环境漂移本地通过、生产失败可复现构建、镜像摘要、依赖锁、迁移演练、金丝雀与回滚
未建模风险安全、性能、隐私、可用性完全没进 Meta风险模板强制列项；未填写不是“不适用”，而是“未知并阻断”

可信计算基 TCB

保证强度不会超过以下组件中最弱的一项：规格与 oracle、源码解析器、编译器/运行时、测试与模型检查器、依赖解析器、CI runner 与基础镜像、策略引擎、制品仓库、签名密钥、生产遥测。每个组件都要有 id + version + digest + owner + self_test。

两个人类决策点，而不是一个G1 在实现前确认“这就是要解决的问题、这些风险可接受”；G2 在发布前确认“证据覆盖了约定范围、例外与剩余风险可接受”。两次都不要求读代码，但都不能交给写代码的同一个 AI。

03从“三张图”升级为“五图证据体系”

三图框架适合解释理念，但要支撑真实发布决策，还需要运行图和证据图。五张图通过稳定 ID 与摘要绑定，而不是靠名称相似来猜映射。

1. 意图图能力、场景、主体、规则、不变量、非功能目标、风险、假设
2. 架构图边界、契约、数据所有权、信任域、允许/禁止依赖、部署单元
3. 实现图符号、调用、数据流、依赖、配置、Schema、API、IaC、制品
4. 运行图真实调用、消息流、拓扑、SLO、业务事件、异常与回滚
5. 证据图Claim → Challenge → Run → Evidence → Decision → Exception
五图不是五份手工文档：意图与架构是承诺；实现与运行由工具抽取；证据图由流水线生成。
映射边必须回答失败条件
REALIZES哪个架构节点实现哪个意图节点？意图无实现，或实现无意图来源
IMPLEMENTS哪个制品/符号实现哪个契约？契约只有名称匹配，没有稳定 ID
OBSERVED_AS静态边在运行时是否出现，是否出现未声明边？动态边无法归属或越过信任边界
VERIFIED_BY每个 claim 由哪些相互独立的 verifier 覆盖？只有实现者自写测试，或只有单一证据类型
INVALIDATES哪类变更使哪些证据过期？换了代码/依赖/规格后仍复用旧绿灯

04ZK 灵感应落在“证据协议”，不是术语包装

v2 保留承诺、挑战、响应、验证四段式，但使用工程上可成立的含义。

协议步骤工程实现必须满足
Statement可执行 claim 集：功能、结构、不变量、SLO、安全与合规每条有稳定 ID、owner、风险级别、oracle 与验收阈值
Commitment对规格包、挑战包、工具链和策略包计算摘要并签名先于实现冻结；变更会生成新版本并使相关证据失效
Challenge公开门禁 + 隐藏样例 + 生成式输入 + 故障注入 + 图约束查询由独立验证域产生；可记录随机种子；不可被实现者定向适配
Response构建制品在隔离环境中的行为、轨迹、指标和反例直接采集，不接受 AI 自述替代原始输出
Verification固定版本 verifier 按策略计算 pass/fail/invalid验证器与输入摘要写入证据；能由另一 runner 重放
Attestation签名 evidence manifest 与 provenance绑定同一源码、制品、规格、环境；防止报告拼接
可以使用密码学，但不要混淆作用哈希、签名、透明日志和证明链能证明“这份证据对应这份输入、未被替换、由这个 runner 产生”；它们不能独自证明业务逻辑正确。密码学在这里保护证据完整性与来源。

05九阶段闭环 v2：同样九步，不再假装是直线

阶段编号表达治理顺序；真正的执行拓扑是 DAG。阶段 ④和 ⑤并行，阶段 ⑥汇合，阶段 ⑨把生产事实反馈回阶段 ①。

G1 意图批准① Meta → ② GE 设计 → ③ 架构与验证计划
↓ 分叉
④ 实现域AI 只获得公开契约；输出冻结制品
⑤ 独立挑战域oracle、隐藏挑战、模型与对抗用例
↓ 汇合
⑥ 质量与制品证明构建、静态、测试、供应链、可复现性
⑦ 多图偏差验证意图/架构/实现/运行的约束差分
↓
⑧ 业务符合性与鲁棒性属性、状态、变形、差分、故障与安全
↓
G2 发布与剩余风险批准⑨ 适配性、金丝雀、运行证据、回滚、Meta 反馈
1

项目 Meta：定义价值、边界与风险宪法

不只写领域描述与能力问题，还要写反目标、外部依赖、数据分类、不可逆动作、SLO、合规约束、威胁模型、风险等级和已知未知项。

承诺meta.yaml + risk.yaml
挑战每个目标可观察；每个风险有控制或明确接受
证据Meta lint、歧义/冲突/孤儿 claim 报告
失效“以后再定”、空 oracle、未知项被写成 N/A
2

Graph Engineering 设计：建立五图 Schema 与追踪规则

定义节点、边、来源、置信度、时间与失效语义。每个 claim 必须能追踪到架构、挑战和证据；不要求所有业务问题都强行翻译成代码图遍历。

承诺ontology.yaml + traceability.yaml
挑战Schema 自洽、关系有精确动词、每条事实带 provenance
证据Schema/约束报告与 trace coverage
失效靠名称相似自动对齐意图与代码
3

架构与验证设计：同时承诺“怎么造”和“怎么证”

模块 DAG 之外，必须包含接口契约、数据所有权、信任域、失败模式、迁移/回滚、允许依赖，以及每条 claim 的验证方法和最小阈值。G1 在这里冻结规格摘要。

承诺architecture.yaml + verification-plan.yaml
挑战无环、无越界数据流、关键风险至少两种独立证据
证据架构规则报告、claim-to-verifier 矩阵
失效只有组件图，没有契约和失败语义
4

隔离实现：代码是受控制品，不是神秘 witness

实现域只读冻结的公开契约，不能改规格、门禁和隐藏挑战。输出源码 commit、依赖锁、SBOM、构建脚本与候选制品摘要。产品负责人不读源码。

输入签名规格包与公开契约
挑战hermetic build、依赖锁、最小权限
证据source/build/artifact digests + provenance
失效实现能修改测试阈值或报告生成器
5

独立挑战设计：在另一条边上构造 oracle

验证域从 Meta、模型、威胁与历史事故生成挑战，不读取实现者的推理与测试。公开测试帮助开发；隐藏测试、生成种子和对抗语料只在候选制品冻结后执行。

承诺challenge pack 摘要先冻结
方法例子 + 属性 + 变形 + 差分 + 模型 + 故障
证据oracle coverage、mutation score、challenge provenance
失效把覆盖率当测试有效性的充分条件
6

代码质量与制品验证：同一个候选物一次性过门

所有检查都针对同一个 artifact digest：编译、类型、lint、静态安全、单元/契约/集成测试、依赖许可与漏洞、SBOM、可复现构建。重建后摘要变化则证据无效。

挑战固定镜像、固定种子、无网络或白名单网络
门禁结果阈值按风险等级，不设统一 80%
证据原始日志摘要 + 结构化结果 + attestation
失效flaky test 重跑到绿；只存摘要不存原始证据
7

代码偏差验证：从结构 diff 升级为多图约束

比较的不是节点数量，而是约束：禁止依赖、信任域穿越、数据所有权、API/schema 兼容、关键路径、变更爆炸半径、运行时未声明边。动态盲区作为显式 debt。

预期意图图 + 架构图 + policy
实际实现图 + 构建图 + 运行图
证据逐条 violation，带源节点、规则、严重度和 provenance
失效“偏差为空”被解释为语义正确
8

业务符合性与鲁棒性：验证可观察语义

能力问题必须落到可观察业务结果，而不只是图路径存在。有限状态系统做模型检查；代数不变量做属性测试；无精确 oracle 时做变形或差分测试；外部依赖做契约、回放与故障注入。

功能场景、状态迁移、前后置条件
鲁棒边界、并发、超时、重试、幂等、恢复
非功能安全、隐私、性能、可靠性、可访问性
证据反例优先；通过率必须带样本、种子和模型范围
9

Meta 适配性、发布与运行反馈：真正闭环

聚合 claim 的独立证据，计算保证等级，列出例外和剩余风险。G2 决策后先金丝雀；生产业务不变量、SLO 与安全信号持续进入运行图。偏差触发回滚并创建新的 Meta/挑战版本。

决策pass / conditional / fail / invalid
发布签名制品、渐进流量、自动回滚
运行SLO、业务不变量、异常预算、漂移
反馈incident → new claim/challenge → 新一轮

06保证等级与风险分级

不是“绿/红”二值神话，而是让保证强度与错误代价匹配。系统总等级取关键 claim 的最低等级，而不是平均值。

L0 可构建锁定环境中能产生制品；没有业务保证。
L1 结构符合类型、契约、依赖和图约束满足；不代表行为正确。
L2 行为符合场景、属性、变形/差分和变异门禁通过；保证限于输入模型。
L3 运行可信安全、性能、故障、金丝雀、SLO 和回滚经过验证。
L4 形式化内核关键有限模型或算法有机器检查证明；不自动外推到整个系统。
风险级别例子最低要求自动发布
R0 实验/可丢弃内部原型、无真实数据L1；基础静态与冒烟允许
R1 可逆内部变更后台工具、可快速回滚L2；变异门禁；金丝雀策略允许时
R2 客户/敏感数据订单、身份、计费L3；安全与隐私；双证据；G2不允许无条件自动
R3 不可逆/监管/人身资金划拨、删除、医疗、权限根关键内核 L4 或独立专家验证；演练回滚；职责分离禁止
“不读代码”的适用边界R0-R1 可以主要依靠自动证据；R2-R3 仍可让产品所有者不读代码，但必须引入独立安全/领域验证者、形式化内核或合格第三方。执念应是“我本人不逐行 review”，而不是“任何人都永远不检查高风险实现”。

证据的七条不变量

  • 每条证据只证明一个明确 claim，不能用“测试全绿”覆盖不相干结论。
  • 源码、最终制品、规格、挑战、策略、环境、验证器七类摘要必须齐全。
  • 证据必须保存原始输出或其内容摘要；AI 生成的自然语言摘要仅是派生视图。
  • 任一绑定摘要变化，相关证据自动标记 invalid，不能继续显示绿色。
  • 随机测试必须记录生成器版本、种子、样本空间和最小反例。
  • flaky 不能靠重跑到绿；必须报告失败分布，并在风险策略中单独处理。
  • 例外必须有 owner、理由、补偿控制、到期时间；过期例外自动阻断。

08最终门禁：不读代码时，你到底看什么

你不需要看一堆工具日志，只看一个“可下钻但不可粉饰”的决策面板。默认展示反例、缺口、过期证据与剩余风险，而不是绿色数量。

PASS所有必需 claim 达到风险等级要求；无未批准例外；证据绑定有效。
CONDITIONAL仅允许有时限、可补偿、可回滚的例外；必须由风险 owner 接受。
FAIL存在反例、阈值失败、未建模高风险或越权依赖；不得合并/发布。
INVALID摘要错配、环境/验证器未知、证据过期或 provenance 断裂；不是失败，而是没有可用证明。
面板必须显示禁止的替代指标
本次变更影响的 claim、风险级别、最低/实际保证等级总测试数、总绿灯数
所有反例、越界边、未覆盖动态点、flaky 与验证器异常单一代码覆盖率
规格/制品/环境/验证器摘要是否一致“最后一次 CI 成功”徽章
供应链变化、权限变化、数据迁移和回滚演练结果只看业务单测
剩余风险、例外 owner 与到期时间AI 自评“低风险”
生产金丝雀和 SLO 状态，及自动回滚是否可用合并即完成
 
release_allowed =
  all(required_claims.meet_minimum_level)
  and evidence_bindings.valid
  and no(open_counterexample)
  and no(unowned_or_expired_exception)
  and supply_chain_policy.pass

  and human_gate_G2.approved_when_required

09最小实现架构与仓库约定

原方案把新增量估计为“四个胶水脚本”，偏乐观。真正可依赖的系统至少需要七个职责清晰的组件，并把报告生成与判定逻辑分开。

组件职责首选形态
spec compiler校验 Meta/claim/架构/验证计划，生成稳定 ID 与摘要CUE / JSON Schema / 自定义 CLI
graph adapters抽取代码、API、DB、配置、IaC、依赖和运行轨迹code-review-graph + 语言/平台适配器
challenge registry保存公开/隐藏挑战承诺、oracle、生成器与种子只读制品库 + 权限隔离
verifier runners静态、契约、属性、模型、变异、安全、性能、故障验证固定容器镜像，按能力插件化
evidence emitter统一输出 schema，绑定摘要、原始日志和 provenanceCI library，不允许各工具自由写总结
policy engine按风险等级求值，输出 pass/conditional/fail/invalidOPA/Rego 或等价确定性规则引擎

对 code-review-graph 的现实定位它可以成为实现图与影响分析的重要数据源，但不能单独承担“业务正确性验证器”。v2 不再写“70% 已就绪”这类未经能力基线验证的比例。接入前应对每种语言、动态特性、数据流和生成代码做抽取精度/召回基准，并把盲区纳入政策。

10落地路线：先证明验证系统抓得到错

每轮验收都用已知缺陷、变异或故障注入来验证验证者本身。不要先追求覆盖所有仓库。

Round范围交付硬验收
0 基线选一个 R1、可回滚、有真实历史 bug 的服务20 个 claim、风险表、10 个历史缺陷语料、当前盲区清单不改代码先回放：系统能检出多少历史缺陷；无基线不宣称有效
1 证据骨架阶段 1-6摘要绑定、可复现构建、结构化 evidence、G1/G2替换 commit/制品/报告任一项，决策必须变为 INVALID
2 五图偏差阶段 7追踪矩阵、架构规则、静态+运行差分注入禁止依赖、未声明消息边、schema 破坏，必须精确定位
3 行为强度阶段 5、8属性/变形/差分/模型/变异组合对业务核心注入语义 bug；以 mutation score 和漏检原因验收
4 生产闭环阶段 9金丝雀、业务不变量、SLO、回滚、incident 反哺演练依赖超时、数据错误和回滚；证据图自动生成新 claim
5 扩域逐仓库/语言/风险扩展验证器能力矩阵和成本数据只有在漏检率、误报率、时延和成本达标后扩大自动发布范围

90 天建议节奏

  • 第 1-2 周：选 PoC、整理历史 bug、写 claim 与风险模板，完成 G1。
  • 第 3-5 周：实现证据 schema、摘要绑定、策略求值和 INVALID 语义。
  • 第 6-8 周：接入实现图、依赖/契约/数据流规则，建立抽取盲区基线。
  • 第 9-10 周：加入属性、变形、差分与变异测试，验证测试本身。
  • 第 11-12 周：金丝雀、业务不变量、回滚演练；用数据决定是否扩大免审范围。

11最终边界与结论

这套方法可以显著降低人工读代码的需要，但不能消除需求责任、oracle 责任与风险责任。

它能给你的它不能给你的
实现与冻结规格之间的结构和行为符合性证据规格本身没有遗漏或理解错误的保证
同一制品、环境和验证器下可复现的结果所有未来环境和输入都正确
对同源自证、报告错配和工具盲区的系统性控制完全不信任任何工具或人的无信任系统
按风险自动化合并/发布低风险变更的依据让高风险不可逆决策完全无人负责
把生产事故转成新 claim、新挑战和新图约束的闭环一次建设、永久有效的验证体系
最终判断：你的直觉有效，但真正有效的不是“ZKP 能证明 AI 代码”，而是 ZKP 启发你把软件交付改造成一个先承诺、后挑战、证据绑定、独立验证、风险决策的协议；Graph Engineering 则负责把意图、架构、实现、运行与证据的拓扑显式化。两者结合后，你可以合理地做到“不逐行 review 代码”，但应把目标写成：用可审计证据替代源码阅读，用有界保证替代绝对正确，用运行反馈完成闭环。
