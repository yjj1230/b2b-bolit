PROJECT AS EVIDENCE

一段讨论，逐步形成一套可执行的方法

从不看代码，
到真正看见项目

我们最初讨论的是一个近乎偏执的问题：能不能几乎不读代码，只确认极少数设计，就把握一个项目的质量？讨论走到最后，答案不再是“少看一点”，而是重新设计项目如何被描述、被测量、被挑战，以及在交付前如何把不确定性一层层压缩。

b2b_pilot_v3 的实践背景 Graph Engineering × 测试 × 可复现证据 面向人类的故事 + 面向 Agent 的执行契约
最终得到的不是一种神奇的“免审代码术”，而是一种更朴素也更严格的交付方式：人负责定义什么算正确，机器负责持续排除不正确，直到只剩少量真正需要人判断的问题。
01 · 起点

问题一开始，听起来有些冒险

“几乎不看代码，能不能完成项目质量 review？”

这个问题并不是偷懒。它背后其实是一种对规模的直觉：代码越多，人逐行阅读越不可能成为稳定的质量手段。全面阅读看似认真，注意力却会被平均摊薄。

最初的问题

如果我只确认非常少的设计，而不去看大量实现，能不能仍然把握项目整体质量？能不能像一次“量子坍缩”，由少数关键信息迫使其他信息保持一致？

最初的回应

可以减少源码阅读，但不能跳过正确性的定义。少量设计之所以有用，不是因为它们少，而是因为它们能约束大量后续选择，并且能被独立证据反复检查。

进一步反思

真正想要的是一套严谨、稳定、可复现的量化方法。从 Meta 到设计文档都模板化，把项目放进一个尺度有限的空间，再用测试、双 Graph、采样和学习不断缩小不确定性。

问题被重新定义

那就不该把 review 理解为“读过多少”，而应理解为“还有多少重要状态没有被区分”。项目交付也不再是 Agent 的一句完成，而是证据满足一组明确条件后的状态。

02 · 转折

真正要改变的，是 review 的对象

不再把源码文本当成唯一事实，而是审查项目的约束、响应和剩余风险。

一份实现可以有无数种写法。只要它们满足同样的业务规则、接口契约、状态变化、数据边界和运行要求，从产品所有者的视角看，它们就属于同一类可接受实现。于是，人不必知道每一处具体写法，只需要确认划分这类实现的规则是否正确。

这和类型系统、数据库约束、会计守恒有些相似。我们不会逐笔猜测库存是否可能变成负数，而是要求所有改变库存的路径都服从同一个约束，并用并发、回滚和真实数据库测试去挑战它。

过去关注什么新的关注对象为什么信息量更高
代码是否写得像预期业务不变量是否在所有相关路径成立一个不变量可以约束许多模块和调用路径
测试是否很多测试能否拒绝错误、杀死变异、复现反例测到过不等于测得有效
文档是否齐全每条设计是否有稳定编号并能追到实现与证据齐全的散文仍可能彼此矛盾
CI 是否全绿证据是否绑定同一源码、制品、环境和验证器避免用旧报告证明新项目
整体分数是否漂亮高风险问题是否仍有未知、反例或过期证据关键风险不能被大量低价值绿灯平均掉

关键转折：我们不再问“Agent 看完了吗”，而是问“项目中还有哪些重要状态无法由现有证据区分”。

03 · 收敛

所谓“坍缩”，实际是约束传播

量子是一个形象的比喻；数独、约束求解和主动提问更接近工程事实。

假设项目最开始有许多可能状态：需求可能有几种理解，架构可能有几种拆法，实现又有大量选择。每确认一条高价值信息，就能排除一批不符合它的状态。

Ω0 = 所有可能的项目状态
Ωt+1 = Ωt ∩ 与新证据一致的状态
交付目标：剩余状态中的风险已经低于当前项目允许的范围
约束必须连得起来

如果设计、实现、测试和运行彼此没有稳定映射，局部确认不会传播到全局。

约束必须能被推翻

“系统应该可靠”无法验证；“并发发货后库存永不为负”可以被反例挑战。

观测器必须先校准

图工具、测试框架和规则引擎若理解错了项目，越精密的数字越会制造假象。

必须保留的边界：内部一致不等于外部正确。一个项目可以从需求到测试都严丝合缝，却从一开始就解决了错误的问题。外部业务事实与专家判断不能被自动化系统自我生成。

04 · 方法拼图

每一种技术，只负责它擅长的那一段

方法的强度来自分工，而不是把所有东西都叫作“证明”。

方法在这里负责什么留下什么结果不要误认为
模板化 Meta 与设计把目标、风险、状态、不变量放进有限且可检查的坐标系稳定编号的声明、假设和开放问题模板覆盖了现实中的一切
世界图与任务图分别说明系统记住什么、系统如何推进，再把两者对齐实体关系、状态迁移、能力问题坐标图上存在一条路径就代表业务正确
实现图与运行图把代码和真实运行投影成可比较的结构调用、依赖、数据流、动态边和影响范围静态抽取能看见反射、配置和所有外部行为
测试与覆盖观察环节联动，验证正确路径，主动拒绝错误路径反例、状态覆盖、组合覆盖、变异结果行覆盖率高就是业务质量高
承诺与挑战先固定规格和挑战摘要，再让独立执行者验证同一制品不可错配、可重放的证据测试报告变成了密码学正确性证明
规范化比较用稳定 ID、统一格式和约束查询消除名字与表达差异预期与实际的明确差异普通映射都需要混淆电路
隐私计算双方不能暴露输入时，仍可计算约定判断只披露判断结果的比较证明它能替代正确的比较规则
经验学习从事故与误报中提出下一批候选规则带来源、解释和历史回放的规则候选统计相关性可以直接成为硬规则

测试覆盖不是一个百分比

如果只看行覆盖率，我们只知道某行曾被执行。真正的质量密度来自多个维度同时成立：

双 Graph 也不是最终答案

世界图和任务图提供了最重要的起点，但真正交付时还要补上实现、运行和证据。五者通过稳定 ID 相连，才能回答“这条业务声明由哪里实现、在哪里运行、由什么证据支持”。

05 · 采样

不穷举所有可能，而是每次问最值钱的问题

排列组合不是为了制造更多测试，而是为了更快地区分故障来源。

现实项目的组合空间太大：角色、状态、数据、网络、重试、并发、时间和外部服务相互作用，无法全部穷举。采样的价值在于用少量实验覆盖高概率交互，并在失败后迅速缩小范围。

遇到的问题适合的办法它如何减少排查成本
参数组合太多二元/三元组合覆盖不遍历全部排列，也能覆盖常见交互缺陷
不知道哪一组变化导致失败分组测试一次试一组，再根据结果继续二分
失败输入或改动太大最小化失败样本自动删减，直到留下最小失败条件
测试预算有限按风险和信息增益排序优先检查高影响、高不确定、高耦合区域
历史缺陷不断增加经验模型与候选规则让过去的事故改变下一次采样顺序

人类 review 的位置也因此改变：专家不再接收一大堆源码，而是接收“当前仍有三种解释无法区分，确认其中哪一种符合业务”的精确问题。专家的回答随后被写回为新声明、新反例或新规则。

用例坐标与文档漂移

验证没有只找代码问题，也反向修正了设计和用例本身。

最有价值的不是这些数字本身，而是它们之间能相互追溯：能力问题产生测试清单，测试暴露实现和设计偏差，偏差回写文档，再由代码图重新回答能力问题。项目不是一条从文档走到代码的直线，而是一条能往返的路。

项目中的一次发现如果只看绿灯会怎样闭环如何处理
事务中错误地查询连接池常规 happy path 可能长期不暴露故障注入发现 → 修复 → 形成“事务内只用同一连接”的规则
幂等键没有租户维度单租户测试全部正常跨租户负例发现 → 修改派生规则 → 增加固定回归样本
部分发货后开票按整单计算整单发货场景看不出问题分批组合暴露守恒失败 → 业务基准改为有效发货量
图工具给出互相矛盾的测试信号可能把工具盲区误当成项目缺口先把测量工具列为被验证对象，再决定哪些指标可用于结论
真实企微环境尚未端到端验证mock 全绿容易被描述成全面完成明确保留为外部环境风险，不用内部证据替代真实运行

这段实践带来的最重要教训：覆盖率是结果，不是目标；图是测量工具，不是现实本身；真正可靠的是能暴露反例、承认盲区并使旧结论失效的过程。

07 · 交付前，Agent 应该怎样工作

从接到项目，到有资格说“可以交付”

下面是给人阅读的版本：每一步都说明要解决什么，以及应该留下什么。

第 0 步

先验证尺子是否可信

用已知缺陷、故意注入的错误和小型标准样例检查图工具、测试框架、规则和运行环境。看不见的动态调用、错误的测试映射和工具自身失败都要列出来。

留下：工具版本、校准结果、已知盲区、谁负责维护。
第 1 步

把项目为什么存在说清楚

整理目标、反目标、用户、数据、外部系统、不可逆操作、可靠性要求和仍未确认的问题。没有答案就写“未知”，不允许自动补成听起来合理的答案。

留下：Meta、风险清单、术语表和开放问题。
第 2 步

把自然语言变成可推翻的声明

每个重要要求都有稳定编号、适用范围、反例和最低证据要求。比如“库存可靠”要改写为并发、回滚和任何合法操作后库存均不为负。

留下：声明、不变量、反例、风险等级和验证方法。
第 3 步

画出问题与工作的坐标

世界图描述实体、关系和业务事实；任务图描述状态与推进；架构说明边界、数据归属、失败与恢复。每个设计元素必须服务某条声明。

留下：图、状态机、接口契约、数据与信任边界、追踪关系。
第 4 步

先固定问题，再开始实现

对规格、设计、验证计划和工具版本计算摘要。实现可以变化，但任何改变问题定义或验证标准的动作都会使已有证据失效并重新确认。

留下：冻结版本及其摘要。
第 5 步

实现与挑战分开进行

一个上下文负责实现，只看到公开契约；另一个上下文负责从风险、历史事故和业务规则中设计隐藏样例、属性、组合和故障。两边在候选制品完成后汇合。

留下：候选制品、公开测试、隐藏挑战摘要和来源。
第 6 步

让同一个候选物接受多种观察

编译、静态检查、单元、契约、集成、端到端、属性、变异、安全、供应链和回滚都指向同一个制品。报告摘要不能代替原始结果。

留下：结构化证据、原始日志摘要、环境与验证器身份。
第 7 步

比较承诺与现实

抽取实现图和运行图，与意图和架构逐项比较。检查禁止依赖、越界数据流、状态缺口、未声明动态边和变更影响范围。

留下：明确差异、动态盲区和受影响声明。
第 8 步

把测试预算花在最不确定的地方

根据风险、耦合、历史缺陷和当前证据空白选择下一轮组合与故障。失败后自动缩小到最小反例；没有信息增益的重复测试停止运行。

留下：采样记录、最小反例、未覆盖组合和停止理由。
第 9 步

把机器无法回答的问题交给人

只提交那些会明显改变结论的问题：业务语义冲突、不可逆风险接受、外部事实缺失。人的回答立即转成新声明、反例或规则，再跑一次相关验证。

留下：决策、责任人、适用范围和被它影响的旧证据。
第 10 步

只有证据收敛后才能交付

所有必要声明达到对应风险要求；没有未处理反例、未知高风险和过期例外；供应链与回滚可验证；仍然存在的限制被清楚地写进交付说明。

留下：可重放的交付包，而不是一句“已完成”。
08 · 最后，人只需要看什么

把复杂性留给系统，把责任留给人

人不需要吞下全部实现细节，但必须看见不能被机器替代的事实。

设计内核项目目标、关键不变量、风险边界是否正确。
反例与未知哪里失败、哪里看不见、哪些外部事实尚未验证。
声明与证据每项要求由什么独立结果支持，证据是否仍有效。
剩余风险例外、回滚、真实环境限制以及需要谁承担。

因此，“不读代码”不是把判断交给 Agent，而是把人的判断放在更高杠杆的位置。机器负责穷尽纪律，人负责定义意义；机器负责不断压缩，人负责在最后的分叉处给出真实世界的答案。

这场讨论最终形成的一句话：用有限模板建立坐标，用图连接承诺与现实，用测试和采样持续排除错误，用可重放证据约束 Agent，再把仍不可区分的少量问题交给专家。项目不是因为“全绿”而完成，而是因为重要的不确定性已经被解释、消除或明确承担。

APPENDIX A · NORMATIVE

Agent 执行契约

本附录是机器执行规范。除非项目配置显式覆盖，Agent 必须按以下标识、状态、产物、转移条件和停止条件执行；不得依赖上文叙事自行补充语义。

A1. 规范词

词唯一含义
MUST不满足即不得进入下一状态。
MUST_NOT出现即将受影响证据标记为 INVALID。
SHOULD默认执行；跳过时必须生成带 owner 和 reason 的例外记录。
MAY可选，不影响状态转移。

A2. 唯一标识与枚举

project_id        := PROJECT.<ASCII_SLUG>
claim_id          := CLAIM.<DOMAIN>.<NNN>
challenge_id      := CHALLENGE.<CLAIM_ID>.<NNN>
run_id            := RUN.<UTC_YYYYMMDDTHHMMSSZ>.<8_HEX>
evidence_id       := EVIDENCE.<CLAIM_ID>.<RUN_ID>.<NNN>
exception_id      := EXCEPTION.<CLAIM_ID>.<NNN>
rule_id           := RULE.<DOMAIN>.<NNN>

risk_level        := R0 | R1 | R2 | R3
assurance_level   := A0 | A1 | A2 | A3 | A4
claim_status      := UNKNOWN | PASS | FAIL | INVALID | EXCEPTED
decision          := PASS | CONDITIONAL | FAIL | INVALID

A0 := 无可用证据
A1 := 可构建且静态/结构约束通过
A2 := 行为、反例、属性与变异验证达到计划阈值
A3 := 真实或等价运行环境、故障、SLO 与回滚已验证
A4 := 指定有限内核具有机器检查的形式化证明

A3. 角色与隔离

role_id允许输入允许输出MUST_NOT
ORCHESTRATOR全部摘要、状态和公开结果调度、状态转移、问题包修改验证原始结果
SPECIFIER用户输入、外部事实、现有设计Meta、claim、架构与验证计划把未知项推断为已确认事实
BUILDER已冻结公开规格与公开测试源码、锁文件、SBOM、候选制品读取隐藏挑战；修改策略或阈值
CHALLENGERMeta、claim、风险、历史缺陷隐藏挑战、生成器、故障计划读取 Builder 推理记录

SKEPTIC图、git、历史结果与证据缺口排序、异常、候选规则直接改变 claim_status

A8. 执行动作流

procedure EXECUTE_PROJECT_DELIVERY(project_root):
  01. load .zkge/project.yaml; validate schema; else STOP(INVALID_CONFIG)
  02. inventory external facts; unresolved fact => UNKNOWN; MUST_NOT infer confirmation
  03. register TCB; run verifier self-tests and historical-bug replay
  04. if calibration fails: STOP(UNCALIBRATED_VERIFIER)
  05. compile Meta -> claims -> architecture -> verification plan
  06. validate: stable IDs, owners, risk, oracle, counterexample, trace edges
  07. if high-risk UNKNOWN exists: emit QUESTION_PACKET; STOP(WAITING_FOR_OWNER)
  08. hash and freeze specification, policy, public challenge, toolchain
  09. dispatch BUILDER and CHALLENGER in isolated contexts
  10. receive artifact; bind source/artifact/SBOM/build-environment digests
  11. run public + hidden challenges against the same artifact digest
  12. emit raw result digests; normalize results into evidence schema
  13. extract implementation/runtime graphs; compare with intent/architecture
  14. compute claim_status, assurance_level, coverage debt, residual uncertainty
  15. while convergence predicate is false:
        a. if open counterexample: minimize; route to BUILDER or SPECIFIER
        b. if evidence INVALID: rerun from earliest changed digest
        c. if high-risk UNKNOWN: emit one highest-information QUESTION_PACKET
        d. else select next challenge by A9; run; update evidence
        e. if no legal next challenge can reduce uncertainty: STOP(BLOCKED)
  16. convert accepted incidents into rule candidates
  17. replay each candidate against positive + negative history
  18. activate rule only after deterministic translation and owner approval
  19. evaluate A10 handoff predicate
  20. if false: decision := FAIL | INVALID | CONDITIONAL; MUST_NOT claim complete
  21. if true: write .zkge/handoff/manifest.json; state := S8_HANDOFF_READY
end

A9. 采样与停止

risk_weight(R0,R1,R2,R3) := (1, 3, 10, 30)
level_gap(i) := max(required_assurance_level(i) - actual_assurance_level(i), 0)
unknown(i) := 1 when claim_status(i) = UNKNOWN else 0
invalid(i) := 1 when claim_status(i) = INVALID else 0
counterexample(i) := 1 when an open counterexample exists else 0

residual_uncertainty U := Σ risk_weight(i) *
  (level_gap(i) + unknown(i) + invalid(i) + 2 * counterexample(i))

challenge_priority(c) :=
  expected_closed_risk_weight(c)
  * affected_claim_count(c)
  * observability_gap(c)
  / max(execution_cost(c), 1)

select next challenge := argmax(challenge_priority(c))

sampling_stop :=
  no_open_counterexample
  and no_R2_R3_unknown
  and all_required_levels_met
  and no_available_challenge_with_positive_expected_closed_risk_weight

residual_uncertainty 仅用于排序与预算，不得替代逐条 claim 判定。任何 R3 FAIL/INVALID/UNKNOWN 均不可被其他 claim 抵消。

A12. 绝对停止条件

conditionrequired_action
SPEC_CONFLICT停止实现；提交冲突事实、受影响 claim 和最高信息增益问题。
ORACLE_MISSING_R2_R3停止验证；不得由 Builder 或同源 Agent 补写 oracle。
EVIDENCE_DIGEST_MISMATCHdecision=INVALID；从最早变化输入重新执行。
VERIFIER_UNCALIBRATED禁用该 verifier 的所有门禁用途；已有证据全部 INVALID。
