二、核心领域层：语义心脏与授权内核

四个关键角色：对象注册、关系建模、数据装配、授权内核。这是为什么它必须是平台中枢。

核心领域层的四个能力维度

能力业务含义技术表达
对象注册定义公司如何统一理解业务——"销售订单"有统一的 ID、字段和状态集合销售订单、客户、合同、发票、样品、产品。每个对象有唯一 ID、标准字段和生命周期状态机。
关系建模"谁负责这个客户"、"谁参与过这张订单"——业务关系是 ReBAC 的事实依据客户负责人关系、订单参与人关系、业务单元归属关系。以关系图为锚支撑"为什么有权限"判断。
数据装配一个完整的"客户"对象可能由客户库 + CRM + Wiki 笔记 + 最近订单状态组装而成每个领域对象声明其数据来源清单（供应链依赖）。装配逻辑集中，不在各模块重复。
授权内核"这个人通过什么业务关系、能看这个对象的哪些字段"——在领域层执行对象级、记录级、字段级。双层模型：服务授权（能不能调）+ 数据授权（能看什么）。
为什么授权必须在领域层执行：只有领域层同时拥有对象定义、关系数据和调用上下文。如果在服务层执行→每个模块重复实现。如果在数据库层→粒度只能到表。 这是 Agent 可以自由编排服务但数据授权永远绕不过领域层的底层保证。

三、业务服务层：原子服务 · 流程服务 · Agent 自主编排

v3 的核心修正。业务服务层不只是"单个服务的编排"，而是三层粒度共存。 它们的共同点：都通过同一套服务注册体系、同一套授权核查、同一套版本管理机制。 它们的差异：粒度不同，适用场景不同，且形成自然的演进路径。

🧱 原子服务 Atomic

单个不可拆的业务能力。

  • 查订单状态、创建订单草稿
  • 查库存、查客户信息
  • 发送质检单、通知发货
  • 查 Wiki 笔记、写入 Wiki 笔记

特点：独立注册、独立授权、独立版本。最细粒度的乐高积木。所有上层编排都基于原子服务。

🧩 流程服务 Workflow

由多个原子服务 + 审批节点 + 决策节点预组合而成的业务流程。

  • "订单审批流程" = 受理→补全→创建草稿→人工审批→写入ERP→通知履约
  • "样品申请流程" = 查客户→推样品→创建申请→主管审批→通知仓库→追踪物流
  • "合同签署流程" = 查模板→生成草稿→法务审批→盖章→寄出→追踪签收

特点：流程本身也是可注册、可调用、可版本化的一等服务。是已经用几块原子积木搭好的"大块积木"。

🤖 Agent 自主编排 Autonomous

Agent 基于工单上下文动态决定调用哪些原子服务或流程服务，不依赖预定义的调用顺序。

  • 建联时同时查客户画像 + Wiki笔记 + 竞品信息 + 产品资料
  • 根据客户类型选择不同的流程服务（大客户走完整审批、小客户走快速通道）
  • 识别异常模式后自主触发异常处理子流程

特点：不预设顺序。Agent 像从乐高盒子里自由选取积木来搭建——可以取原子积木，也可以取现成的组合积木。

三者关系：原子服务是基础积木。流程服务是用几块积木搭好的大块积木——它本身也是一块积木。 Agent 自主编排是自由搭建——但从盒子里拿的时候，既可以是原子积木也可以是组合积木。 三者不冲突、不替代，而是互补共存。它们的共同点：都通过核心领域层获取装配好的、授权合规的领域对象。

流程服务的设计要点

流程即服务：Workflow as a Service

设计维度含义设计原则
注册为服务 流程被注册为平台的一等公民——有服务 ID、有输入输出声明、有版本号 流程服务与原子服务共用同一套契约体系；外部调用者不感知内部实现
混合节点编排 流程中包含三类节点：原子服务调用、人工审批节点、AI Agent 决策节点 基于 workflow.md 调研结论——原生支持"人工审批节点"与"AI Agent节点"混合编排，确保从人审到Agent的平滑演进
人工审批节点 挂起流程执行，等待指定角色确认或驳回。支持通过、退回、会签、并行网关 审批节点是流程的一等节点类型——不是"外部回调"，而是流程引擎内建能力
版本化与灰度 流程服务与原子服务一样支持版本并存、灰度发布、回退 变更审批节点的参与者或替换为 AI 决策节点时可以安全灰度
状态持久化 流程执行状态（当前节点、等待谁、已执行历史）持久化，支持暂停、恢复、超时处理 流程中断后可从断点恢复——与工单服务的"工单上下文"协同而非冲突

从"人审"到"AI Agent 替代"的渐进演进路径

这是 workflow.md 调研的核心诉求——不能一开始就全量 AI 审批，需要一条从人审逐步过渡到 Agent 的路径。流程服务的混合节点编排天然支持三种渐进方式：

🔄 节点替换

将流程中的某个"人工审批节点"直接替换为"AI Agent 决策节点"。先在灰度环境验证替换后的正确率和异常率，达标后逐步扩大范围。BrokerFlowAI / AStudio / n8n 原生支持此模式。

💡 AI 辅助审批

保留人工审批节点，但 AI Agent 先给出审批建议（"建议通过：该客户历史回款良好，订单金额在授信额度内"），供人参考后决策。降低人的认知负担，同时人保留最终决策权。

⚡ 策略驱动路由

设定规则：简单场景（金额 < 阈值、客户白名单、标准产品）AI 自动批；复杂场景（大额、新客户、非标产品）转人工审批。n8n 的 HITL 节点和 LightAgent 的审批节点均支持此模式。

平台不绑定特定工作流引擎：流程服务的抽象——注册、混合节点编排、审批节点、版本化——是平台级概念。 底层可以用 BrokerFlowAI（LangGraph 原生审批）、n8n（HITL 可视化编排）、Warm-Flow（极轻量 Java BPM）等来实现。 选型取决于团队技术栈和场景需求，但平台层面的服务注册契约是统一的。

核心领域层从两条供应链获取原始数据 → 装配为领域对象 → 施加授权过滤 → 返回给业务服务层（无论原子、流程还是 Agent 编排）。

五、LLM Wiki：极轻量、加密、个人的知识笔记

销售和商务积累的隐性知识（"佘总说半吨C68"、"这个客户偏好圆通"）需要极轻量的知识载体。

🗒 LLM Wiki 核心设计

  • 极轻量存储：每个人的知识笔记是一个加密 SQLite 文件。Agent 通过 SQL 读写，无额外 API 层。
  • 加密与授权天然一体：默认仅本人可见。授权共享 = 临时密钥授权。天然处理了"销售怕被替代"的防御心理。
  • Agent 可持续维护：每次工单完成后，Agent 提取关键发现写入 Wiki。"编译一次、持续复合"——不是每次都重新推导。
  • 从个人到团队的渐进路径：高频高价值笔记经 owner 审批后升级为共享知识。

LLM Wiki 的生命周期

  • 创建：新人入职时自动创建加密 SQLite，注入初始模板
  • Agent 写入：每次工单完成后提取关键发现
  • Agent 查询：新指令进来时检索补全
  • 授权共享：Owner 授权特定同事或 Agent，共享有有效期
  • 升级：经审批后结构化发布到共享知识图谱

为什么选 SQLite 加密

  • 不去用中心化知识库——太重
  • 不去用纯文件——Agent 读写不便
  • SQLite 加密文件 = 恰好够用：结构化但不重、加密但无需运维、Agent 友好但 owner 可控

六、业务模块如何接入、如何升级

v3 中，业务模块接入时可以提交原子服务、也可以提交流程服务。两者走同一套契约。

接入答案：提交"六件套契约"——业务对象、动作（原子或流程）、输入输出、权限审计、数据供应链依赖。流程服务额外声明其内部节点编排和审批节点定义。
声明业务对象使用客户、订单、发票，或注册新对象。
声明动作原子服务：查询、创建、提交。或流程服务：声明子服务+审批节点+决策节点。
声明输入输出字段、状态、错误码和上下游事件。
声明权限审计谁能做、何时确认、哪些字段要脱敏。
声明数据供应链依赖内部供应链 + 外部供应链的数据来源声明。
升级答案：新旧版本并存——原子服务升级和流程服务升级走同一套灰度、回放、回退机制。流程服务升级时可以安全地将人工审批节点替换为 AI 决策节点。
登记新版本说明规则、字段、接口和权限变化。
兼容性检查契约校验；破坏性变化必须提供迁移方案。
历史工单回放用脱敏样本比较新旧结果。
灰度与观察限定组织/用户/比例，包括流程服务节点替换的正确率和异常率。
切换或回退审计记录版本；未达门槛一键恢复旧版。

八、授权设计：双层模型 + 流程服务的授权覆盖

服务授权（能不能调）→ 数据授权（能看什么）。流程服务作为一等服务，其内部每个原子调用的授权都需满足。

流程服务的授权特殊性：一个流程服务可能调用 5 个原子服务。调用者需要对这 5 个原子服务都有调用权限——流程服务不能"绕过"其内部调用的服务授权。 但可以预授权：当调用者被授予"订单审批流程"的调用权时，平台自动检查其对内部所有原子服务的权限，缺失的提示补授权。
授权视角业务表达在领域层的实现
岗位视角我是商务/销售/仓库/主管领域层内建角色-对象-动作映射表
客户负责视角谁负责这个客户，谁看客户相关订单以"客户负责人"关系为锚
订单参与视角参与过这张订单的人可处理相关事项以"订单参与人"关系为锚
🗒 LLM Wiki 视角个人笔记默认仅本人可见SQLite 文件加密密钥为授权锚点
🔄 流程服务调用视角能调用"订单审批流程"的人需对所有内部原子服务有权限预授权检查——平台自动验证，缺失补授权

提供结构化事实、非结构化知识和个人经验笔记。不直接对业务服务层开放——必须通过领域层。

结构化事实

  • 用于查询、校验、统计、台账同步
  • 不直对业务服务层开放

十一、平台如何分析、整理并推动业务迭代

记录经领域层访问了哪些对象、做了什么、人工审批点在哪个节点卡住。
整理按对象、异常类型、审批耗时、Wiki 置信度变化自动聚合。
建议识别可被AI替代的审批节点、Wiki中可升级的高频知识。
验证审批后生成候选版本，回放、灰度、对比、回退。
信号结论改进决策人
订单审批流程中"主管审批"节点平均耗时 4h，通过率 99.2%该节点可被 AI 策略替代升级为策略驱动路由：金额<阈值自动批销售运营
某销售 Wiki 中"物流偏好"笔记被高频跨个体检索隐性知识有团队价值建议 owner 升级为共享知识销售本人

十二、低成本 Pilot：6–8 周可演示闭环

第 1–2 周 · 固定契约与样本确认对象、权限、模块边界和供应链依赖；选脱敏工单。定义第一个流程服务："订单审批流程"。
第 3–4 周 · 打通最小闭环完成工单、授权、审计、网关；实现订单审批流程（人工审批节点先由模拟审批替代）。
第 5–6 周 · 小范围真实运行1 个业务单元、5–10 名用户；关键写操作人工确认；验证流程服务的审批节点运作。
第 7–8 周 · 升级演示与复盘演示流程服务版本升级（例如将模拟审批替换为 AI 辅助审批）；验证灰度回退。

五项"继续投入"门槛

  1. 业务闭环：至少 80% 试点工单在一个入口看见完整状态。
  2. 领域层中枢验证：所有数据读写经核心领域层；原子和流程服务不直连数据源。
  3. 流程服务验证：至少一个流程服务包含人工审批节点并成功完成端到端闭环。
  4. 安全追溯：每次读取、提交、审批都能回答"谁、为何、哪个版本"。
  5. Wiki 有效性：至少一位销售的个人 Wiki 在 Pilot 期内形成可度量的补全准确率提升。

v3 架构修正摘要：核心领域层是语义心脏——所有数据在此装配、所有授权在此执行。业务服务层以三层粒度承接编排—— 原子服务（单个能力）、流程服务（原子+审批+决策组合）、Agent 自主编排（基于上下文自由选取）。
流程服务是一等公民——可注册、可版本、可灰度、可演进。从"人工审批"到"AI Agent替代"的三条渐进路径（节点替换、AI辅助、策略驱动）天然内建于混合节点编排模型。
