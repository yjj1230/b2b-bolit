ReBAC 授权表（SpiceDB）：
怎么定「谁、能看什么、能做什么」

这不是技术文档。这是一张你可以自己填的表格——用它描述"在公司里，谁因为什么关系，能看到备货单的哪些字段，能发起发货还是只能看进度"。填完了，系统就按你的意思跑。本项目的授权引擎是 SpiceDB（Google Zanzibar 论文的最成熟开源实现，Netflix 等验证）。

① 人谁要访问
② 关系凭什么能访问
③ 权限能看什么 · 能做什么
核心概念 授权表模板 场景实填 特殊场景 全景汇总 Excel 共享授权表

ReBAC 的核心：你能不能访问，不取决于你是哪个部门，而取决于你跟这条信息之间有没有业务关系。SpiceDB 用"关系元组"存储这些关系，毫秒级判定。

① 人

就是登录系统的那个人。
商务张明、仓管王强、客户联系人李客户。
在 SpiceDB 里统一叫 user。

② 关系  ← ReBAC 的核心

这个人和数据之间的业务关系。
"张明是天华科技备货单的负责人"
"王强被分配了发货单 SHP-02"
"李客户是天华科技的客户联系人"

关系是事实，不是标签。SpiceDB 把它存为"关系元组"：prestock:PS-8801#owner@user:zhang_ming。

③ 权限

基于关系，能做什么。
能查看、能改额度、能发起发货。
能确认、能驳回、能上传凭证。

可以精确到：这条记录的这些字段你能看（如客户看不到价格）。

一句话：ReBAC = "因为你跟这个东西之间有关系，所以你才能动它。"
跟传统"因为你是销售部的所以你都能看"完全不同——关系比部门标签更精确。你每次在企微群里判断"这人能不能看这张备货单"，本质上就是在做 ReBAC。SpiceDB 就是那个帮你自动判定的引擎。

三、你的真实场景，填进授权表

场景 A：商务在企微客户群开备货单

日常：张明在天华科技客户群里打开侧边栏，系统自动识别出这是天华科技的群。张明选择一张已生效的采购订单，填写备货额度 1000kg，提交。审批通过后额度生效。

张明 = 天华科技的 account_owner
+ 订单创建人		 天华科技的已生效订单 订单全部字段 开备货单 长期
售后·李娜 无关系
（既非 account_owner 也非 creator）		 天华科技的订单 — 不能开备货单 看不到

开备货单需要两个关系之一：你是这个客户的负责人，或者你是这张订单的创建人。不是"商务部门的人都能开"——是"跟这个客户/订单有具体关系的人才能开"。

场景 B：商务改备货额度、发起多次发货

日常：张明的备货单 PS-8801 审批通过了（状态=ACTIVE），总额度 1000kg。他先发 300kg，再发 200kg，系统实时显示剩余 500kg。他想把总额度改到 1200kg。

每次发货的状态·物流		 查看 · 改额度

仓管·王强 被分配仓管
（是 warehouse_manager 但非 owner）		 备货单 PS-8801 可查看 不能改额度
不能发起发货		 —
注意：SpiceDB 只管"关系对不对"，不管"额度够不够"。
王强是 warehouse_manager，SpiceDB 允许他查看备货单，但不允许他改额度或发起发货——这些权限只给 owner。
如果张明想发 2000kg 而总额度只有 1000kg——SpiceDB 会放行（因为他是 owner），但 Workflow 会拒绝（因为超额）。
这叫"两道门"：第一道门（SpiceDB）判断关系，第二道门（Temporal Workflow）判断状态和额度。

场景 C：仓管确认或驳回被分配的发货单

租户隔离是 SpiceDB 的内置能力。每个权限定义末尾都有 & tenant->member——即使你有 owner 关系，如果你不属于这个租户，权限求交（intersection）会拒绝你。业务数据库和对象存储额外加一层租户校验，形成三道防线。

这是 SpiceDB 的 Caveats（条件授权）——阶段二才上线。
它允许在"有关系"的基础上加一个条件判断："你有 requester 关系，但只有创建后 30 分钟内才能作废"。
Pilot 第一版不包含 Caveats——状态和时间窗由 Workflow 判定。阶段二再把稳定条件（如作废窗口）下沉到 SpiceDB。

四、两个特殊但非常重要的场景

场景 G：临时代办

日常：张明休假三天，让李娜帮忙盯着。"这三天，我负责的天华科技备货单你来处理。回来之后就不用了。"
谁凭什么关系对什么能看什么能做什么有效期批准的
商务·李娜 临时委托
张明委托李娜代管天华备货单		 天华科技所有备货单
及关联发货单		 跟张明本人看到的一样 张明能做的
李娜都能做		 7/13–7/16
3天后自动删除关系元组		 张明本人授权
主管确认
SpiceDB 怎么实现临时代办：
系统给 SpiceDB 写入一条带有效期的关系元组：prestock:PS-8801#owner@user:li_na。
3 天后，Outbox 投影器自动调用 DeleteRelationships 删除这条关系——李娜权限自动收回。
不需要管理员手工改权限。张明点"委托给李娜，7/13-7/16"，系统自动操作。
💡 Outbox 投影器是什么（业务版）：
你可以把它理解成"自动同步员"——每当系统里发生了一件会影响权限的事（比如张明创建了备货单、王强被分配了发货单、李娜被委托代办），系统会把这件事记在一张"待办清单"（Outbox 表）里。然后"自动同步员"（投影器）会逐条把这些关系变化同步到 SpiceDB 授权引擎里。这样就保证了业务数据库里存的关系 = SpiceDB 里判定的关系，不会出现"数据库说张明是负责人但授权引擎不知道"的情况。
技术版：Transactional Outbox 模式。业务事务内同时写入业务数据 + outbox_event 表，Go 投影器异步消费 outbox → 调用 SpiceDB WriteRelationships / DeleteRelationships。投影幂等（同一条 event 重复消费不产生重复关系），失败可重放。详见 golang_pilot_temporal_rebac.html §7.3–7.4。

六、规模化授权：3 个商务 × 几百个客户怎么管

前面的场景都是以"一个人、一张单"讲的。但真实的企业是：3 个商务，每人负责几百个客户，每个客户有备货单、发货单、凭证。如果逐条手填授权表，表会膨胀到几千行，根本维护不动。这一节告诉你：怎么用 SpiceDB 的 RBAC + ReBAC + ABAC 三层能力，让授权表保持十几行的规模，同时覆盖几千个客户。

真实痛点：张明负责华东区 300 个客户。如果授权表写成"张明→客户 C001 的负责人→开备货单"、"张明→客户 C002 的负责人→开备货单"……光是张明一个人就要 300 行。3 个商务就是 900 行。每次有客户新增、商务调岗、客户交接——都得改表。

你要的不是"张明能看 C001、C002、C003……"，而是"张明是华东 A 组的商务负责人，对这个组里的所有客户都能开备货单"。

6.1 核心思路：把"策略"和"数据"分开

SpiceDB 是 RBAC + ReBAC + ABAC 的结合体。规模化授权的关键是不要把"谁对谁有什么权限"全写到一张表里——而是拆成三层，各自独立维护。

6.2 RBAC 层：角色模板——"商务负责人能做什么"写一次

把"商务负责人能做什么"定义成一个角色模板。所有商务共享这个模板——不管是张明还是李娜，只要他们有"商务负责人"这个角色，就自动获得模板里的所有权限。这就是 RBAC（基于角色的访问控制）。

业务语言

"商务负责人"这个角色，能做三件事：
① 开备货单
② 改额度
③ 发起发货

不用管谁是商务负责人——谁戴这个帽子，谁就能做。

SpiceDB 怎么实现

在 Schema 里定义角色和授权绑定：
definition role {
relation can_create_prestock: user:*
}
definition role_grant {
relation role: role
relation grantee: user
}

效果

张明获得"商务负责人"角色 → 自动获得所有关联权限。
新来一个商务 → 授一次角色 → 全自动。
商务调岗 → 收回角色 → 权限自动消失。

🗒 角色授权模式（SpiceDB ZSL，阶段二增强）

// === RBAC 层：角色模板定义 ===
// 试点 v1 使用直接关系 (account_owner: user)，更简单。
// 角色授权模式留作"需要自定义角色管理 UI"时的阶段二升级路径。

definition role {
    relation can_create_prestock: user:*      // 通配符: 拥有此角色的任何人都能开备货单
    relation can_change_quota: user:*
    relation can_request_shipment: user:*
    relation can_close: user:*
}

definition role_grant {
    relation role: role
    relation grantee: user

    permission create_prestock = role->can_create_prestock & grantee
    permission change_quota = role->can_change_quota & grantee
    permission request_shipment = role->can_request_shipment & grantee
    permission close = role->can_close & grantee
}

// customer 的 account_owner 可以接受 role_grant 作为 subject:
definition customer {
    relation account_owner: user | role_grant  // 直接关系 OR 角色授权
    // ... 其余 relation 不变 ...
}

// 运行时: 给张明授权"商务负责人"角色
// WriteRelationships: role_grant:sales_owner_grant#grantee@user:zhang_ming
// WriteRelationships: role_grant:sales_owner_grant#role@role:sales_owner
// 此后张明对所有他 account_owner 的客户自动拥有 sales_owner 角色的全部权限
试点 v1 不需要这个。v1 直接用 account_owner: user（简单直接关系），角色授权模式留作阶段二——当业务方说"我需要一个界面来管理谁有什么角色"时再升级。两种模式可以共存：已有的客户用直接关系，新增客户或需要批量管理的客户走角色授权。

6.3 ReBAC 层：关系即事实——CRM 里改了，SpiceDB 自动同步

"张明是华东新材的负责人"这是一条关系事实，它不应该由授权表来维护，而应该由 CRM（客户管理系统）来维护。授权表只管"负责人能做什么"，CRM 管"谁是负责人"。这就是 ReBAC 的规模化核心——权限跟着关系走。

CRM 里维护（日常操作）
张明 = 华东新材的 account_owner
王强 = SHP-02 的 warehouse_operator
李客户 = 天华科技的 contact

业务在 CRM 里改就行
→
Outbox 自动投影（无人值守）
customer:tianhua#account_owner@user:zhang_ming
shipment:SHP-02#warehouse_operator@user:wang_qiang

关系变化自动同步到 SpiceDB
为什么规模化必须这样：张明调离 → CRM 里把华东新材的负责人改成李娜 → Outbox 自动删除旧元组、写入新元组 → 李娜即时获得所有华东新材备货单的权限，张明即时失去。不用在五个地方手动改。一个商务换岗只改 CRM 一条记录，几百个客户的授权自动联动。这就是 ReBAC 的核心威力。

可选优化：Subject-Set 分组

如果业务方希望"华东 A 组的成员自动成为 A 组内所有客户的负责人"，可以把 account_owner 的 subject 扩展为团队：

definition customer {
    relation account_owner: user | sales_team#member
    // 可以是具体的人 (user:zhang_ming)，也可以是"华东A组的所有成员"
}

团队加人 → 只需要在 sales_team 里加一条 member 元组，新人自动获得组内所有客户的权限。同样标注为阶段二可选。

6.4 ABAC 层：条件授权——静态属性 vs 动态条件

ABAC（基于属性的访问控制）让你在"有关系"的基础上附加条件。但 SpiceDB 里必须区分两种 ABAC——用错了会影响性能。这是很多团队踩坑的地方。

类型适合什么怎么在 SpiceDB 里做例子
静态属性不随请求变化的属性
（订单状态、客户等级、合同类型）		建模为关系对象 + 交集箭头
不要用 caveat！		"只看已发货且待开票的订单"
→ 把 order_status 建模为对象
→ 用 & status_shipped & status_pending
动态条件只在请求时刻才知道的数据
（当前时间、IP、地理位置）		Caveats（条件表达式）"发货单创建后 30 分钟内可作废"
→ caveat within_void_window(now, created_at) { now < created_at + 30min }
⚠️ 关键规则（来自 SpiceDB 官方文档）："Using caveats for static data can have negative performance impacts. Static attribute data should always be modeled in the schema."
翻译：不要把订单状态写进 caveat。静态属性应该建模为 SpiceDB 里的关系对象。caveat 只用于时间、位置等在请求时才变的数据。

示例：静态属性建模（阶段二评估）

// === 把"已发货待开票"建模为关系对象，而不是写 if-then ===
definition shipment_status {
    relation member: shipment
}

definition shipment {
    relation status_shipped: shipment_status
    relation status_evidence_complete: shipment_status
    // ... 其余 relation 不变 ...

    permission can_auto_complete = status_shipped & status_evidence_complete
    // 两个条件都满足 → 可以自动结案
}

⚠ 试点 v1 状态门由 Temporal Workflow 确定性校验、SpiceDB 聚焦关系授权——符合设计文档"两道门"原则。静态属性下沉 SpiceDB 是阶段二评估项。

📋 怎么读这张表的三层结构：
T1-T6（RBAC 模板层）= 业务要填的策略——定义每种角色能做什么、能看到哪些字段。约 6 行，很少改。
D1-D5（ReBAC 数据层）= 不需要在授权表里填——这些由 CRM 或 Workflow 自动产生、Outbox 自动投影到 SpiceDB。这里只放几个例子说明"关系数据长什么样"。实际运行时，张明→天华科技的 account_owner 关系在 CRM 里维护，改一条就全自动联动。
C1（ABAC 条件层）= 在"有模板权限 + 有关系数据"之后附加的额外条件，如"仅创建后 30 分钟内可作废"。
X1-X3（拒绝示例）= 展示三种拒绝原因：模板里没这个权限、数据里没这个关系、租户不匹配。
每个单元格有上下两行——上面是业务语言，下面是程序映射（SpiceDB 标识符）。程序员会写脚本自动转换。
📋 怎么用这张表： ① T1-T6 模板行 = 你要填的。把此表复制到 Excel，在模板区域定义"每种角色能做什么"。跟业务团队讨论："客户负责人应该能做什么操作？能看到哪些字段？"填进模板行。
② D1-D5 数据行 = 不需要在授权表里填。这些由 CRM 和 Workflow 自动产生。授权表里保留这几行只是说明"存在这种类型的关系数据"，实际运行时有几千行。
③ C1 条件行 = 特殊限制。如"发货单创建后30分钟内可作废"——这种需要附加时间/位置条件的场景。
④ 后续有新角色 → 在模板区加一行（T7, T8...）。模板区保持 10 行以内。
⑤ 填完的 Excel 发给开发——这就是授权的正式需求文档。开发写脚本从 Excel 生成 SpiceDB Schema。

程序员视角：这张表 → SpiceDB Schema + 关系元组

下面展示上面 13 行授权记录如何映射到 SpiceDB 的 Zanzibar Schema Language（ZSL）和运行时关系元组（Relationship Tuples）。实际项目中，程序员写一个脚本自动从 Excel 读取这张表并生成。

🗒 SpiceDB Schema 定义（Zanzibar Schema Language）

// === 从授权表生成的 SpiceDB Schema ===
// 表的每一行 → 对应的 definition / relation / permission

definition user {}

definition tenant {
    relation member: user          ← X3: 租户隔离的基础
}

definition customer {
    relation account_owner: user  ← T1: 客户负责人
    relation contact: user         ← T4/D3: 客户联系人
    relation tenant: tenant         ← X3: 租户绑定

    permission view = (account_owner + contact) & tenant->member
    permission manage_fulfillment = account_owner & tenant->member  ← T1
}

definition order {
    relation creator: user          ← T1: 订单创建人也可开备货单
    relation customer: customer
    relation tenant: tenant

    permission view = (creator + customer->view) & tenant->member
    permission create_prestock = (creator + customer->manage_fulfillment) & tenant->member  ← T1
}

definition prestock {
    relation order: order
    relation owner: user             ← T2/D5: 备货单负责人（含临时代办）
    relation warehouse_manager: user  ← T2: 备货单负责人（可查看，不可改额度）
    relation tenant: tenant

    permission view = (owner + warehouse_manager + order->view) & tenant->member  ← T2
    permission change_quota = owner & tenant->member          ← T2
    permission request_shipment = owner & tenant->member     ← T2
    permission close = owner & tenant->member                 ← T2
}

definition shipment {
    relation prestock: prestock
    relation requester: user           ← T5/C1: 发货发起人
    relation warehouse_operator: user  ← T3: 被分配仓管
    relation customer_contact: user    ← T4: 客户联系人
    relation tenant: tenant

    permission view = (requester + warehouse_operator + prestock->view) & tenant->member  ← T3/T5
    permission confirm = warehouse_operator & tenant->member    ← T3
    permission reject = warehouse_operator & tenant->member      ← T3
    permission void = requester & tenant->member                ← C1 (阶段二+Caveat)
    permission append_evidence = (requester + warehouse_operator + customer_contact) & tenant->member  ← T3/T4/T5
    permission view_evidence = (requester + warehouse_operator + customer_contact) & tenant->member   ← T4
}

definition evidence {
    relation shipment: shipment
    relation uploader: user            ← T6: 凭证上传者
    relation tenant: tenant

    permission view = (uploader + shipment->view_evidence) & tenant->member  ← T6
    permission append_version = shipment->append_evidence & tenant->member    ← 凭证追加继承
}

// === 授权表每一行 → 运行时 WriteRelationships 元组 ===
// 这些是 SpiceDB 实际存储和判定的"关系事实"

// D1: 张明 = 天华科技的客户负责人
// 张明 = PO-042 的创建人
customer:tianhua#account_owner@user:zhang_ming

// T2: 张明 = PS-8801 的负责人
prestock:PS-8801#owner@user:zhang_ming

// D2: 王强 = SHP-02 的仓管员

// 李客户 = SHP-02 的客户联系人

// D4: 王客户替换李客户

程序员怎么用这张表：
① 扫描授权表 Excel 的每一行，提取 subject relation resource permission caveat
② 汇总所有不同的 relation 和 permission → 生成 SpiceDB Schema（.zed 文件）
③ 根据每行的业务场景 → 生成 WriteRelationships 调用（在备货单创建时、发货单分配仓管时、委托时等）
④ 写一个脚本自动做这个转换——Excel 表就是你的 Single Source of Truth。
⑤ Schema 变更走 PR → 迁移 → 授权矩阵测试（A2黄金矩阵）→ UAT 流程，确保不会意外破坏现有权限。
为什么这张 Excel 表是共享 Single Source of Truth：
业务侧：你只需要维护这十来行（以后可能到 20-30 行）——每次有新角色、新关系、新权限，在 Excel 里加一行。
开发侧：不会出现"业务说的权限跟代码里写的不一样"——因为代码是从这张表自动生成的。
审计侧：任何一次数据访问，都能追溯到这张 Excel 表的哪一行授权了它。
未来：这张表可以做成在线表单——搜"张明"就能看到他的全部权限，搜"PS-8801"就能看到谁能动它。测试个体权限的在线界面也可以直接从这张表的数据生成。
