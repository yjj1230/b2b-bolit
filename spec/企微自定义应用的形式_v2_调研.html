1.2 关键官方概念（基本概念介绍）

证据 W1 · 服务端 API 基本概念官方文档 ↗
corpid：企业 ID（每个企业唯一）
userid：成员唯一标识（企业内）
agentid：应用唯一标识（每个自建应用/第三方应用各有 agentid）
secret：应用密钥（换取 access_token 用）
access_token：全局唯一调用凭证（2 小时过期，需缓存刷新）
可见范围：应用对成员/部门/标签的可见性配置（控制谁在工作台看到该应用）

官方定义的四要素（corpid/agentid/secret/access_token）即本项目服务端对接企微的握手基础；「可见范围」= 应用权限的 RBAC 基础。

P5 · 特殊能力 —— 会话存档 / 数据与智能专区 / 原生审批

5.1 会话内容存档（合规留痕）

官方「会话内容存档」path/91360：企业可合规获取员工与客户的会话内容（需员工/客户授权 + 购买增值服务）。实现路径官方明确为：

  • 仅已认证企业可开通；需上传《会话内容使用授权函》
  • 通过「数据与智能专区」path/99941 授权后，meeting_room_id / 文档/文件选择等能力可用
  • 会话存档 SDK：GetChatData 拉取加密消息 → 企业服务端解密 → 存储
边界：会话存档=付费增值 + 授权函 + 代开发/服务商通道（官方 path/91360 明确）；对"群内口头下单审计"场景，这是唯一合规路径，但成本高，非 P0。

5.2 官方原生审批流（可选替代自建）

官方「应用发起审批」path/97202 允许自建应用直接发起企微原生审批（模板自定义、控件自定义、审批人/抄送人指定、回调通知）。

方案审批载体优点缺点
方案 A：自建审批流订单系统内审批与订单状态机同源；可编排复杂闸门（审价→到账→备货→发货→开票）需自建审批 UI/通知
方案 B：企微原生审批企微审批应用审批 UI/通知/移动端原生；模板控件 API 化（97202）审批状态与订单系统需回调同步；复杂多阶段闸门表达受限
建议：以方案 A 为主（订单状态机内嵌审批闸门，模板卡片触达），方案 B 作为轻量备选（如内部费用审批）。

应用形态：自建应用（agentid 自管，无需服务商）✅ 官方支持 path/90665 页面承载：H5 + JS-SDK（零迁移，全能力）✅ path/90513 登录鉴权：OAuth snsapi_base 静默授权 + 服务端 code2userid ✅ path/91335 会话上下文：getCurExternalChat / 获取当前客户ID/群ID ✅ path/100746-100749 消息触达：template_card + 更新卡片 ✅ path/101032/94888 工作台入口：webview 型模板 ✅ path/92535 审批：自建状态机 + 模板卡片（备选：官方审批 97202） 审计留痕：会话存档（P2，付费增值）✅ path/91360

P7 · 能力边界、风险与结论

7.1 官方能力边界（必须知道）

  • 侧边栏仅外部客户会话：聊天工具栏 entry（single_chat_tools/group_chat_tools）只在与客户单聊/客户群生效（官方 91789）；企业内部会话需工作台入口。
  • JS-SDK 必须在企微浏览器内：wx.config 签名（90506）+ 企微内打开；普通浏览器访问需降级提示。
  • access_token 2 小时过期：需服务端缓存刷新（官方 91039），多实例并发需锁。
  • 模板卡片更新有时限：官方规定卡片可更新时长（template_card 更新接口约束），超时需重新发送。
  • 会话存档门槛高：认证企业 + 授权函 + 付费增值（91360），且需代开发/服务商通道启用数据与智能专区。
  • 可见范围 = 权限边界：工作台/侧边栏可见性由应用可见范围控制（90665），角色裁剪需在应用层二次实现（本项目 ReBAC）。

7.2 结论

以企微官方文档为据：「自建应用（H5 + JS-SDK）+ 聊天工具栏（外部会话）+ 工作台（webview 模板）+ 应用消息（template_card）」四件套即覆盖订单履约全部 P0 需求，全部为官方原生支持、零服务商依赖。会话存档为 P2 付费增值项。纷享销客的商用实现（v1 文档）证明该组合在大规模生产环境可行——但技术可行性依据来自企微官方文档本身，不依赖任何厂商。

8.4 结论：项目的技术形态（最终回看）
