0. 结论摘要（TL;DR）

三大支柱的验证结论预期

① 授权：SpiceDB 用「全局角色关系 + 资源级关系 + 条件关系」即可同时表达 RBAC 与 ReBAC，且与现有 pilot 的 7 定义 15 权限可直接演进；字段级裁剪（仓管看不到价格金额）由 BFF 在资源级授权通过后做投影，边界清晰。② 流程：Temporal 以 1 个 OrderWorkflow 主流程 + 3 类子流程（发货 / 转交 / 例外开票）承载四环节，用 Timer 做超时催办、用 Signal 接企微回调，与现有 PrestockWorkflow/ShipmentWorkflow 映射后即可复用大部分骨架。③ 企微（重点）：「客户在群里发言→自动变成下单需求」在技术上完全可行，但只有一条官方通道——「会话内容存档」API；它要求企业认证 + 付费开通 + 员工知情同意，属于合规敏感能力，需在 Phase 0 设决策门。侧边栏 H5、应用消息卡片、回调均为主流成熟能力，风险低。

② 备货审批
（STK）		 合同已生成（款到发货）→ 待商务备货（选仓+发货量）→ 待仓管确认备货（评估库存/执行能力）→ 退回 / 申请转仓 / 可执行 → 待财务确认到账（按供方分流：总部/化工/阳原/分公司财务）→ 商务发出发货命令 备货对象是备件/整机而非原料批次；库存粒度到设备型号+序列号；「财务确认到账」弱（多为服务合同分期），「仓管」= 售后库管 STK 状态机不变；「仓库」抽象为库存域（区域仓 ↔ 备件库），「财务确认」节点按配置可跳过或改为「服务合同校验」；转仓规则复用（库房间调拨）

③ 发货分配及出库
（SHP）		 出库单已生成 → 商务选仓+发货量 → 仓管填实际发货量 → 累计发货=订单总量? → 全部完成 / 部分发货（剩余三种处理：按原分批继续 / 仓管申请退回或转仓 / 已发货部分可申请开票）；一张发货单只发一次，少发回退备货层 发货=设备安装/物流送货上门（含安装调试动作）；凭证含安装单、验收单而非回单；批次粒度=单台设备 SHP 状态机不变；「凭证类型」配置（回单 ↔ 安装/验收单）；「分批规则」配置（按吨 ↔ 按台）；少发回退备货层逻辑复用
转交：仓管申请转交及原因 → 商务确认 → 转交其他仓管 安装任务可转交其他售后工程师/区域 TransferWorkflow 复用；「转交审批人」配置为商务 ↔ 服务经理
④ 开票回单审批
（INV）		 已发货 → 款到直接进 / 有回单 / 无回单超 5 天自动进入 / 5 天内提前申请（回单异常审核）→ 待开票申请（提交人）→ 推送财务 → 有回单→订单结束；无回单→待补回单→结束。回单不卡开票 开票主体多为服务合同（维护费/备件），发票类型与税率不同；回单弱化为电子服务确认 INV 状态机不变；「回单阈值」与「开票依据」配置（回单 ↔ 服务验收）；四种开票分流规则为配置数据
开票独立于发货（评审批注 #17/#24）：订单存在即可开票，按有效发货勾选合并开票 服务费可按周期开票，天然符合「开票独立」设计 「有效发货」抽象为「有效服务交付」；合并开票入口复用

2. 验证目标与范围

2.1 目标

  • 主轴目标：以长安仁恒订单履约四分支（订单创建→备货审批→发货分配及出库→开票回单审批，依据《三方审批流程图_v2》）为演示主轴完整走通，该验证项目同时作为展示给智厨的演示样板；在对应环节以「智厨映射」对照列说明智厨场景如何适配，验证系统对两类业务的可展示性与复用边界。
  • 授权目标：验证 SpiceDB 的 RBAC + ReBAC 混合模型能覆盖长安仁恒订单系统的复杂权限（多角色、客户归属、代办、交接、转交、C/D 级董事长审批、供方分流财务、多租户隔离、字段裁剪），并形成可复用 schema 与自动化测试。

4. 授权支柱：SpiceDB（RBAC + ReBAC 混合）

4.1 混合模型设计

在 SpiceDB 中，RBAC 与 ReBAC 都是「关系」——差别只在于被授权对象是角色组还是具体资源。混合体现在授权表达式上：权限 = 全局角色关系（岗位）∩ 资源级关系（归属/关系）∩ 条件关系（例外/时效），三者全部满足才放行。这与需求中「仓管是角色、但只能看本仓任务（关系）」的语义完全对应。

// 概念级 schema（验证项目将落地为 config/schema.zed）
definition organization {
    relation member: user
    relation role: user | member   // RBAC：member 是成员，role 是岗位
    permission has_role = role
}

definition customer {
    relation tenant: organization
    relation owner: user            // ReBAC：客户归属销售
    relation proxy: user            // 代办：可替 owner 操作（交接/休假）
    relation managed_by: user       // 商务统筹
    permission view = owner + proxy + managed_by
    permission create_order = owner + proxy
}

definition order {
    relation tenant: organization
    relation customer: customer
    relation creator: user
    permission view = customer.view + creator
    permission approve_price = tenant.has_role("sales_manager")
}

definition warehouse {
    relation tenant: organization
    relation operator: user
    permission manage = operator
}

definition shipment {
    relation tenant: organization
    relation warehouse: warehouse
    relation requester: user
    relation handler: user | warehouse.operator   // 仓管 + 转交后的新办理人
    permission confirm = handler
    permission append_evidence = requester + handler + customer_contact
    permission view_price = false                 // 字段级裁剪：仓管永远无价格权限
}

definition invoice {
    relation tenant: organization
    relation order: order
    relation approver: user
    permission approve = approver + tenant.has_role("finance")
}

关键设计点：

  • RBAC 部分：tenant.has_role("sales"|"sales_manager"|"operations"|"warehouse"|"finance"|"admin") 表达岗位；角色关系由管理员写入。
  • ReBAC 部分：customer.owner / proxy / managed_by、shipment.handler、order.creator 表达资源级关系；交接 = 迁移 owner 关系；转交 = 迁移 handler 关系；代办 = 增加 proxy 关系（带有效期则用条件关系 caveat）。
  • 字段级裁剪：SpiceDB 是资源级授权，字段投影由 BFF 在 view 通过后执行（仓管视图不含 price/amount 字段）。验证项目将其固化为「授权结果 → 响应投影」的强制管线 + 契约测试。
  • 双门禁：SpiceDB 回答「能不能做」（关系），Temporal/状态机回答「该不该现在做」（状态与额度）——approve_price 即使有权限，订单不在待审批状态也不能推进。

5.2 双门禁与状态一致性

  • 双重表述：PostgreSQL 保存业务事实（订单、批次、回单、发票状态），Temporal 保存「下一步做什么」与完整历史轨迹（History 即审计）。订单状态由实际业务结果事件汇总（回单齐、发票关联、回款登记），任何节点被点击都不能直接改完成——这正是需求 V2.0+ 的硬性要求。
  • 事务性 Outbox：业务写 + 事件在同一 DB 事务；Outbox 投影到 SpiceDB 关系与读模型（现有 Relation Projector 复用）。
  • 超时催办：每个人工节点配置 SLA，Timer 到期触发催办 Activity（企微应用消息），N 次后升级上级——对应需求「超时自动催办 + 升级」与「驳回带原因」。超时/逾期订单进入商务工作台「疑似漏发/超时清单」。
  • 防重复：旧待办只读、task_id 校验、撤回重提生成新任务——由 OrderWorkflow 状态机 + SpiceDB 双门禁保证，沿用现有 pilot 的 L3 补偿测试模式。

6.3 「群发言→预订单」可行性分析（核心）

结论先行

技术上完全可行，且只有「会话内容存档」一条官方通道。验证项目将其作为 S2 场景的技术底座，但必须满足三项前置：① 测试企业完成认证并付费开通会话存档（按需存档的账号数计费）；② 获得存档范围内员工（销售/商务）的知情同意（企微官方要求，含告知义务）；③ 存档数据仅用于「下单意图识别与业务协同」，原始消息最小化留存、日志脱敏、按留存策略清理。若公司合规不认可第②条，S2 降级为「半自动」：销售在群内看到消息后一键打开侧边栏（S1），系统预填客户与历史订单，人工确认后进入下单流程——产品价值打折，但整体架构不变。

6.5 交互设计要点

  • 预订单卡片：展示客户、产品（匹配产品库后的标准名+原始说法）、数量、单价（合同价/历史价，标注来源）、交期解析（「下周五」→具体日期）、分批与特殊要求；任何生成结果都需人工确认才能成为正式订单（对应 AI 安全边界：Agent 不得独立签约/承诺）。
  • 识别失败/低置信：只推送「王总在群里提到补货，请确认是否需要下单」轻提醒，不自动建单——误报成本≈一条提醒，漏报由人工兜底。
  • S1 侧边栏交互：entry 分流（single_chat_tools 用 getCurExternalContact，group_chat_tools 用 getCurExternalChat，normal 显示我的待办/我的订单）；无映射客户时给出选择器并走服务端授权，不信任前端身份字段。
  • S3 通知交互：审批卡片点击直达对应订单详情；驳回必须带原因；催办升级链（超时 → 催 → 上级）。
  • 状态机驱动 UI：前端按「booting→authenticating→registering→resolving→loading→ready」状态机初始化，不做定时器轮询客户 ID（避免旧客户串话）。

8. 验证计划（五阶段）

Phase 0 · 环境与决策门（第 1 周）

测试企业认证确认；创建自建应用；配置可信域名、回调域、客户联系权限；开通会话内容存档（最小账号集）并完成员工知情同意流程；准备测试成员、客户、客户群。

退出条件：会话存档可拉取测试群消息（决策门通过）或明确降级为半自动模式；其余配置截图留档。
Phase 1 · 授权支柱（第 1–2 周，与 P0 并行）

落地 RBAC+ReBAC 混合 schema（含 caveat 条件关系）；完成 9 类 B2B 场景授权用例（4.2 表）；字段投影管线；Auth-Pillar 自动化测试；Temporal Activity 内授权。

退出条件：全部授权用例测试通过，无越权缺陷（P0 红线）。
Phase 2 · 流程支柱（第 2–3 周）

OrderWorkflow 主流程 + ShipmentWorkflow/TransferWorkflow/ExceptionInvoiceWorkflow 子流程；SLA 超时催办与升级；企微 Signal 接入；双门禁与防重复；L0–L3 测试。

退出条件：四环节演示链路在 Mock 环境全通；催办升级与例外开票用例通过。
Phase 3 · 企微接入（第 3–4 周）

S1 侧边栏 H5（三 entry）+ OAuth + 双签名；S2 存档捕捉→预订单→卡片确认全链路；S3 审批/催办/通知卡片；S4 工作台视图；客户联系事件回调维护映射。

退出条件：真实测试企业跑通「群里发言→销售确认→进入审批」端到端；采集延迟与识别准确率指标。
Phase 4 · UAT 与验收（第 5 周）

四端（桌面/移动）、四角色（销售/总监/商务/仓管/财务）、单聊/群聊/工作台入口 UAT；失败路径（无权限/无映射/限流/旧链接）；证据归档（截图/录屏/日志 trace/指标）；输出决策报告。

退出条件：三大支柱验证结论 + 上线路线图（含会话存档合规结论）签字。

11. 开放问题

  1. 会话存档开通的账号数预算与计费方式（按需存档人数）——由商务/老板与企微侧确认。
  2. 员工知情同意的落地形式（劳动合同补充条款 vs 操作前弹窗确认）——法务确认。
  3. 测试企业认证状态与「客户联系」权限是否已具备——若不具备，验证项目需先完成企业认证（周期 1–2 周，纳入 Phase 0 关键路径）。
  4. 「仓管看不到价格」是否需要对仓管角色彻底隐藏金额类字段（含明细导出、报表权限）——授权投影范围需业务确认。
  5. 多租户验证深度：验证项目用单企业即可，是否额外做「第二企业」隔离冒烟——建议做，成本低。
  6. 意图识别模型选型（LLM 服务 vs 本地模型）与评测集规模（≥50 条真实群消息回放）——Phase 3 前确定。
  7. 智厨展示定位确认：已确认长安仁恒验证项目作为演示样板直接展示给智厨、不为智厨定制验证项目；「智厨映射」列基于会议纪要提取，演示时作为沟通对照使用，是否后续单独建设由样板演示与业务沟通后再决策。
  8. 《三方审批流程图_v2》实现口径确认：客户商誉评估办法与客户等级表、合同模板与要素来源（评审批注 #5/#7）、供方分流财务（总部/化工/阳原/分公司）、回单超 5 天自动进入阈值——这些规则需业务方书面确认后固化为配置与测试用例。
