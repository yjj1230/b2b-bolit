1生产部署架构与端口矩阵

1.1 目标生产形态（R2 发布后）

v0.1 生产发布把新系统部署在可写副本 PG上（D-007 P3 口径：主库继续同步，发布前由备库 promote），主库只做同步与准备。新系统与旧飞书系统按「一次写入、其余只读」的原则耦合：

  • 新系统唯一对外写：POST /api/v1/bridge/orders → 旧系统 POST /external-orders/create（写飞书审批实例 + JSONL 真相）。
  • 新系统本地写：只写自己的台账（orders 桥接行 + legacy_flow_mapping），不写旧系统其它表。
  • 读方向：旧系统 JSONL → 多维表 / pgAPI → cmd/sync 周期同步 → 新系统 PG → 我的订单/状态回显；详情实时跳旧系统只读页。
  • 回退：关闭 B2B_FEISHU_BRIDGE_ENABLED 即停新入口，商务回到原飞书流程；旧系统零回滚。

1.3 发布边界与回滚口径

可以写

  • 新系统 → 旧系统创建外部订单
  • 新系统自己的台账/事件链
  • 旧系统既有审批动作（飞书侧）

只读

  • pgAPI 客户/产品/合同
  • 多维表/pgAPI 订单镜像
  • 旧系统 /flows/:flow_id 详情

禁止

  • 新系统回写旧 JSONL 业务表
  • 新系统代飞书审批动作
  • 生产桥接与影子栈共用凭据

回退矩阵：关桥接开关（停止新入口）→ 商务回飞书；副本异常回切主库；企微不可达回 PC 兜底（/bridge、/assistant PC 端）。

  1. DSN 库名必须 b2b_shadow
  2. Temporal namespace 必须 b2b-shadow
  3. Task queue 必须 b2b-shadow-order
  4. WeCom provider 必须 mock
  5. Feishu bridge 必须 false
  6. SpiceDB 地址必须在白名单

六个二进制入口（api/worker/ingest/feed/audit + migrate）全部接入；任一违反即拒绝启动，而不是「运行时才发现」。

5.4 六同原则：保证「影子结论 ≈ 真实系统结论」

六同含义现状
① 同代码同镜像shadow-* 与 A 轨同一提交、同一 Dockerfile、同一 workflow/domain/repo已满足
② 同数据真实只读源 + 完整事件链 + 同一 SanitizeRow待 HR2 真实 pgAPI 凭据
③ 同状态机无 shadow-only FSM 分支；shadow-inject 只注入 Timer 等价分支已满足（TestShadowParityWithNonShadow）
④ 同执行环境真实 PG/Temporal/SpiceDB 引擎；SpiceDB 默认向 postgres 升级PG/Temporal 已满足；SpiceDB postgres 化待做
⑤ 同查询面shadow-api 复用 api 二进制与投影代码，仅换白名单/租户已满足
⑥ 同审计事件链、守恒、待办与 A 轨同一 repo 事务已满足

显式例外只有四类：零出站通知器、零回写、无公网入口、PRE/Gatekeeper 内部种子。除此之外的任何差异都视为缺陷。

一句话总结

v0.1 发布后：A 轨用「桥接 + 可写副本 + 单向只读同步」让销售助理下单无缝进入旧飞书审批流；影子轨 S 用「独立环境 + 六同原则 + 六条铁律 + 新单实时增量重放（D-012）」在真实数据上持续预演完整状态机。两条轨的唯一物理关系是只读数据源，因此影子系统可以高频发布、影子先行，而生产系统永远只有一条被桥接开关保护的下单写路径。
