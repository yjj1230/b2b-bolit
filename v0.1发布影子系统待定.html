0.6 · 两个高风险逐条拆解（为什么会错 / 错在哪 / 怎么验）

会怎么错：四个具体失败场景

真实情况当前行为后果
动作叫 PRICE_APPROVED，不叫「主管通过」每条事件翻译失败 → 写 UNMAPPED_EVENT 分歧影子订单建了，但一步都推不动，R1 报告全是「未映射」

为什么危险：错误是「安静的」

  • 这些错误不会让进程崩溃：未知动作走 UNMAPPED 分歧、缺字段走 SKIPPED、错映射走错误推进——每个都有「合法出口」；
  • 于是影子轨会跑完并产出一份看起来完整的审计报告，而这份报告是 v0.2「数据迁入」Go/No-Go 的核心证据；
  • 后果链：翻译错 → 边覆盖与分歧统计全错 → v0.2 决策建立在错误证据上 → 到真实数据迁入时才暴露，代价最大。

A13 影子「像真人一样推进」的驱动方式（生产飞书注入 / 影子侧种子 / 飞书测试环境）

所属影子事件的来源策略：如何让影子流程看起来在真实往前跑建议决策人项目 owner + 旧系统负责人 + 技术负责人

SCENE · 场景

BUSINESS · 业务

「数据不会作为真实库去用」这句话只对一半：如果补丁写在生产飞书上，那写的就是真相库本身——真实用户可能收到通知、真实订单可能被推进、真实报表会被污染。风险大小取决于写入位置，而不是「影子用不用这份数据」。

TECH · 技术

三种实现：① 影子侧合成注入——事件直接写 shadow_source_events（source=seed），完全不碰飞书；② 飞书测试环境注入——复制一份飞书测试库/测试实例，补丁和 job 只在那里跑，影子指向测试环境；③ 生产飞书补丁注入——在生产飞书加 job/补丁生成动作（可能发通知、推进真实订单、被 A 轨 sync 同步，需全面隔离）。

风险矩阵：为什么「生产飞书注入」不是低风险

方案真实感生产风险主要代价 / 注意事项判断
A · 影子侧合成注入中：workflow 与真系统同代码，事件源非飞书零开发一个 shadow-seed 注入器，事件全部 source=seed；审计报告按 seed/real 分开日常主选
B · 飞书测试环境注入高：真实飞书代码/审批引擎在跑，只换环境低需搭建/复制飞书测试环境；数据脱敏；影子只读指向测试环境要「跟真人一样」时选
C · 生产飞书补丁注入最高，但是对真相库写操作中高合成行可能：发真实通知、推进真实订单、进入 A 轨 sync 与报表、被真人误操作；必须前缀隔离 + 通知全关 + 清理 runbook + owner 签字不推荐，除非是临时、封闭、可回滚的试验

生产飞书注入（方案 C）的具体风险链：① 飞书没有「影子租户」概念，补丁写入的订单/审批事件会被它的通知服务当真实事件推送；② 已有 cmd/sync 会把飞书订单同步进 A 轨，虹励可能在「我的订单」看到影子造的假单；③ 审批任务会占用真实审批人；④ 后续清理生产数据本身是高风险动作；⑤ 它污染「真相永远在飞书」的审计前提——影子分歧到底是飞书真实差异，还是自己注入的脏数据，再也分不清。

选项与判据
  • A. 影子侧合成注入（source=seed），零生产风险（推荐，立即可做）；
  • B. 搭飞书测试环境，把补丁/job 放测试环境，影子指向测试环境（要最高真实感时做，推荐顺序第二）；
  • C. 生产飞书补丁：仅限「前缀隔离 + 通知关闭 + sync 排除 + 可清理 + owner 签字」五项全满足的封闭试验，且必须写明结束时间与回滚方式（默认不做）。
该怎么做 · ACTION（1-5 步）
  1. 先定目标：是补 79 边覆盖（选 A），还是模拟真实审批引擎行为（选 B）。
  2. 选 A 就实现 shadow-seed：生成 JSONL 事件 → 走现有 ingest/feed，所有事件 source=seed，报告分开统计。
  3. 选 B 就排飞书测试环境搭建：复制结构、脱敏数据、部署补丁/job，影子 ingest 配置指向测试环境。
  4. 如果确实要 C：先写五项隔离清单（前缀 / 通知 / sync 排除 / 清理 / 回滚），owner 逐项签字后才允许动生产。
  5. 任何方案都要在 shadow_runs.note 里标注本次 run 的驱动方式，防止真实与合成数据混算。
