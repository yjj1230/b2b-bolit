0 · TL;DR

最终采纳方向：

  • 旧飞书复杂三方审批流程：不改造、不再承接新业务，冻结后只读归档。
  • 飞书侧：新增几个极简单节点审批流程，只服务销售、销售主管、董事长。
  • 新系统：不新增飞书支持，只暴露通用 REST API，成为唯一状态机与数据真相。
  • 商务、财务、仓管、销售助理：全部在企微上处理流程。
  • v0.3 的“全量切换”因此退化为：历史数据回填 + 四层对账 + 旧系统只读归档，不再等同于重新发布一次项目。
  • 最终目标：飞书通道作为可插拔组件，随时可以整体摘除，飞书完全下线。

用户对原计划的核心质疑：v0.3 的全量切换“跟重新发一次项目没有区别”。本次设计讨论正是围绕如何绕开这个二次发布展开。

1 · 完整讨论过程（来龙去脉）

第 1 轮 · v0.2 现状与“旧系统最小动作”

用户提出：到 v0.2，除了销售、销售主管、董事长，其它角色都已经上到企微流程；这三个角色在流中做的事情很有限。所以是否更适合反过来：对旧飞书系统做一些额外的最小动作，仅支持好销售、销售主管、董事长的动作处理，其它全都在企微上？

分析结论：可行。本质是“旧系统继续当真相 + 多前端”：商务/财务/仓管在企微操作，通过受信办理通道写回旧系统；销售/主管/董事长继续用飞书原生审批。优点是不为三个低频角色做重 UI、不需要提前切换真相；缺点是旧系统仍长期存在，且要解决 approver_token 安全获取、双通道并发等受信通道问题。

第 2 轮 · v0.2 直接迁数据，新系统当真相，旧系统降级为 UI

用户提出：如果 v0.2 就把数据都迁到新系统；只有销售、主管、董事长还在老系统上走自己的几个重要节点；其它人都在企微上处理流程，这样的风险和可能性如何？

用户进一步明确（最新确认）：旧飞书系统不能再自己当“状态机”，只能退化成这三个角色的“审批 UI / 输入终端”。销售的操作最终确认为：下单（如果销售仍然自己下单）、信息确认（如果销售是提交人）、填写开票信息（SHP 阶段）、盖章回传（INV 阶段）、驳回后重提。

分析结论：终态更干净，但这是“旧系统核心重构 + 新系统状态机接管 + 全量切换”，风险高：双状态机、飞书回调转发丢失、节点重复创建、重提链双写。四个销售动作逐个映射后，信息确认最简单，下单和开票信息是表单反转，驳回重提最重（root/revision/resubmit 链必须搬进新系统）。

第 3 轮 · 最终想法：旧系统不改造，新增几个单节点飞书流程

用户提出：

  1. 最终目标是飞书完全下掉。
  2. v0.3 做全量切换，感觉跟重新发一次项目没有区别。
  3. 旧系统如果不是改造，而是新做几个单节点流程呢？
  4. 新系统如果不新增飞书支持，全部都以旧飞书系统的新增需求来解决呢？

最终结论：这是三条路线里最优的一条。旧飞书复杂流程不再改造、不再使用，冻结 + 只读归档；飞书侧新增几个极简单节点流程 + 一个轻量飞书通道服务；新系统不增加任何飞书支持，只提供通用 REST API；v0.3 的全量切换退化为“历史数据回填 + 四层对账 + 旧系统只读归档”。最终把飞书完全下掉时，只需停掉通道服务和单节点审批定义。

核心洞察：新系统 = 业务大脑（渠道无关）；飞书 = 可插拔审批渠道；企微 = 另一条渠道。旧系统复杂状态机不再是架构的一部分。

将上述讨论沉淀为本文档，供后续 Agent 接手 v0.2 设计。接手时需要继续推进：

  3. 评估新系统 v0.2 全流程建设范围与现有代码差距。

驳回后重提 H5 表单，预填驳回数据 轮询被驳回订单 → 渲染 H5 → 提交后调新系统 signal: resubmit（已有）
销售主管 审价审批 单节点审批 轮询待办 → 创建实例 → 回调转信号 signal: price-review（已有）
董事长 C/D 级终审 单节点审批 轮询待办 → 创建实例 → 回调转信号 signal: chairman-review（已有）

关键判断：销售主管、董事长的审批动作是纯 approve/reject，最适合做成单节点飞书流程；销售的下单、信息确认、开票信息、盖章回传是表单/附件类动作，用 H5 表单或单节点审批均可，驳回重提走 H5 预填重提，均不触碰旧复杂流程。

7 · 新系统“不新增飞书支持”的边界

可以做到，且应该做到。新系统只需要补齐三个通用能力，它们都不属于飞书支持：

  1. 服务间受信身份：飞书通道以“系统级凭证 + 代表用户”方式调新系统；新系统只认内部 user_id，不认识 open_id。
  2. 稳定的待办查询 API：飞书通道靠 GET /api/v1/todos?assignee=... 轮询主管/董事长待办（现有端点，按需扩展过滤）。
  3. 业务信号/表单接口：创建订单、price-review、chairman-review、resubmit 信号均已存在；开票信息提交与盖章回传（含附件）按需补普通 HTTP 接口/信号。

当前 v0.1 的 internal/bridge 与 B2B_FEISHU_* 配置，在 v0.2 可以作为临时兼容层逐步退场，不再是长期架构。

9 · 仍然不能省的硬工作

  1. 历史数据回填：16 个 JSONL 文件 → 新 PG；订单、事件链、附件、审批历史；migration_batches 幂等回填。
  2. 存量单规则：新单新办法，存量单在旧飞书复杂流程里走完；旧复杂流程只出不进。
  3. open_id ↔ user_id 映射：放在飞书通道服务，不放新系统；新系统永远只看到内部 user_id。
  4. 飞书审批定义配置：新增主管审批、董事长审批等单节点定义；旧飞书应用若支持多 approval_code 可复用，否则新建独立飞书应用。
  5. 回调幂等 + 关联表：feishu_instance_code ↔ new_order_id / task_id；飞书回调重试、重复点击都不能重复推进。
  6. 通道服务可靠性：它是销售/主管/董事长的唯一入口；待办轮询有延迟，若要求实时，可让新系统发通用 webhook（仍是普通 HTTP，不算飞书支持）。
  7. 服务间鉴权：新系统与飞书通道之间的受信凭证、用户代表机制、审计链路。

10 · 剩余风险

风险等级说明
飞书通道故障，三个角色办不了事中比旧系统改造风险低，但仍需监控和快速回退
待办轮询延迟低主管/董事长晚几分钟看到待办，业务可接受
open_id 映射错误中映射错会把审批推错人，上线前必须逐人核对
单节点审批实例和企微待办重复低只要旧复杂流程冻结，就不存在双待办
旧复杂流程残留存量单中需要明确收口规则，否则销售可能两边都有单
历史回填漏事件链中用批次校验和 + 四层对账兜底
影子 HR1 映射未签字 → v0.2 证据不可信中代码事实基线已生成；业务逐条签字 + detail 字段名冻结后权威化

12 · 最终结论

采纳路线：

  1. 旧系统不改造，旧复杂流程冻结归档；
  2. 飞书侧新增几个单节点流程，由轻量飞书通道服务承接；
  3. 新系统不增加飞书支持，只暴露通用 REST API；
  4. v0.2 是新系统的功能上线，v0.3 退化为历史数据回填 + 对账验收，不再等同于重新发一次项目；
  5. 最终下飞书时，只需停掉飞书通道服务和单节点审批定义，把销售/主管/董事长迁到企微。

一句话：把飞书从“复杂旧系统”降级为“一个可插拔的审批渠道”，是最接近最终目标、且每一步都可回退的路线。影子轨是这条路线上的“真实数据预演器”，v0.2 的每一步角色迁移都应以它的覆盖率与分歧裁决为证据。
