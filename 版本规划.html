版本规划 · v0.1 / v0.2 / v0.3

用大白话讲清楚：每个版本上线之后希望看到的效果状态，以及这个阶段还可以做什么。注意：本页描述的是目标状态；能否宣称达成，以文末「设计前提与未决项」为准。

读者：产品同学 + 非架构方向程序员。所有结论来自仓库内已冻结文档：docs/v0.1/01–12、project/decisions/D-006..D-011、v0.1业务发布梳理.html 与《发布计划可行性验证》。

v0.1 = 双卡双待 + 后台沙盘推演 v0.2 = 数据正式迁入新系统，除销售/主管/董事长外全部上企微 v0.3 = 企微体系发布完成：全员迁入 + 全量数据迁完 + 影子撤销

1v0.1 上线后：旧流程照跑，虹励以“销售助理”身份先跑通下单闭环 + 后台“沙盘推演”商务全流程

一句话状态：财务、仓管继续用飞书原流程，一点不受影响；虹励以销售助理身份完成“OAuth 授权 → 桥接代下单 → 飞书待办 → 状态回显 → 查我的订单”闭环（企微 / PC）。她作为商务的“备货 → 发货 → 开票”操作本期不迁入新系统，继续在飞书原流程办。与此同时，影子系统在后台用真实飞书数据把完整订单流程（含商务备货 / 发货 / 开票）暗中重演一遍，为 v0.2 数据正式迁入新系统做流程校验。

具体效果

  • 飞书侧数据单向只读同步进新系统：看得到、查得到，但新系统绝不写回飞书。（飞书 → 新系统，只进不出）
  • 虹励（她既是商务、也是销售助理）：v0.1 开放的只是她的销售助理身份——OAuth 授权（飞书）→ 桥接代下单（企微 / PC）→ 飞书旧流程续跑（飞书）→ 状态回显 + 查“我的订单”（企微 / PC）。她作为商务的“备货 → 发货 → 开票”本期不在新系统开放，继续在飞书原流程办（飞书）。
  • 其他销售助理：同一套企微 H5 / PC 桥接入口代下单 + 查自己的订单（企微 / PC）。
  • 销售 / 主管 / 董事长：企微侧边栏、审价卡、终审卡等能力在系统里已实现（demo 已演示），但按 v0.1 发布口径本期不开放他们登录操作（企微端不开放）；是否提前放行由发布范围单 + 白名单决定。
  • 财务 / 仓管：继续在飞书干活，企微端本期不开放操作；他们的数据同步进新系统是设计目标，“存量订单同步”已裁决：v0.1 不做（归 v0.2 数据迁入），本刀不承诺存量可见（飞书 → 新系统，给后续版本用）。
  • 影子系统：内部专用、零客户触达、零出站（不发企微）、零回写（不写飞书）。v0.1 目标是新单实时 hook 模式（D-012，主通道由 T3 落定：旧系统埋点或飞书事件订阅）：客户在飞书下单 / 审批的同时，事件实时进影子（飞书 → 影子库），把商务备货 / 发货 / 开票等完整流程重演一遍；hook 未接线前用 JSONL / 列表轮询兜底（实时性降级，不阻塞上线）；存量数据不依赖；每天产出覆盖率 / 分歧 / 审计报告，连续迭代提前完成 v0.2 发布前的流程校验测试，把 v0.2 数据迁入的安全系数大幅提高。
v0.1 企微端开放名单（避免混淆）：本期只开放销售助理身份——① 虹励（她同时是商务，但这一刀只用销售助理身份）：桥接代下单 + 查自己的订单（企微 / PC）；② 其他销售助理：同一套入口（企微 / PC）。商务功能（备货 / 发货 / 开票）本期不在新系统开放，继续在飞书原流程办；销售、主管、董事长、财务、仓管企微端也不开放。

边界（0.1 明确不做的）

  • 商务的备货 / 发货 / 开票操作不迁入新系统（继续在飞书原流程跑；影子轨只在后台预演这些流程）。
  • 自动下单不做（企微会话存档备案未完成，人工确认段保留）。
  • 锁库存不做（发货只做数量守恒校验）。
  • 其他角色不迁入（先让一个人跑起来）。

这个阶段还可以做什么

  • 换真实数据：真实用户、两个外租仓库、真实客户 / 产品（现在是演示数据）。
  • 飞书侧调研：16 张表字段映射、状态语义映射、只读账号、敏感字段清理。
  • 旧系统小改：识别 B2B_V01_ 前缀自动确认“信息确认”、配好审批人（防 fallback 错人）。
  • 企微侧：回调 URL、应用主页、可信域名、卡片 / 侧边栏验证、仓库群升级企微群（回单机器人前置）。
  • 把待确认规则定下来：无回单能否开票（A5）、合并开票业财归属（P4）、守门员直发规则（P5）——这些不阻塞 v0.1 下单闭环，是为 v0.2 数据迁入做准备。
  • 发布动作本身：R1 测试环境 → UAT → 回退演练 → Go/No-Go → R2 生产 → 8 小时稳定复盘；影子 R1 新单全集重放（D-012） + R2 上线 24 小时。

2v0.2 上线后：数据正式迁到新系统；除销售、主管、董事长外，全部岗位切换到企微体系

一句话状态：因为有 v0.1 + 影子系统提前做完了 v0.2 发布前的流程校验测试，安全系数大幅提高，v0.2 敢把数据正式迁到新系统：飞书 JSONL → 新系统 PG，新系统成为唯一状态机与数据真相。商务、财务、仓管、销售助理全部在企微手机 / PC上处理流程；销售、主管、董事长不开放企微手机 / PC，继续用飞书——旧复杂流程冻结，飞书侧只保留为这三个岗位新增的极简单节点审批。

具体效果

  • 数据正式迁移：飞书 JSONL 全量迁入新系统 PG（含事件链）（飞书 → 新系统），新系统成为唯一状态机与数据真相。
  • 商务：在企微办备货“选仓 / 自提 + 收件人 + 收货地址 → 通过 / 驳回”（企微 / PC），数据落新系统。
  • 财务：款到类订单确认到款、开票相关处理在企微办（企微 / PC），数据落新系统。
  • 仓管：在企微确认发货（数量守恒、超发拦截）+ 上传回单（企微 / PC）；仓管视图金额不可见（剥价）。
  • 销售助理：继续在企微 / PC 下单 + 查“我的订单”（v0.1 已有），订单直接落新系统。
  • 销售 / 主管 / 董事长：不开放企微手机 / PC，继续在飞书办审价、C/D 终审、开票信息、盖章回传等（飞书）；旧系统复杂流程冻结，飞书侧只保留为这三个岗位新增的极简单节点审批 + 轻量飞书通道服务对接新系统（通道服务尚未实现，属 v0.2 前提项）。
  • 旧系统：不再承接新业务、不再是状态机（飞书）；复杂流程冻结，历史只读。
  • 影子系统：v0.1 攒下的新单实时重放证据（D-012）就是这一刀的 Go/No-Go 尺子——连续 K 笔新单门槛达标才放行。

这个阶段还可以做什么

  • 全量数据迁移 + 四层对账（订单数 / 状态 / 事件链 / 附件）与回滚演练。
  • 轻量飞书通道服务落地：只为销售 / 主管 / 董事长的单节点审批做桥接，不把旧复杂状态机带进来。
  • 商务 / 财务 / 仓管 / 销售助理的企微工作台与待办视图（按角色过滤）。
  • 旧系统复杂流程冻结 + 三个岗位的极简飞书审批定义（下单 / 信息确认 / 开票信息 / 盖章回传 / 审价 / 终审）。
  • 企微官方通道补全 template_card；企微备案域名未就绪时先用 PC 订单后台。
  • 影子系统持续发布（D-012 新单实时增量）：连续 K 笔新单门槛（UNMAPPED=0、FSM_GAP P0=0、终态对齐、零出站 / 零回写哨兵全绿）达标才放行。

3v0.3 上线后：企微体系发布完成——全员迁入、全量数据迁完、影子撤销

一句话状态：v0.3 = 企微体系的发布完成：销售、主管、董事长也迁入企微（开放企微手机 / PC），全员都在企微体系里处理流程；全量数据一定已经全部迁完（存量订单 + 事件链 + 附件四层对账 100% 一致）；旧飞书只读归档 / 下线；影子系统正式撤销。

具体效果

  • 全量数据迁完：全部存量订单 + 事件链 + 附件 100% 回填进新系统（飞书 → 新系统），订单数 / 状态 / 事件链 / 附件四层对账一致，业务方抽单签字。
  • 销售全员：迁入企微（开放企微手机 / PC）：填写开票信息 + 盖章回传，本人订单数据可见。
  • 销售主管 / 董事长：迁入企微（开放企微手机 / PC）：新系统审批台做审价、C/D 终审，有通知和超时提醒。
  • 企微体系发布完成：所有岗位都在企微手机 / PC 上处理流程；飞书通道摘除，旧系统只读归档 / 下线（飞书）。
  • pgAPI 收口：停飞书上游同步，三方审批镜像改只读历史 / 台账，或由新系统接管写入。
  • 影子系统撤销：归档报告和分歧清单 → 停栈 → drop 影子库——全量数据已迁完、企微体系已发布完成，它不再常驻。

这个阶段还可以做什么

  • 销售 / 主管 / 董事长的企微入口与审批台落地（这是 v0.3 完成企微体系的最后一批岗位）。
  • 全量回填脚本 + 幂等批次（影子轨已演练过迁移和重放）+ 四层对账 + 业务签字。
  • 旧系统只读归档 / 下线 + 附件保留期管理（附件 6 个月）。
  • 飞书通道摘除演练 + 回滚预案；观察期每日对账无差异。
  • pgAPI 定位拍板：只读历史 / 台账，还是新系统接管写入。
  • 影子撤销清单 + teardown 演练（归档 → 停栈 → drop）。

② v0.2 = 数据正式迁到企微体系：新系统成为唯一真相，除销售、主管、董事长外全部岗位切到企微；影子证据说了算。
③ v0.3 = 企微体系发布完成：销售、主管、董事长也上企微，全员迁入；全量数据 100% 迁完并对账一致；旧飞书只读归档，影子系统撤销。

1影子 hook 主通道 T3 落定（旧系统埋点 vs 飞书事件订阅）；若选埋点，需书面放宽“旧系统唯一小改”边界v0.1 / 影子未定；代码当前只有 file / http 轮询实时性降级为轮询；不影响 v0.1 上线，影响影子迭代速度

核一致性说明与技术可行性结论

  • 方向自洽：v0.1 影子提前校验 → v0.2 数据迁入新系统（唯一真相）→ v0.3 三岗位完成企微切换 + 全量数据迁完 + 影子撤销，顺序正确、风险前置合理。
  • v0.1 技术可行：桥接下单 / 查单代码与测试在库；影子栈代码已实现并本地预演；hook 未实现但不阻塞上线（轮询兜底）。
  • v0.2 / v0.3 方向可行、不等于已就绪：全量迁移、附件存储、三岗位飞书通道与企微审批台、pgAPI 停同步时点等均为未完成工程项，必须排入对应版本发布任务后才能宣称达成。
  • 一致性残余漂移（已收敛）：v0.1_CQ 的 OT/V01 组已按 D-013 重标；任务列表已增加 release 字段，D 线存量同步类任务标 v0.2；v0.1业务发布梳理等旧文档以顶部归档提示标版。
