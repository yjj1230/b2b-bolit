项目迭代机制

00

先给结论：目录不能承担真相，关系才能

合理方案不是重新规定“以后以 spec 为准”或“永远看最新 demo”。目录只表达制品的职责与生命周期；真正的决定性必须落在带稳定 ID 的声明、决策、实现和证据关系上。时间是裁决条件之一，不是最高权威。

以“声明”为最小治理单位，以“决策”为语义权威，以“制品”为不同视角的投影，以“证据”为可重放观察，以“基线”为某一时刻可交付的一致切片，以“机制版本”为所有裁决的可审计前提。
本文件的身份与效力：仓库根目录的 证据收敛式项目迭代机制.html 是 ECM 1.0.0 的引导提案（PROPOSED），也是当前设计讨论的完整人类可读载体；它不是已经生效的项目门禁。只有完成 §07 的批准与发布、生成版本化规范，并由 project/policies/mechanism/current.yaml 和 project/project.yaml 共同指向后，某个 ECM 版本才是 ACTIVE。在此之前，Agent 可以依据本文分析和执行首次迁移，但不得声称项目已由 ECM 正式治理。
DIRECTORY

目录分职责，不排真相顺序

spec 保存来源，docs 保存解释，demo 保存可交互假设，代码保存实现，测试保存验证程序，project 保存它们之间的治理关系。

INFORMATION

状态必须正交

“已决定、已实现、已验证”是三个不同维度。一个需求可以已决定但未实现；一个 demo 可以已实现但尚未被业务接受。

FLOW

每次变化触发局部收敛

任何制品变化先生成变更事件，按声明关系计算影响，只让受影响的文档、demo、代码与证据进入待收敛状态。

META

机制也按同一规则治理

规则变更先成为提案，经历史回放、影子运行和人工批准后生效；旧基线继续绑定旧机制，禁止无声改尺子。

现有资料已经自然形成了多条演进支线，但目录名、文件名和更新时间无法表达它们之间的真实关系。以下不是抽象担忧，而是本次扫描直接观察到的事实。

观察当前事实暴露的问题
来源与加工混放spec 同时含业务原稿、调研、技术核验、方法论、评审逐字稿、修改意见和 UI 实现。“位于 spec”不能自动等价于“一手且已批准”。
最新 demo 快速演进docs/demo 在 8 月 10–12 日连续迭代，晚于主体架构、测试和多数产品文档。交互现状领先，但不能据此声称后端、测试或业务规则已同步。

现在与未来混在同一意见中评审将物流小程序标为“分期”，当前 demo 仍展示图片发群。二者可能分别属于 v0 当前方案和 vNext 目标方案，不应被误判成直接冲突。
前提被否定但下游仍存在评审指出“客户签收后发凭证”的前提不成立，真实链路是司机、仓库、商务的线下回单；较早用例仍保留客户凭证识别。前提变化应自动重开依赖声明，而不是等人碰巧发现。
代码与产品节奏分叉代码的最近集中变更在 8 月 7 日，demo 与产品评审持续到 8 月 12 日。demo 是交互探索的当前事实，不是已经交付的系统事实。
测试数字会被误读仓库有 221 个 Test 函数，已有文档声明约 180 个，说明报告快照与当前代码计数不在同一观察时点。任何覆盖与通过结论都必须绑定 commit、环境、命令和验证器版本。
根因：当前系统主要管理“文件”，但项目真正演进的是文件内部的业务声明、设计决定、交互假设、实现行为和验证结论。文件是容器，不是治理原子。
02

七条不变原则

P1 / SCOPED AUTHORITY

权威必须带问题域

业务原稿决定业务意图，已批准决策决定当前承诺，demo 证明交互长什么样，代码证明系统实际做什么，测试证明某个观察程序看到了什么。任何制品都不得越权。

P2 / CLAIM ATOM

以声明而非文件为原子

一个文件可同时包含已确认、待定、分期和已废弃内容。每条可影响行为的陈述都要有稳定 claim_id，状态单独管理。

P3 / ORTHOGONAL STATUS

语义、实现、验证三态分离

ACCEPTED 不等于 IMPLEMENTED，IMPLEMENTED 不等于 VERIFIED，测试通过也不能反向把一个待定业务假设变成已批准需求。

P4 / CAUSAL TIME

用因果时序，不只用修改时间

mtime 只能提示扫描顺序。裁决需要来源发生时间、观察时间、生效区间、替代关系与基线版本；复制旧文件不能制造新事实。

P5 / LOCAL INVALIDATION

变化只作废受影响证据

声明、代码、环境、验证器或机制变化时，通过依赖边计算影响半径。旧证据转 STALE，保留审计，不全量删除、不默认全仓重跑。

P6 / EXPLICIT UNKNOWN

未知和冲突是合法状态

机制要允许项目在部分未知下继续，但高风险未知不得伪装为共识。阻塞应落到具体声明、负责人和所需最小问题，而不是笼统地“等业务确认”。

P7 / VERSIONED METHOD

治理规则本身是受治理制品

权威矩阵、状态机、阈值、生成器和门禁都有版本、负责人、适用范围、测试与迁移计划。方法变更不能重写历史判断。

九种关系

DERIVED_FROMREFINESIMPLEMENTSVERIFIESDECIDESSUPERSEDESDEPENDS_ONCONFLICTS_WITHVALID_DURING

关系必须可定位到声明或文件片段；只有文件路径而没有 claim 边，无法做可靠影响分析。多对多是正常状态：一条“群内金额不可见”声明会同时约束 demo 截图、API 投影、ReBAC、测试和产品说明。

三组状态必须分开

SEMANTIC

这是不是当前承诺

PROPOSED → ACCEPTED → DEFERRED / REJECTED / SUPERSEDED

IMPLEMENTATION

制品是否已经跟上

UNPLANNED → PLANNED → PARTIAL → IMPLEMENTED → DRIFTED

VERIFICATION

证据是否足够且仍有效

UNVERIFIED → PASS / FAIL → STALE / INVALID / EXPIRED

禁止合并成一个“状态=完成”。当前 demo 的单页长表单可以是 ACCEPTED + IMPLEMENTED(demo) + UNVERIFIED(code)；物流小程序可以是 DEFERRED(vNext) + UNPLANNED；当前图片发群则是另一个 v0 声明的 ACCEPTED/CONDITIONAL + IMPLEMENTED(demo)。

完整度不是百分比，而是一个向量

范围完整度关键角色、场景、异常、阶段是否有声明
分解完整度业务目标是否被拆成可设计、可实现、可验收的粒度
追踪完整度必需 claim 是否都有来源、决策、实现和验证边
证据充分度证据等级是否达到风险要求，是否覆盖反例
冲突闭合度是否还有未裁决矛盾、前提失效或范围重叠
新鲜度依赖摘要、环境、验证器和 TTL 是否仍有效
completeness := [scope, decomposition, trace, evidence, conflict_closure, freshness]
handoff 逐维设门槛；禁止用平均分掩盖任一 R3 缺口。

细节颗粒度的判断标准

不追求“每句话一个 ID”。当一段信息满足以下任一条件时，拆成独立 claim：它可以被单独接受或拒绝；它有不同 owner；它会映射到不同实现；它需要不同 oracle；它的风险或生效阶段不同。否则保持在同一声明中，避免治理对象爆炸。

冲突裁决：新鲜度有用，但不能越权

按问题选择权威，不按文件夹选冠军

要回答的问题首要权威次级证据不能替代它的东西
业务真实流程是什么被识别的业务 owner 的一手事实 + 已批准 BDR逐字稿、现场观察、业务系统数据demo、代码、测试通过
当前版本承诺做什么生效中的 Decision + Claim baseline规范化 PRD、范围表原始材料中尚未裁决的建议
交互当前设计成什么样已批准交互 claim；其当前 demo 是最强可视投影UI spec、UAT 记录后端代码、较旧产品说明
系统当前实际做什么目标 commit 的代码 + 真实运行观察API 快照、图谱、日志架构图、demo
实现是否满足某声明有效 oracle 下的证据组合静态分析、测试、人工验收单一覆盖率数字
某次交付包含什么签名 Baseline manifest构建产物、SBOM、evidence manifest工作区最新状态

九步裁决算法

1
归一化先判断两个陈述是否真在谈同一 subject / predicate / scope / phase。不同阶段、角色或终端的陈述可以并存。
2
可采信性来源身份、完整性、digest、时间和上下文不明的材料只能做线索，不能直接进当前承诺。
3
问题域权威按上表选择谁有资格回答当前问题；demo 对交互形态强，对业务真实性和生产实现弱。
4
决策状态ACCEPTED 高于 PROPOSED；DEFERRED 不是被否定，而是对特定 phase 不生效。
5
因果时序明确 SUPERSEDES 的后继优先；只有同权威、同 scope、依赖前提未变时，较新观察才优先。
6
具体性更窄且不违反上位约束的声明覆盖更宽默认规则；例如群内资金信息禁发高于某页面“展示完整订单”的泛化描述。
7
证据反驳代码/测试可证明“当前没做到”或“假设不可行”，但不能自动改写业务目标；它们生成反例并重开决策。
8
人工裁决仍不可区分时，生成不超过 3 个高信息增益问题，交给对应 owner；记录选择、理由、前提与复核日期。
9
局部失效裁决后标记被替代 claim，并只让受影响视图、demo、代码和证据变为 STALE。
authority(candidate, question) = admissibility × domain_authority × decision_state × scope_fit × causal_freshness
mtime 只影响 causal_freshness 的一部分；任一前置项为 0，文件再新也不能成为答案。

一致性的五个层次

语义一致

同一 scope 下没有两个同时生效、互相排斥的 accepted claim。

时间一致

观察、决策、生效和替代顺序可解释，没有拿旧证据证明新制品。

结构一致

产品、数据、接口、权限和流程的依赖边不缺失、不悬空。

行为一致

demo、代码和运行对已接受 claim 的实现没有不可解释漂移。

证据一致

不同观察器的结论可组合；冲突结果不被平均或重跑到绿。

06

信息流动：事件驱动的局部收敛双循环

每次提交不是“同步所有文档”的命令，而是一个变化事件。系统先识别变化触及哪些声明，再决定需要更新视图、实现还是验证。不能自动裁决的部分被压缩成人类问题包；其余工作继续。

1 / INGEST登记变化、来源、digest、观察时点与提交者角色
2 / NORMALIZE抽取或关联 claim；区分事实、提案、决定和观察
3 / DIFF做声明级语义 diff，不只看文本 diff
4 / IMPACT沿依赖边计算受影响视图、demo、代码、测试和证据
5 / ROUTE自动同步、生成任务，或向 owner 发最小问题包
6 / VERIFY运行受影响挑战，绑定制品、环境、验证器与机制摘要
7 / BASELINE门禁通过后发布新的可交付一致切片

五种入口的差异化路由

变化入口先把它当作什么自动动作何时需要人
spec 更新新的来源事实或需求候选，不直接等于 accepted抽取候选 claim；与当前 baseline 比较；标记依赖前提变化；生成决策候选语义变化、范围变化、R2/R3 冲突或 owner 不明确
docs 更新视图变化；可能只是表达修正，也可能偷带新规则比对所引用 claim；纯表达更新只重建视图摘要；新增规范性语句则转成 proposal文档试图越过 decision 直接修改当前承诺
demo 更新可执行交互提案或已接受交互的实现运行场景 smoke/截图 diff；检查 claim 覆盖；更新 demo implementation 状态出现未绑定交互、改变业务规则、权限、字段或流程节点
代码更新实现事实变化图谱影响分析；重跑相关测试；对照 accepted claim 与接口契约；使旧运行证据 stale代码行为与承诺冲突但无法判断是需求变了还是实现错了
测试更新验证器或 oracle 变化，风险高于普通代码变更校准测试自身；旧结果按 verifier digest 局部失效；检查是否降低断言强度oracle 改变业务含义、删除高风险断言或引入临时豁免

快循环：推进项目

on ARTIFACT_CHANGED(event):
  register(event.path, kind, digest, author_role, observed_at)
  candidate_changes = semantic_diff(event, referenced_claims)

  for change in candidate_changes:
    if change.is_editorial:
      rebuild_view(change)
      continue

    claim = resolve_or_propose_claim(change)
    conflicts = find_active_conflicts(claim.scope)
    impact = traverse(claim, DEPENDS_ON | IMPLEMENTS | VERIFIES | REFLECTS)

    if conflicts.need_human_decision:
      emit_question_packet(max_items=3, ranked_by=closed_risk_per_cost)
      mark(claim, WAITING_DECISION)
    else:
      apply_authority_policy(claim)
      mark_impacted_artifacts(STALE, impact)
      dispatch_minimal_tasks(impact)

  run_affected_verifiers()
  publish_baseline_only_if(handoff_predicate == true)

慢循环：更新机制本身

A / OBSERVE记录漏检、误报、死锁、人工成本和事故
B / PROPOSE形成 policy/rule/schema 变更提案
C / REPLAY在历史正反例上回放，检查召回与误伤
D / SHADOW新旧机制并行计算，不改变当前门禁
E / APPROVE人审查差异、迁移成本和失败回滚
F / ACTIVATE发布新版本；基线显式选择何时迁移

人介入的接口必须窄

系统不应把整仓资料丢给人“看一下”。每个问题包最多 3 项，并包含：冲突的精确 claim、各候选及来源、受影响范围、不回答的风险、推荐项与可逆性、最晚决策点。人的回答生成 Decision，不直接覆盖文件；后续自动派生修改任务。

07

机制的版本化：不能悄悄换尺子

机制不是一个永远正确的脚本，而是一组有边界、有误差、会演进的政策与观察器。它必须像业务制品一样被声明、测试、批准和回滚。

机制自身放在哪里

机制采用“机器规范是规范源、人类指南是发布视图”的双制品结构。版本号进入文件名，已发布版本不可原地覆盖；当前生效版本由指针选择，不能靠无版本文件或修改时间猜测。

Agent 启动协议

  1. 从仓库根目录读取 project/project.yaml；不得搜索并选择“最新 ECM 文件”。
  2. 沿指针读取 current.yaml，确认 ID、版本、status=ACTIVE 与项目绑定一致。
  3. 读取固定版本的 YAML 规范源和 HTML 指南，核对规范、指南及实际参与判断的组件摘要。
  4. 冻结这次机制快照，将 ID、版本和摘要写入本轮事件、证据、handoff 与 baseline。
  5. 若指针缺失、状态非 ACTIVE、版本不一致、摘要不匹配或 YAML/HTML 冲突，报告 MECHANISM_UNRESOLVED，不得回退为读取根目录提案并假定生效。
  6. 仅首次迁移可读取本根目录提案；输出必须标明 bootstrap_mode=true 和 mechanism_status=PROPOSED。

规则从事故到生效

  1. 事故或漏检先记录为不可改写的案例，包含当时输入、旧机制输出和人工正确答案。
  2. 提出最小规则变更，声明它要修复的案例、可能误伤的范围和退出条件。
  3. 在历史正例、反例和边界例上回放；不能只验证促成该规则的单一事故。
  4. 影子运行至少一个真实迭代周期，对比新旧机制产生的冲突数、漏检数、人工问题数和交付阻塞时长。
  5. 人批准后冻结 YAML 规范源和同版本 HTML，记录两者摘要与 activation Decision；已发布文件不可原地修改。
  6. 原子更新 current.yaml，再更新选择迁移的项目和 baseline；旧 baseline 保持旧版本并可重放。
  7. 规则长期零命中、误报过高或前提失效时进入退役提案，同样走回放与批准。
局部绑定原则：证据不只绑定一个粗粒度的“机制总版本”，还绑定实际参与判定的 policy component digest。修改文档排版规则不应让数据库一致性证据失效；修改测试证据等级规则才应重开相应验证结论。
08

桌面推演：用当前项目反过来攻击这套机制

下面不是理想流程示意，而是用本仓库已经发生或很可能发生的变化验证机制。每个案例都检查：会不会误覆盖、会不会全量重跑、会不会把未知伪装成完成、会不会阻塞无关工作。

SIM-01 / SPEC

业务一手资料更新：签收凭证前提被否定

输入：评审说明客户签收完全无感，司机带纸质出库单回仓库，旧用例却让客户在群内发签收照片。

机制结果：创建新的事实 Source；命中 CLM-RECEIPT-CHAIN 的前提冲突。由于业务 owner 的当前事实对“真实流程”有权威，旧 claim 不被悄悄删除，而转为 CHALLENGED。只让 XS6 demo、凭证流程、相关权限和 CQ-09 测试进入 stale；订单查询、审价等无关区域继续。

判断：通过 局部阻塞且保留审计，没有让 demo 的存在反向证明业务流程成立。

SIM-02 / DOCS

产品文档落后：用例总表仍是 4 步向导

输入：同日会议决策和更晚 demo 都已采用单页长表单，docs/用例总表.html 尚未更新。

机制结果：三者关联同一 claim。Decision 明确 supersede 旧交互，demo 是该 accepted claim 的实现投影；用例总表被标记 STALE_VIEW，生成一个文档同步任务。无需人工裁决，也不重跑后端测试。

判断：通过 “更晚”只用于确认 demo 与决策的因果顺序；真正的权威来自已批准 Decision。

SIM-03 / DEMO

demo 先探索：设计师把物流图片改成小程序

输入：小程序在评审里是分期方向，但 demo 分支提前实现。

机制结果：若改动绑定 vNext deferred claim，则记录为 DEFERRED + IMPLEMENTED(demo)，不影响 v0 baseline；若它覆盖了 v0 场景且未声明 phase，则检测为 scope 冲突，要求补清阶段而非认定“最新 demo 就是需求”。

判断：通过 允许探索，不让探索无声升级为当前承诺。

SIM-04 / CODE

代码先修复：群内接口不再返回金额

输入：代码实现字段投影收紧，产品文档和 demo 已有“群内资金信息不发”规则。

机制结果：图谱找到 API projection、ReBAC、群截图与测试的共同 claim。代码 implementation 状态更新；相关契约与安全测试重跑；通过后将代码从 DRIFTED/PARTIAL 推到 IMPLEMENTED。不会因为代码先落地就生成新的业务决定。

判断：通过 代码可以领先于文档同步，但必须能追溯到已有承诺。

SIM-05 / TEST

测试更新：把“金额必须为空”改成“不检查金额”

输入：测试仍然全绿，但 oracle 被弱化。

机制结果：测试程序是 verifier。其 digest 和断言语义变化导致旧 PASS 证据 stale；校准用例应检测出断言强度下降。R2 权限声明没有有效 oracle 时回到 UNVERIFIED，禁止仅凭绿灯交付。

判断：通过 测试变化不会被当成普通实现维护；能防止“删断言换全绿”。

SIM-06 / METHOD

机制更新：规定所有 demo 改动必须先有 accepted claim

输入：新规则看似更一致，却会扼杀用 demo 探索交互的现实工作方式。

机制结果：历史回放会在早期 demo 探索案例中产生大量误报；影子运行显示问题包数量上升、迭代变慢。规则被修改为“demo 可实现 proposed claim，但不得进入交付 baseline，且改变高风险业务规则时必须先决策”。

判断：通过 慢循环能拒绝过度严格但不合用的治理规则。

故障注入结论

不会因更新来源不同而失灵

五类入口有不同语义，但都收敛到同一 claim/decision/evidence 模型。

不会因局部冲突而冻结全项目

按依赖图局部 stale；只有高风险且处于交付关键路径的未知才阻塞对应 baseline。

仍依赖一项人类纪律

业务 owner、产品 owner、技术 owner 和验收 owner 必须可识别。没有 owner 的高风险声明无法靠目录或算法补出来。

Agent Handoff：先确认起点，再继续工作

Handoff 不是一段会话摘要，而是一个有版本、有摘要、有接受回执的状态转移。接手 Agent 的第一件事不是扫描代码或执行待办，而是验证机制、baseline、交接包和交接后的变化窗口，建立可信起点。

接手第一原则：先证明“我接到的状态仍然是当前状态”，再继承任务；不能验证的上下文只能作为线索，不能作为继续实施或宣布完成的依据。

1

2
定位交接读取 project/handoffs/current.yaml 和固定 ID 的 manifest；禁止按目录时间挑“最新交接包”。
3
校验基点核对 repo、branch、commit、working-tree digest、baseline ID、机制版本、claim/evidence 索引摘要。
4
检查变化窗口比较 handoff.created_at 到当前时刻之间的提交、未提交修改、外部资料和过期证据；任何新增变化先进入正常收敛流。
5
恢复开放状态读取开放 claim、冲突、反例、临时豁免、等待人工问题和未完成验证；按风险和依赖重建下一步，不照抄前任优先级。
6

每次变化必须产出

  1. 一个带 digest、actor、时间与 kind 的 ArtifactChanged 事件。

  4. 自动任务或人工问题包；每项有 owner、风险、截止门禁和完成条件。

成功指标

变化到定位

从任一 spec/docs/demo/code/test 变化到生成受影响 claim 清单，目标小于 5 分钟。

问题到责任人

R2/R3 未知或冲突 100% 有 owner、问题包和最晚决策门。

声明到证据

每个进入 baseline 的高风险 claim 可在一次查询内回到来源、决策、实现和原始证据。

局部重算率

多数变化只重建受影响子图；全仓重跑必须能解释原因。

机制发现率

历史事故回放持续通过；新规则同时报告漏检下降与误报成本。

人工负担

衡量每轮问题包数量、决策等待时长和无效问题率，防止治理机制成为项目瓶颈。

最终目标不是让所有文件在每一刻完全相同，而是让任何差异都有类型、有原因、有权威范围、有影响半径、有下一步；让项目能在异步变化中持续前进，同时知道自己哪些地方尚未收敛。

      missing => return BOOTSTRAP_DIAGNOSTIC(PROJECT_CONTROL_PLANE_MISSING)

A.6 确定性 Handoff 接受算法

procedure ACCEPT_HANDOFF(valid_mechanism, max_attempts = 2):
  for attempt in 1..max_attempts:
    01. capture S0 := project snapshot and observation_started_at
    02. read exactly project/handoffs/current.yaml
        missing => return REJECTED(HANDOFF_POINTER_MISSING)
    03. require pointer selects exactly one handoff_id and status in {OFFERED, ACCEPTED}
    04. read selected manifest and every required file; validate schemas and digests
    05. require manifest mechanism id/version/digest == valid_mechanism snapshot
    06. require repo identity matches; referenced commit and baseline must exist
    07. compute change_window(manifest.change_cursor/created_at, S0)
    08. classify every change using the closed definitions in A.3
    09. load every open item; require id, status, risk, owner or explicit UNKNOWN,
        blocked_scope, next_gate, and evidence status
    10. independently recompute the next action from current risk/dependency state;
        predecessor recommendation is advisory only
    11. capture S1 using the same snapshot algorithm
    12. if S1 != S0: append HANDOFF_RACE and restart the loop
    13. decide by A.7; write acceptance receipt bound to S1
    14. reread receipt and verify its digest; return decision
  end
  return REJECTED(HANDOFF_RACE_EXHAUSTED)
end

步骤 13 的写入只有在用户当前请求和运行环境授权写入时才执行。若写入未获授权，Agent 必须输出同构的内存回执并标记 receipt_persisted=false；此时 handoff decision 可以表示本次观察结论，但持久化 handoff 状态保持不变，Agent 不得声称仓库已记录接受。

CANONICALIZATION_FAILED路径、文本、时间或摘要输入无法按 A.3.1 规范化修复输入或由机制新版本显式定义处理规则
DUPLICATE_ID_CONFLICT同一稳定 ID 对应不同内容创建冲突记录并由 owner 裁决，禁止覆盖

“停止”只停止依赖该无效前提的动作。Agent 仍可执行更高优先级指令允许的只读诊断、报告事实或处理明确不相交的任务；但不得使用未解析的机制、handoff 或 baseline 作完成性结论。

A.10 幂等性、并发与更新后义务

  1. 幂等：相同 snapshot、相同机制、相同 handoff 输入必须产生相同 decision、reason codes 和 blocked scope；Agent 文风差异不得改变判定。
  2. 并发：任何指针、HEAD、工作区、机制、baseline、handoff、event cursor 或证据新鲜度在校验中变化，都视为 snapshot 变化，按 A.6 重试；不得把前后两次观察拼成一个 snapshot。
  3. 最小写入：接手校验默认只读。除 acceptance receipt 外，不得在 READY 前修改项目制品；receipt 写入也必须在用户授权范围内。
  4. 变更后重验证：Agent 自己造成的任何 snapshot 变化都必须进入正常事件流；完成前重新核对机制版本、受影响 claim、证据与开放项。
  5. 交出义务：Agent 停止、换人、换线程或上下文将无法完整保留时，必须在授权允许下生成新的 OFFERED handoff；不得覆盖上一份已接受回执。
  6. 无自证：同一 Agent 可以生成交接提议，也可以在连续工作中做一致性自检，但不得把自己的自检描述为独立接手验证；需要独立性时必须由不同 Agent 或人产生 acceptance。

A.12 可验证性边界与激活门槛

规则 ID规范要求
ECM-ACT-001本 HTML 附录定义语义契约，但单独存在时不能证明实现符合。ECM 版本只有同时发布 YAML Schema、canonicalizer、状态机/决策表测试向量和可重放 validator，才允许标记 ACTIVE。
ECM-ACT-002激活测试必须至少覆盖：缺失指针、根外路径、摘要错配、HTML/YAML 冲突、重复 ID、R3 UNKNOWN、CONDITIONAL scope 相交、两次并发变化、无写权限回执和 bootstrap 禁止自激活。
ECM-ACT-003validator 输出必须包含协议版本、输入 snapshot、每条适用规则 PASS/FAIL/NOT_APPLICABLE、最终状态和失败码；只输出布尔值不符合。
ECM-ACT-004若两个符合性实现对同一测试向量产生不同最终状态、失败码或 allowed actions，该机制版本为 CALIBRATION_FAILED，不得用于门禁。
符合性不是“听起来遵循了原则”，而是同一输入得到同一状态、同一失败码和同一允许动作。任何无法确定的字段都保留为 UNKNOWN；任何未获授权的动作都保持未执行；任何机制、交接或基线歧义都不得由 Agent 自行猜平。
