1 · 一句话结论

能完成，但不是「现在就能发」。当前仓库已经有一套能自己跑通订单全流程的引擎（下单→审价→终审→备货→发货→开票→回单），也有读飞书数据的同步骨架；但最新发布计划 v0.1 的真正命门——销售助手在企微/PC 下单，订单写进旧飞书三方审批流并续跑——对应的桥接代码还不存在。

好在这条命门在《B2B_V01_对比与同步设计_20260818》里已有明确方案（方案 A1：代理 OAuth + 调用旧系统既有下单接口），我们逐行核对了旧系统接口，是真实可用的。因此：技术上有能力评估；发布计划成立；能否赶上 08-21，取决于是否接受「最小上线切片」——先做「下单桥接 + 我的订单 + 跳转旧系统详情」，把存量订单同步、前端精装修、复制重提等体验项后置。

最难的仗在 0.5 真相源切换（JSONL→PG 一次性迁移 + 两级终审迁入），那是「切换项目」级别，必须单独立项，不是普通一版。

4.1 v0.1 的真实范围（已由 2026-08-18 决策锁定，勿再推翻）

  • 唯一用户：销售助手虹励；其他用户零影响、继续用飞书。
  • 只做三件事：① 在 v0.1 侧下单；② 订单写进旧飞书审批流，旧系统继续跑完后续所有环节；③ v0.1 列表/详情能回显状态、跳转旧系统 flows 页。
  • 明确不做：v0.1 不执行备货/发货/开票；不迁移 JSONL；不修旧系统 bug；不新增旧系统导出端点；自动下单/锁库存继续移出。
  • 开发量边界：为上线新增的开发量全部算 v0.1；旧系统只允许一处小改（自动确认 + V01 profile 注入），其余只做配置/数据操作。

5 · 缺什么：12 个风险 Gap 总表

读表说明：类型里「施工」= 我们自己写代码就能解决；「决策」= 必须业务方/外部给信息才能定；「配置」= 不用写代码但要有人去旧系统后台/数据文件操作；「旧改」= 需要动旧系统代码（有边界）。大小 S=1 人日内，M=2–4 人日，L=5–10 人日，XL=跨版本项目级。

# Gap 现状 类型 大小 能否补 怎么补（说人话）
G1 下单桥接模块
（v0.1 命门）		 没有 施工 L 能 新建 internal/bridge：① 代理飞书 OAuth 授权；② 拿 code 调旧系统既有 /api/approval/feishu-user-by-code 换 token 并缓存；③ 把销售助手表单映射为旧系统 POST /external-orders/create 的字段；④ 成功后回写 flow_id/instance_id 到 PG。字段映射和错误分类设计文档 §6.2 已给全。
G2 旧系统针对性小改
（自动确认信息确认 + V01 profile）		 未开工 旧改 S 能 只改旧系统下单创建处（submitExternalOrder.ts）：识别 v0.1 幂等键前缀 → 自动通过「信息确认」节点 + 注入 V01_SALES_ASSISTANT profile。改动收敛一处、只影响 v0.1 订单；但要独立测试服务验证后上生产。
G3 销售助手前端
（下单页 + 我的订单 + 详情跳转）		 没有 施工 L 能 本仓库无 web/ 目录。最小做法：先做一个极简 PC 后台页（下单表单 + 我的订单列表 + 点详情跳旧系统 /flows/:flow_id），跑通闭环；企微入口和精装修后置。ord_fulfill demo 只能当交互稿，不是可上线前端。
G4 存量订单同步
（多维表 HTTP 源）		 半成品 施工 + 决策 M 能 同步骨架已有（cmd/sync + 幂等批次），但 HTTPFetcher 是占位报错、column_map 为空。需要：① 实现飞书 bitable API 拉取；② 回填字段映射配置；③ 飞书应用先有 bitable 读权限（外部配置）。此 Gap 可后置 1 周——销售助手下单后可在飞书审批中心直接看进度。
G5 T1.3 五项状态语义拍板 未决 决策 无代码量 能 5 个问题（订单撤回/作废、发货取消、回单位置、开票信息填写位置、盖章回传）需要业务方拍板。不拍板就先用「旧系统原始状态/节点文字」展示，不阻塞下单主链，但会卡住状态映射配置冻结。
G6 旧系统配置/数据操作
（白名单、回调地址、审批人）		 未做 配置 S 能 四件事：① 旧飞书应用重定向白名单加 v0.1 回调地址；② agent/sales 白名单加虹励；③ V01 profile 显式配 TEST_SUPERVISOR（必配！否则 fallback 到王杰→卡单）；④ 确认生产 role map 是否与提供文件一致。都有明确清单（附录 D）。
G7 企微备案域名 未就绪 决策 不定 能绕行 企微群聊/侧边栏入口依赖备案域名。未就绪就先用 PC 订单后台 + 飞书授权 + 飞书审批中心，体验闭环照样能跑；企微入口后置。这是关键路径上的外部依赖。
G8 企微官方通道补全
（template_card、群发）		 简化 施工 M 能 OfficialGateway 的 SendCard 现在是 text 简化版；GroupSender 无 official 实现（只有 mock）。v0.1 最小切片不依赖它；等企微入口提上日程时再补 template_card 和群发。
G9 部署与监控补齐 半 施工 S–M 能 compose 已有 9 服务（含 sync）、Dockerfile 4 target；缺前端静态资源容器、证据文件卷、日志/审计目录挂载、同步失败告警。上线前按 v0.1/10-deployment 清单补齐。
G10 v0.2 受信办理通道 未开工 施工 + 旧改 M 能 新系统办理 → 旧系统 decision 接口。旧系统三个 decision 接口只认 approver_token、支持文件上传，已验证无鉴权死路；v0.2 前补真实 operator + 幂等锁即可。不阻塞 v0.1。
G11 v0.4 新系统详情页/附件查看自立 未开工 施工 L 能 0.5 前必须就绪，否则旧系统停机后详情/附件变死路。依赖 G3 前端建设时一并规划。
G12 0.5 真相源切换 未开工 施工 + 决策 XL 能 最大工程风险：JSONL 级全量迁移（含事件链）+ 新系统审批台 + 环节编排接管 + 切换仪式 + 演练。设计已有（P0-7/P0-8），应作为「切换项目」单独立项，不随普通版本排期。

🧭 决策 / 外部信息

这些不是写代码能解决的，必须拿到答案才能冻结配置。好在设计文档已经把它们和代码解耦：没拍板前可以先过渡，不阻塞下单主链。

  • G5 五项状态语义：影响状态回显映射，可先用旧系统原始状态文字过渡。
  • G7 企微备案域名：影响企微入口，可先用 PC 后台过渡。
  • G6/D5 审批人与结算方式：不拍板会卡单或走错财务闸门，必须上线前关闭。
  • 飞书 bitable 读权限：只影响存量订单列表（P1），不阻塞下单。

🔧 施工 / 内部可控

这些是我们可以直接排期开发的。最大的是 G1（桥接）和 G3（前端），但都有明确方案和接口依据。

  • G1 桥接模块：方案 A1 已定，依赖旧系统既有接口（已验证存在），无未知技术风险。
  • G3 前端：工作量最大，但可以用「极简 PC 后台」策略把 v0.1 闭环先跑通。
  • G4/G8/G9：有骨架，补完即可。
  • G10–G12：后续版本施工，按周迭代排，别挤进 08-21。
